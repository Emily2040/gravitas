# gravitas

[English](./README.md) · [简体中文](./README.zh-CN.md) · **日本語** · [한국어](./README.ko.md)

[Google Antigravity](https://antigravity.google/) 向けのオーケストレーションスキル。作業を並列サブエージェントに分配し、さらなるテキストではなく実際に動いているソフトウェアの挙動に照らして主張を検証し、機械的な文体を取り除く測定可能な文章基準を成果物に課す。

`agy` CLI 1.2.7 と Antigravity Hub 2.15.0 で構築・検証。

---

## このスキルが実際に解決する問題

AI コーディングエージェントで少し大きめの作業をしたことがあれば、次の三つは見覚えがあるはずだ。

**一つめ、もっともらしい不完全さ。** 「プロジェクト全体にセキュリティ上の問題がないか調べて」と頼む。エージェントはファイルを三つ丁寧に読み、本物の問題を二つ見つけ、筋の通った報告書を書き、そこで止まる。報告書には「三つのファイルしか見ていない」とは書かれていない。読んだ側はプロジェクトが監査されたと受け取る。実際にはコードの九割は一度も開かれていない。

エージェントが嘘をついているわけではない。見つけた問題は本物だ。問題は「何かを見つけた」を「探し終えた」として扱っている点にあり、カバー率を述べさせる仕組みがどこにもない点にある。

**二つめ、合意による幻覚。** 信頼性を上げようとして、同じコードを五体のエージェントに独立して審査させ、多数決を取る。五体とも「ここのロックは安全だ」と言う。それを信じる。

しかしその五体は同じテキストを読み、同じ推論の仕方を使っている。誤りは独立ではなく相関している。同じ盲点が五つ重なっても洞察にはならず、より自信に満ちた誤りになるだけだ。投票者を増やしても推論は事実に変わらない。

**三つめ、機械的な文体。** エージェントが書いた不具合報告は内容としては完全に正しい。しかし全文にダッシュが走り、段落ごとに「X ではなく Y」の対比構文が入り、文の長さが不自然にそろっている。メンテナは一目で生成物だと判断し、読むのをやめる。

ここでは内容の正しさが効かない。評価される機会そのものが来ないからだ。

## 中核となる主張：証拠の階層

本スキルは、すべての結論に「どうやって確立されたか」を明記することを求める。

| 階層 | 根拠 | 具体例 |
|---|---|---|
| **1. observed 観測済み** | 動いているものを実際に見た | スクリーンショット、コンソールログ、実際のネットワークペイロード、描画後の DOM |
| **2. executed 実行済み** | 実行し、その結果を確認した | テスト通過、終了コード 0、クエリが実際に行を返した |
| **3. read 読んだ** | ソースにそう書いてある | 「このハンドラは入力を検証している」 |
| **4. inferred 推論** | エージェントがそう推論した | 「おそらく競合状態だろう」 |

決定的な規則が一つある。**第 4 階層の主張は仮説であって結論ではない。**

敵対的な投票、つまり複数のエージェントに互いを反証させる手法は、主張を第 4 階層の内部で動かすだけだ。第 3 階層以上へ昇格させることは決してできない。昇格には、何かを実際に実行することが要る。

当たり前に聞こえるが、これを硬い規則として書いているオーケストレーション基盤はほとんどない。多くは「エージェントを増やして見せる」だけで、意見の一致を信頼性として扱う。それは相関を独立と取り違えている。

## なぜこのスキルは Antigravity でしか成立しないのか

マルチエージェントのオーケストレーションに関する助言のほぼすべてが、道具立てを「テキストとファイル」と前提している。実際、ほとんどのエージェント基盤にはそれしかないからだ。

**Gemini は見える。** Antigravity はそれを使える道具にした。ブラウザのスクリーンショット、コンソールの捕捉、ネットワークリクエストの検査、ページ内での JavaScript 実行、画像生成、そしてブラウザ専任のサブエージェント。

これは検証を議論から観測へと変える。

具体例を挙げる。エージェントがボタンのスタイルを変更したとする。

*視覚がない場合*の検証は、CSS を読み、コンポーネントを読み、その組み合わせがどう描画されるかを推論することを意味する。エージェントは「変更は正しそうです」と言う。

*視覚がある場合*の検証は、アプリを起動し、変更前のスクリーンショットを撮り、変更後のスクリーンショットを撮り、両方を新しい読み取り専用の批評エージェントに渡して、差分を記述させ、それが意図した差分かどうかを判定させることを意味する。

後者は、前者では構造的に発見できない種類の欠陥をまとめて捕まえる。

- 要素同士の重なり
- コンテナに切られたテキスト
- 基準を満たさないコントラスト比
- 画面外に描画された要素
- 幅 400px で崩れるレイアウト
- 終わらないスピナー
- DOM には存在するが人間の目には見えないコントロール

コードを読むだけでは、どれ一つ見つからない。これらは描画の結果であって、ソース中の文字列ではない。

同じ理屈は API 契約にも及ぶ。クライアントを読み、サーバを読み、両者が一致しているかを推論するより、実際にその経路を通し、`browser_list_network_requests` で本当に飛んだリクエストを読むほうが早い。テキスト審査では推測しかできない問題が一度に片づく。二重送信、そもそも飛んでいないリクエスト、クライアントが送りサーバが無視しているフィールド、ステータス 200 なのに本文がエラーの応答、リトライの嵐。

## サブエージェントは二段階

これは実測で判明した落とし穴で、ドキュメントでは強調されていない。

**サブエージェントは定義してからでなければ呼び出せない。** ランタイムはこの点について明確だ。*"Subagent %q defined successfully. It can now be invoked via invoke_subagent"*、そして *"at least one subagent spec is required."*

定義を飛ばすのが最も多い失敗である。`invoke_subagent` は宣言されていない専門家を見つけられず、ファンアウト全体が静かに空振りする。

モデル階層は、その役割が実際に行う仕事で選ぶ。

| 階層 | 用途 |
|---|---|
| `MODEL_TIER_FLASH_LITE` | 機械的な抽出、ファイルの振り分け、広く浅い探索 |
| `MODEL_TIER_FLASH` | 探索役、読解役、ブラウザ観測役 |
| `MODEL_TIER_PRO` | 判定役、反証役、視覚批評役、最終統合 |
| `MODEL_TIER_INHERIT` | 実装。利用者が選んだモデルに従わせる |

ファイルの振り分けに PRO を払うのは無駄だ。視覚批評を FLASH_LITE で走らせるのは偽の節約である。そして実装に `INHERIT` を使うことには意味がある。利用者が選んだモデルを黙って格下げするのは、利用者がしていない決定だからだ。

見落とされやすい規則がもう一つある。**批評役は読み取り専用でなければならない。** 書き込める批評役は批評役ではない。自分が誤診したものを自分で直し、成功したと報告してしまう。

## 反復には規律が要る

「完璧になるまで直し続ける」は最も直感的なエージェントループであり、研究上もっとも信頼できないと示されているものでもある。

Huang ら（ICLR 2024）は**内在的自己修正**を、モデルが「外部フィードバックという杖なしに、自身の能力だけに基づいて」回答を修正することと定義し、モデルは「外部フィードバックなしでは自己修正に苦労し、自己修正のあとでかえって性能が下がることさえある」と報告している。

結論より機構のほうが重要だ。**モデルは誤りの位置を教えられればたいてい直せるが、自分の出力の中からその位置を確実に見つけることはできない。** 誤りを生んだ推論そのものが、その誤りを捕まえるよう求められている。

つまりループは回数不足で失敗するのではない。各周回に新しい材料がないから失敗する。

そこで本スキルはループを二種類に分け、正反対の規則を課す。

**収束ループ**は正しさを追う。各周回は新しい外部シグナルを必ず消費し、そのシグナルは誤りの位置を特定できるものでなければならない。失敗したアサーション、スタックトレース、コンソール例外、スクリーンショットの差分、期待と矛盾するネットワーク応答。新しいシグナルがなければ止める。

**勾配ループ**は品質を追う。文章、命名、API の手触り、レイアウトなど、逸脱する唯一の正解が存在しない領域。既定で 3 周、5 周を超えてはならない。実測された形状は一貫している。改善は最初の一、二周に集中し、三周から四周あたりで飽和し、三周を超えると逆転しうる。

**決して反復しない**のは、反証もできずシグナルも得られない判断。独立した意見を一度取り、仮説として明記し、先へ進む。

## インストール

Antigravity はワークスペースの `.agents/` ディレクトリを走査しないため、グローバルなスキルディレクトリが唯一の選択肢になる。

```bash
git clone <このリポジトリ> && cd <このリポジトリ>
bash scripts/install.sh ja
```

```powershell
git clone <このリポジトリ>; cd <このリポジトリ>
pwsh scripts/install.ps1 ja
```

言語は `en`、`zh-CN`、`ja`、`ko` から選べる。どの言語版も同じスキル名を使うため、同時に入れられるのは一つだけである。切り替えるには言語を変えて再実行する。

インストールスクリプトは該当ディレクトリを `~/.gemini/config/skills/gravitas/` に複製し、その場で検証する。完了後は Antigravity を再起動すること。

英語版をインストールした場合でも、トリガー語に日本語・中国語・韓国語の語彙が含まれているため、日本語で書いた依頼でも起動する。

```

scripts/
  check_skills.py          Antigravity が黙って飛ばす前にスキルを検証する
  slopcheck.py             機械的文体の構造的痕跡を測る
  install.sh / install.ps1
  rename.py                フックまで含めて一括改名
```

## 二つのツール

**`check_skills.py`** が必要な理由は、壊れた `SKILL.md` が黙って飛ばされるからだ。解析エラーはローテーションログにしか書かれず、利用者の目には決して入らない。つまりスキルは突然読み込まれなくなり、どこにも告知は出ない。

Windows ではとくに起こりやすい。UTF-8 の BOM だけで発生し、Windows PowerShell の `Set-Content` と `Out-File` は既定で BOM を付ける。完全に正しいスキルを書いたのに、目に見えない一バイトのせいで拒否される。

```bash
python scripts/check_skills.py
```

frontmatter が解析できるか、`name` が存在しディレクトリ名と一致するか、`description` があるか、BOM の有無、相対リンクの切れ、`SKILL.md` の欠落を検査する。問題があれば終了コード 1 を返す。

**`slopcheck.py`** は語彙ブラックリストでは見えないものを測る。文章は特定の語を一つも含まずに、それでもはっきり生成物として読める。痕跡が構造に宿っているからだ。

```bash
python scripts/slopcheck.py <ファイル>
```

ダッシュの密度、文長の平均と標準偏差、短文の数、太字始まりの割合、対比構文、曖昧な強調語、修辞疑問を報告する。

**日本語についての重要な注意：** 対比構文、強調語、語彙ブラックリストの三つの検査は英語向けであり、日本語を処理するときは明示的に飛ばされ、その旨が出力に出る。検査を通過したかのように装うことはしない。文長とリズムの検査は日本語でも有効で、語数ではなく文字数で数え、閾値もそれに合わせてある。日本語の機械的文体は別の形をとる。「〜することができます」の多用、すべての段落が同じ長さ、体言止めの連発、「いかがでしたでしょうか」の類の締め、助詞を省いた名詞の積み重ね。これらは今のところ人間の目で判断する必要がある。

## 組み込まれているプラットフォーム制約

いずれも 1.2.7 で再現済みで、欠陥にあたるものは報告済みである。

- ワークスペースの `.agents/` 配下のカスタマイズは決して読み込まれない。スキル、フック、ルール、プラグインのいずれも。
- 壊れたスキルは黙って飛ばされる。
- `force_continue` に反復上限がない。三回の計測で 3、8、12 周となり、12 はテスト側が設けた自己制限であってプラットフォームのものではない。
- ヘッドレスでは `autoExecutionPolicy: AUTO` が効かず、`PreToolUse` フックが `decision: "allow"` を返しても呼び出しは許可されない。ただし `deny` は実際に阻止し、`overwrite` は実際に適用される。
- 権限の許可はコマンドの文字列そのものとして保存されるため、蓄積する一方でほぼ再一致しない。ある環境では設定ファイルが 301 KB に達し、その 97.5% が二度と一致しない死んだ許可だった。

詳細と回避策は `skill/references/platform.md` を参照。
