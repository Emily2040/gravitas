# gravitas

[English](./README.md) · [简体中文](./README.zh-CN.md) · [日本語](./README.ja.md) · **한국어**

[Google Antigravity](https://antigravity.google/) 를 위한 오케스트레이션 스킬. 작업을 병렬 서브에이전트에 나눠 맡기고, 더 많은 텍스트가 아니라 실제로 돌아가는 소프트웨어의 동작에 비추어 주장을 검증하며, 기계적인 문체를 걷어내는 측정 가능한 문장 기준을 결과물에 적용한다.

`agy` CLI 1.2.7 과 Antigravity Hub 2.15.0 에서 만들고 시험했다.

---

## 이 스킬이 실제로 해결하는 문제

AI 코딩 에이전트로 조금이라도 큰 작업을 해 봤다면 아래 세 가지는 낯익을 것이다.

**첫째, 그럴듯한 불완전성.** "프로젝트 전체에 보안 문제가 있는지 살펴봐"라고 시킨다. 에이전트는 파일 세 개를 꼼꼼히 읽고, 진짜 문제 두 개를 찾아내고, 조리 있는 보고서를 쓰고, 거기서 멈춘다. 보고서에는 파일 세 개만 봤다는 말이 없다. 읽는 쪽은 프로젝트가 감사되었다고 받아들인다. 실제로는 코드의 90퍼센트가 한 번도 열리지 않았다.

에이전트가 거짓말을 한 것은 아니다. 찾아낸 문제는 진짜다. 문제는 "뭔가를 찾았다"를 "다 찾았다"로 취급했다는 점, 그리고 커버리지를 말하게 강제하는 장치가 어디에도 없다는 점이다.

**둘째, 합의된 환각.** 신뢰도를 높이려고 같은 코드를 에이전트 다섯이 각자 검토하게 하고 다수결을 낸다. 다섯 모두 "여기 락은 안전하다"고 말한다. 그래서 믿는다.

그러나 그 다섯은 같은 텍스트를 읽었고 같은 추론 방식을 썼다. 오류가 독립적이지 않고 상관되어 있다. 같은 사각지대 다섯 개가 겹친다고 통찰이 되지는 않는다. 더 자신만만한 오류가 될 뿐이다. 투표자를 늘려도 추론이 사실로 바뀌지 않는다.

**셋째, 기계적인 문체.** 에이전트가 쓴 결함 보고서는 내용상 완전히 옳다. 그런데 전체에 대시가 흐르고, 문단마다 "X 가 아니라 Y" 대조 구문이 들어가고, 문장 길이가 부자연스럽게 고르다. 메인테이너는 한눈에 생성물이라고 판단하고 읽기를 그만둔다.

여기서는 내용의 정확성이 작동하지 않는다. 평가받을 기회 자체가 오지 않기 때문이다.

## 핵심 주장: 증거 계층

이 스킬은 모든 결론에 "어떻게 확립되었는가"를 표기하도록 요구한다.

| 계층 | 근거 | 구체적인 예 |
|---|---|---|
| **1. observed 관찰됨** | 실행 중인 것을 직접 보았다 | 스크린샷, 콘솔 로그, 실제 네트워크 페이로드, 렌더링된 DOM |
| **2. executed 실행됨** | 실행했고 그 결과를 확인했다 | 테스트 통과, 종료 코드 0, 쿼리가 실제로 행을 반환 |
| **3. read 읽음** | 소스에 그렇게 쓰여 있다 | "이 핸들러는 입력을 검증한다" |
| **4. inferred 추론됨** | 어떤 에이전트가 그렇게 추론했다 | "아마 경쟁 상태일 것이다" |

결정적인 규칙이 하나 있다. **4계층 주장은 결론이 아니라 가설이다.**

적대적 투표, 즉 여러 에이전트에게 서로를 반증하게 하는 방식은 주장을 4계층 안에서 움직일 뿐이다. 3계층 이상으로 승격시키는 일은 결코 없다. 승격하려면 무언가를 실제로 실행해야 한다.

당연해 보이지만 이것을 단단한 규칙으로 적어 둔 오케스트레이션 프레임워크는 거의 없다. 대부분은 "에이전트를 더 붙여서 보게 한다"에 그치고, 의견 일치를 신뢰도로 취급한다. 그것은 상관을 독립으로 착각하는 것이다.

## 왜 이 스킬은 Antigravity 에서만 성립하는가

멀티 에이전트 오케스트레이션에 관한 조언은 거의 전부 도구 표면을 "텍스트와 파일"로 전제한다. 실제로 대부분의 에이전트 환경에는 그것뿐이기 때문이다.

**Gemini 는 볼 수 있다.** Antigravity 는 그것을 쓸 수 있는 도구로 만들었다. 브라우저 스크린샷, 콘솔 캡처, 네트워크 요청 검사, 페이지 내 JavaScript 실행, 이미지 생성, 그리고 브라우저 전담 서브에이전트.

이것이 검증을 논쟁에서 관찰로 바꾼다.

구체적인 예를 들자. 에이전트가 버튼 스타일을 바꿨다고 하자.

*시각이 없을 때*의 검증은 CSS 를 읽고, 컴포넌트를 읽고, 그 조합이 어떻게 그려질지 추론하는 것을 뜻한다. 에이전트는 "변경이 맞아 보입니다"라고 말한다.

*시각이 있을 때*의 검증은 앱을 띄우고, 변경 전 스크린샷을 찍고, 변경 후 스크린샷을 찍고, 둘 다 새로운 읽기 전용 비평 에이전트에게 넘겨 차이를 기술하게 하고 그것이 의도한 차이인지 판정하게 하는 것을 뜻한다.

후자는 전자가 구조적으로 발견할 수 없는 종류의 결함을 통째로 잡아낸다.

- 요소끼리 겹침
- 컨테이너에 잘린 텍스트
- 기준에 못 미치는 명암비
- 화면 밖으로 렌더링된 요소
- 폭 400px 에서 무너지는 레이아웃
- 끝나지 않는 스피너
- DOM 에는 있지만 사람 눈에는 보이지 않는 컨트롤

코드만 읽어서는 어느 것도 찾을 수 없다. 이것들은 렌더링의 결과이지 소스 안의 문자열이 아니다.

같은 논리가 API 계약으로도 이어진다. 클라이언트를 읽고 서버를 읽고 둘이 맞는지 추론하기보다, 실제로 그 경로를 통과시키고 `browser_list_network_requests` 로 진짜 나간 요청을 읽는 편이 낫다. 텍스트 검토로는 추측만 가능한 문제들이 한 번에 정리된다. 중복 제출, 아예 나가지 않은 요청, 클라이언트가 보내고 서버가 무시하는 필드, 상태 코드는 200 인데 본문이 오류인 응답, 재시도 폭주.

## 서브에이전트는 두 단계다

이것은 실측으로 드러난 함정이고 문서에서 강조되지 않는다.

**서브에이전트는 정의한 뒤에야 호출할 수 있다.** 런타임은 이 점에 대해 분명하다. *"Subagent %q defined successfully. It can now be invoked via invoke_subagent"*, 그리고 *"at least one subagent spec is required."*

정의를 건너뛰는 것이 가장 흔한 실패다. `invoke_subagent` 는 선언된 적 없는 전문가를 찾지 못하고, 팬아웃 전체가 조용히 헛돈다.

모델 계층은 그 역할이 실제로 하는 일에 따라 고른다.

| 계층 | 용도 |
|---|---|
| `MODEL_TIER_FLASH_LITE` | 기계적 추출, 파일 분류, 넓고 얕은 탐색 |
| `MODEL_TIER_FLASH` | 탐색자, 독해자, 브라우저 관찰자 |
| `MODEL_TIER_PRO` | 판정자, 반증자, 시각 비평자, 최종 종합 |
| `MODEL_TIER_INHERIT` | 구현. 사용자가 고른 모델을 그대로 따르게 한다 |

파일 분류에 PRO 를 쓰는 것은 낭비다. 시각 비평을 FLASH_LITE 로 돌리는 것은 거짓 절약이다. 그리고 구현에 `INHERIT` 를 쓰는 데에는 이유가 있다. 사용자가 고른 모델을 조용히 강등하는 것은 사용자가 내린 적 없는 결정이기 때문이다.

놓치기 쉬운 규칙이 하나 더 있다. **비평자는 읽기 전용이어야 한다.** 쓸 수 있는 비평자는 비평자가 아니다. 자기가 오진한 것을 스스로 고치고 성공했다고 보고해 버린다.

## 반복에는 규율이 필요하다

"완벽해질 때까지 계속 고친다"는 가장 직관적인 에이전트 루프이며, 연구상 가장 신뢰할 수 없다고 밝혀진 것이기도 하다.

Huang 등(ICLR 2024)은 **내재적 자기 수정**을 모델이 "외부 피드백이라는 지팡이 없이 자신의 능력만으로" 답을 고치는 것으로 정의하고, 모델이 "외부 피드백 없이는 자기 수정에 어려움을 겪으며, 자기 수정 후 성능이 오히려 떨어지는 경우도 있다"고 보고한다.

결론보다 기제가 중요하다. **모델은 오류의 위치를 알려주면 대개 고칠 수 있지만, 자기 출력 안에서 그 위치를 안정적으로 찾아내지는 못한다.** 오류를 만든 그 추론이 오류를 잡아내라는 요구를 받고 있는 셈이다.

즉 루프는 횟수가 모자라서 실패하는 것이 아니다. 매 회차에 새로운 재료가 없어서 실패한다.

그래서 이 스킬은 루프를 두 종류로 나누고 정반대의 규칙을 건다.

**수렴 루프**는 정확성을 좇는다. 매 회차는 새로운 외부 신호를 소비해야 하고, 그 신호는 오류의 위치를 짚어주는 것이어야 한다. 실패한 단언, 스택 트레이스, 콘솔 예외, 스크린샷 차이, 기대와 어긋나는 네트워크 응답. 새 신호가 없으면 멈춘다.

**경사 루프**는 품질을 좇는다. 문장, 이름 짓기, API 사용감, 레이아웃처럼 벗어날 단일 정답이 없는 영역. 기본 3회, 5회를 넘기지 않는다. 측정된 모양은 일관된다. 개선은 첫 한두 회차에 몰리고, 세 번째에서 네 번째쯤 포화하며, 세 회차를 넘기면 뒤집힐 수 있다.

**절대 반복하지 않을 것**은 반증도 불가능하고 신호도 얻을 수 없는 판단이다. 독립적인 의견을 한 번 받고, 가설로 표기하고, 넘어간다.

## 설치

Antigravity 는 워크스페이스의 `.agents/` 디렉터리를 훑지 않으므로, 전역 스킬 디렉터리가 유일한 선택지다.

```bash
git clone <이 저장소> && cd <이 저장소>
bash scripts/install.sh ko
```

```powershell
git clone <이 저장소>; cd <이 저장소>
pwsh scripts/install.ps1 ko
```

언어는 `en`, `zh-CN`, `ja`, `ko` 중에서 고른다. 모든 언어판이 같은 스킬 이름을 쓰기 때문에 한 번에 하나만 설치할 수 있다. 바꾸려면 언어를 달리해 다시 실행한다.

설치 스크립트는 해당 디렉터리를 `~/.gemini/config/skills/gravitas/` 로 복사하고 곧바로 검증한다. 끝나면 Antigravity 를 재시작할 것.

영어판을 설치했더라도 트리거 어휘에 한국어, 중국어, 일본어 단어가 들어 있으므로 한국어로 쓴 요청에도 작동한다.

## 저장소 구조

```
skill/                     영어판, 기준 버전
  SKILL.md
  references/
locales/
  zh-CN/  ja/  ko/         각 언어판, 구조는 동일
scripts/
  check_skills.py          Antigravity 가 조용히 건너뛰기 전에 스킬을 검증
  slopcheck.py             기계적 문체의 구조적 흔적을 측정
  install.sh / install.ps1
  rename.py                훅까지 포함해 한 번에 이름 변경
```

## 두 가지 도구

**`check_skills.py`** 가 필요한 이유는 잘못된 `SKILL.md` 가 조용히 건너뛰어지기 때문이다. 파싱 오류는 순환 로그 파일에만 기록되고 사용자 눈에는 결코 들어오지 않는다. 즉 스킬이 갑자기 로드되지 않게 되고, 어디에도 알림이 없다.

Windows 에서 특히 잘 일어난다. UTF-8 BOM 하나면 충분하고, Windows PowerShell 의 `Set-Content` 와 `Out-File` 은 기본으로 BOM 을 붙인다. 완벽히 올바른 스킬을 써 놓고 보이지 않는 한 바이트 때문에 거부당한다.

```bash
python scripts/check_skills.py
```

frontmatter 가 파싱되는지, `name` 이 있고 디렉터리 이름과 일치하는지, `description` 이 있는지, BOM 이 있는지, 상대 링크가 끊겼는지, `SKILL.md` 가 빠졌는지 검사한다. 문제가 있으면 종료 코드 1 을 반환한다.

**`slopcheck.py`** 는 어휘 블랙리스트로는 보이지 않는 것을 측정한다. 글은 특정 단어를 하나도 쓰지 않고도 명백히 생성물로 읽힐 수 있다. 흔적이 구조에 있기 때문이다.

```bash
python scripts/slopcheck.py <파일>
```

대시 밀도, 문장 길이의 평균과 표준편차, 짧은 문장 수, 굵게 시작하는 비율, 대조 구문, 모호한 강조어, 수사 의문문을 보고한다.

**한국어에 대한 중요한 안내:** 대조 구문, 강조어, 어휘 블랙리스트 세 가지 검사는 영어용이며, 한국어를 처리할 때는 명시적으로 건너뛰고 그 사실을 출력에 표시한다. 검사를 통과한 것처럼 위장하지 않는다. 문장 길이와 리듬 검사는 한국어에도 유효하고, 단어 수가 아니라 글자 수로 세며 임계값도 그에 맞춰 두었다. 한국어의 기계적 문체는 다른 형태를 띤다. "~할 수 있습니다"의 반복, 모든 문단이 같은 길이, "~적인"의 남발, "결론적으로 말하자면" 같은 마무리 상투구. 이런 것들은 지금으로서는 사람 눈으로 판단해야 한다.

## 이 스킬이 담고 있는 플랫폼 제약

모두 1.2.7 에서 재현했고, 결함에 해당하는 것은 보고했다.

- 워크스페이스 `.agents/` 아래의 커스터마이즈는 결코 로드되지 않는다. 스킬, 훅, 규칙, 플러그인 모두.
- 잘못된 스킬은 조용히 건너뛰어진다.
- `force_continue` 에 반복 상한이 없다. 세 번 측정해 3회, 8회, 12회가 나왔고 12는 테스트 쪽이 건 자체 제한이지 플랫폼의 것이 아니다.
- 헤드리스에서 `autoExecutionPolicy: AUTO` 는 작동하지 않고, `PreToolUse` 훅이 `decision: "allow"` 를 반환해도 호출은 허용되지 않는다. 다만 `deny` 는 실제로 막고, `overwrite` 는 실제로 적용된다.
- 권한 허가는 명령의 문자열 그대로 저장되므로 쌓이기만 하고 거의 다시 일치하지 않는다. 어떤 환경에서는 설정 파일이 301 KB 까지 커졌고 그중 97.5퍼센트가 다시는 일치하지 않는 죽은 허가였다.

세부 사항과 우회 방법은 `skill/references/platform.md` 참조.
