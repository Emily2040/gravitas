# gravitas

[English](./README.md) · **简体中文** · [日本語](./README.ja.md) · [한국어](./README.ko.md)

一个面向 [Google Antigravity](https://antigravity.google/) 的编排技能。它把工作分派给并行的子代理，用运行中的软件的真实表现来验证结论而不是靠更多文本，并以一套可度量的文风标准约束产出，剔除机器腔调。

基于 `agy` CLI 1.2.7 与 Antigravity Hub 2.15.0 构建与测试。

---

## 这个技能到底解决什么问题

如果你用过任何 AI 编码代理做稍微大一点的任务，下面三种情况应该都不陌生。

**第一种：貌似完整。** 你让代理"检查整个项目有没有安全问题"。它认真看了三个文件，找到两个真实的问题，写了一份条理清晰的报告，然后停下了。报告没有说它只看了三个文件。你读完以为项目审计过了。实际上百分之九十的代码从未被打开过。

这不是代理在撒谎。它确实找到了真问题。问题在于它把"我找到了一些东西"当成了"我找完了"，而且没有任何机制迫使它说出覆盖率。

**第二种：共识性幻觉。** 为了提高可靠性，你让五个代理各自审查同一段代码，然后投票。五个都说"这里的锁是安全的"。你信了。

但这五个代理读的是同一份文本，用的是同一套推理方式。它们的错误是相关的，不是独立的。五个相同的盲区叠在一起，不会变成一个洞察，只会变成一个更自信的错误。增加投票者无法把一个推理变成事实。

**第三种：机器腔调。** 代理写出的缺陷报告内容完全正确，但通篇破折号、每段都是"不是 X，而是 Y"的对比句式、所有句子长度整齐划一。维护者扫一眼就知道这是生成的，于是不读了。

内容的正确性在这里不起作用，因为它根本没有被评估的机会。

## 它的核心主张：证据分层

本技能要求给每一条结论标注它是怎么被确立的。

| 层级 | 依据 | 具体例子 |
|---|---|---|
| **1. observed 已观察** | 你亲眼看了正在运行的东西 | 截图、控制台日志、网络请求的真实负载、渲染后的 DOM |
| **2. executed 已执行** | 它跑过了，并且结果被检查过 | 测试通过、命令退出码为 0、查询真的返回了行 |
| **3. read 已读取** | 源码这么写的 | "这个处理函数校验了输入" |
| **4. inferred 已推断** | 某个代理推理出来的 | "这里大概是竞态条件" |

关键的一条规则是：**第 4 层的主张是假设，不是结论。**

对抗式投票，也就是让多个代理互相反驳，只能在第 4 层内部移动一条主张。它永远无法把一条主张提升到第 3 层或更高。要提升层级，你必须真正去运行点什么。

这听起来像常识，但几乎没有编排框架把它写成硬规则。多数框架的做法是"多派几个代理去看"，然后把一致当作可信。那只是把相关性误当成独立性。

## 为什么这个技能只在 Antigravity 上成立

市面上绝大多数关于多代理编排的建议，都默认工具面是"文本加文件"。因为大多数代理框架确实只有这些。

**Gemini 能看见。** Antigravity 把这件事变成了可用的工具：浏览器截图、控制台捕获、网络请求检查、在页面中执行 JavaScript、生成图像，以及一个专门驱动浏览器的子代理。

这把验证从一场辩论变成了一次观察。

举个具体的例子。假设代理改了一个按钮的样式。

*没有视觉能力时*，验证意味着：读 CSS，读组件代码，推理这些改动合起来会产生什么效果。代理会说"改动看起来是正确的"。

*有视觉能力时*，验证意味着：把应用跑起来，改动前截一张图，改动后截一张图，把两张图交给一个全新的、只读的评审代理，让它描述差异并判断这个差异是不是想要的那个。

第二种方式能发现第一种方式在结构上不可能发现的一整类缺陷：

- 元素互相重叠
- 文字被容器裁切
- 颜色对比度不达标
- 元素渲染到了屏幕外
- 布局在 400px 宽度下塌陷
- 转圈动画永远不结束
- 控件存在于 DOM 里，但人眼看不见

没有任何代码阅读者能找到这些。它们是渲染的结果，不是源码里的字符串。

同样的道理延伸到接口契约。与其读客户端、读服务端、然后推理它们是否一致，不如真的走一遍这条路径，用 `browser_list_network_requests` 读实际发出的请求。这能一次性解决文本审查只能猜测的问题：重复提交、根本没发出的请求、客户端发了而服务端忽略的字段、状态码 200 但正文是错误的响应、重试风暴。

## 子代理必须分两步

这是一个实测出来的坑，文档里没有明确强调。

**子代理必须先定义，后调用。** 运行时对此很明确：*"Subagent %q defined successfully. It can now be invoked via invoke_subagent"*，以及 *"at least one subagent spec is required."*

跳过定义这一步是最常见的失败。`invoke_subagent` 找不到一个从未声明过的专家，于是整个扇出静默失效。

模型分层按角色实际做的事来选：

| 层级 | 用于 |
|---|---|
| `MODEL_TIER_FLASH_LITE` | 机械性抽取、文件初筛、广度扫描 |
| `MODEL_TIER_FLASH` | 查找者、阅读者、浏览器观察者 |
| `MODEL_TIER_PRO` | 裁判、反驳者、视觉评审、最终综合 |
| `MODEL_TIER_INHERIT` | 实现，让工作沿用用户自己选的模型 |

用 PRO 做文件初筛是浪费。用 FLASH_LITE 做视觉评审是假节省。而实现环节用 `INHERIT` 很重要，因为悄悄把用户选的模型降级，是一个用户没有做过的决定。

还有一条容易被忽略的规则：**评审者必须是只读的。** 一个能写文件的评审者不是评审者。它会去修自己可能误判的东西，然后报告成功。

## 迭代必须有纪律

"一直改到完美为止"是最直觉的代理循环，也是被研究证实最不可靠的一个。

Huang 等人（ICLR 2024）把**内在自我纠正**定义为模型"仅凭自身能力修正回答，没有外部反馈这根拐杖"，并发现模型"在没有外部反馈的情况下难以自我纠正，有时自我纠正之后性能反而下降"。

比结论更重要的是机制：**模型通常能在被告知错误位置之后修好它，却无法可靠地在自己的产出中找到这个位置。** 产生错误的那套推理，正是被要求去发现这个错误的推理。

所以循环失败不是因为跑得不够多，而是因为每一轮都没有新信息可用。

本技能因此把循环分成两类，规则完全相反。

**收敛型循环**追求正确性。每一轮都必须消费一个新的外部信号，且该信号必须能定位错误：失败的断言、堆栈跟踪、控制台异常、截图差异、与预期矛盾的网络响应。没有新信号就停下。

**梯度型循环**追求质量，用于散文、命名、接口手感、布局，这些地方不存在唯一正解。默认跑 3 轮，绝不超过 5 轮。实测形状很一致：收益集中在前一到两轮，大约第三到第四轮饱和，超过三轮后会开始反转。

**永不迭代**那些无法证伪、也拿不到信号的判断。取一次独立意见，标注为假设，继续往前。

## 安装

Antigravity 从不扫描工作区的 `.agents/` 目录，所以全局技能目录是唯一可行的位置。

```bash
git clone <本仓库> && cd <本仓库>
bash scripts/install.sh zh-CN
```

```powershell
git clone <本仓库>; cd <本仓库>
pwsh scripts/install.ps1 zh-CN
```

语言可选 `en`、`zh-CN`、`ja`、`ko`。因为各语言版本使用同一个技能名，同一时间只能安装一种。换语言就重新运行一次。

安装脚本会把对应目录复制到 `~/.gemini/config/skills/gravitas/` 并随即校验。装完请重启 Antigravity。

即使你安装的是英文版，技能的触发词里也包含了中文、日文、韩文的关键词，所以用中文提问同样能触发它。

## 两个工具

**`check_skills.py`** 存在的原因是：格式错误的 `SKILL.md` 会被静默跳过。解析错误只写进一个滚动日志文件，用户永远看不到。所以一个技能可能突然不再加载，而任何地方都不会提示。

在 Windows 上这尤其容易发生：一个 UTF-8 BOM 就足以触发，而 Windows PowerShell 的 `Set-Content` 和 `Out-File` 默认会加上 BOM。你写了一个完全正确的技能，却因为一个看不见的字节被拒绝。

```bash
python scripts/check_skills.py
```

检查 frontmatter 能否解析、`name` 是否存在且与目录名一致、`description` 是否存在、是否有 BOM、相对链接是否失效、`SKILL.md` 是否缺失。发现问题时退出码为 1。

**`slopcheck.py`** 度量词汇黑名单看不见的东西。一段文字可以完全不含"赋能""抓手""闭环"，读起来依然明显是生成的，因为破绽在结构里。

```bash
python scripts/slopcheck.py <文件>
```

它统计破折号密度、句长均值与标准差、短句数量、加粗开头的比例、对比式句式、模糊强调词、反问句。

**关于中文的重要说明：** 对比式句式、强调词与词汇黑名单这三项检查是针对英文的，处理中文时会被跳过，并在输出里明确提示，不会假装通过了检查。句长与节奏检查对中文有效，按字符数而非词数统计，阈值也相应调整过。中文的机器腔调有它自己的形态：四字短语堆砌、每段都以"不仅……而且……"收束、通篇句长整齐、以及"综上所述"一类的收尾套话。这些目前需要人眼判断。

## 它编码了哪些平台约束

以下都在 1.2.7 上复现过，属于缺陷的已上报。

- 工作区 `.agents/` 下的定制内容永远不会加载。技能、钩子、规则、插件都一样。
- 格式错误的技能被静默跳过。
- `force_continue` 没有迭代上限。三次测试分别跑出 3、8、12 轮，其中 12 是测试脚本自己设的限制，不是平台的。
- 无头模式下 `autoExecutionPolicy: AUTO` 不起作用，`PreToolUse` 钩子返回 `decision: "allow"` 也不会放行。但返回 `deny` 确实能拦截，`overwrite` 确实会生效。
- 权限授权保存的是命令的字面文本，因此会不断累积且几乎不会再次匹配。有一台机器上的配置文件涨到了 301 KB，其中 97.5% 是永不再匹配的死授权。

细节与绕行办法见 `skill/references/platform.md`。
