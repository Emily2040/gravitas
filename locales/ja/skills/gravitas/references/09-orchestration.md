# モジュール 09 - 編成

## 目的

このモジュールは、ファンアウトの組み立て方を扱います。結果を待つときと待たないとき、どの状況にどのパターンが合うか、そして台帳で件数と重複排除を正確に保つ方法です。標準規模以上で読み込みます。各パターンは、解決する問題、構造、防ぐ失敗を述べており、自由に組み合わせられます。

パターンは分野を問いません。探索役は作業リストの上でひとつの種類の欠陥を探し、作業リストはファイルでも、条文でも、論文でも、帳簿の行でもかまいません。マルチモーダルな掃引は複数の角度から同時に探し、コードベースならディレクトリ、呼び出しグラフ、描画結果、文献レビューなら引用のつながり、キーワード、著者、再現に失敗した研究を意味します。

## パターンの選び方

| 状況 | パターン |
| :--- | :--- |
| 独立した検証がある | 観察優先の検証（`04-runtime-verification.md`） |
| 問題がいくつあるかわからない | 枯れるまでのループ |
| ひとつの角度では見落とす | マルチモーダルな掃引 |
| 解の空間が広い | 審査団 |
| 発見がもっともらしくて誤っているかもしれない | 敵対的な反証 |
| 発見が複数の形で誤り得る | 観点の異なる検証 |
| 何かを見落としたかもしれない | 網羅性の批評 |
| 項目ごとのコストが大きく違う | 段階的な格上げ |
| 数百の項目を正確に数えたい | スクリプトによる編成（`13-platform.md`） |
| 修正を緑まで持っていかなければならない | 収束型のループ（`10-iteration.md`） |
| 出力に要るのは訂正ではなく磨き | 勾配型のループ（`10-iteration.md`） |

## まず偵察し、段階ごとにひとつのファンアウト

まず自分のツールで作業リストを見つけます。ファイルを一覧し、検索を走らせ、条文の索引を取り出し、目次を読みます。そして見つけたものに対してファンアウトします。複数段階の作業は、段階ごとにひとつのファンアウト（理解、設計、実装、レビュー）を順に行い、親は各結果を読んでから次を計画します。最初に計画した巨大なファンアウトは、まだ何も学んでいないときに書いた作業リストに縛られます。

## 既定はパイプライン

発見は出てきたらすぐに検証します。早く戻った探索役の発見は、遅い探索役がまだ作業している間に反証役の前に置かれるべきです。

全体がそろうのを待つのは、次の手順が一度にすべてを必要とするときだけです。高価な検証の前にすべての探索役の結果の重複を除くとき、合計がゼロで早期に終えるとき、発見どうしを比べる手順のときです。平坦化、絞り込み、整形には待ちは要らず、項目ごとに行います。五つの探索役が走り、最も遅いものが最も速いものの三倍かかるとき、何も必要としていない待ちは、速い結果を実行時間の三分の二のあいだ遊ばせます。

## 台帳

件数、重複排除、票の集計は帳簿付けであり、帳簿付けはコードの仕事です。三ラウンドにわたる四十の発見を頭の中で追うモデルは、数を間違え、すでに退けた発見を検証し直し、ループを早すぎたり遅すぎたりして止めます。`scripts/ledger.py` はその状態を JSON ファイルに保ち、判断を決定的にします。必要なのは Python 3.8 以上だけです。

インストールしたプラグイン内の完全なパス `<home>/.gemini/config/plugins/gravitas/skills/gravitas/scripts/ledger.py` で実行し、台帳ファイルは実行後も残るようにワークスペースか成果物のディレクトリに置きます。以下の例ではパスを短くしています。

```bash
python scripts/ledger.py init  run.ledger.json --scale full
python scripts/ledger.py add   run.ledger.json finder-security.json --round 1 --by gravitas-finder
python scripts/ledger.py verdict run.ledger.json <key> --by gravitas-refuter --refuted no \
    --tier executed --source "pytest tests/test_session.py::test_logout -> 1 failed"
python scripts/ledger.py verdicts run.ledger.json refuter-verdicts.json --by gravitas-refuter
python scripts/ledger.py child run.ledger.json --id <conversation-id> --agent gravitas-finder --status denied \
    --note "read_file denied on src/auth"
python scripts/ledger.py close-round run.ledger.json --round 1
python scripts/ledger.py report run.ledger.json
```

台帳が強制すること：

- 層が `observed`、`executed`、`read` で `source` が空のレコードは `inferred` に格下げされ、内容を何も引用していない `source` を持つ `read` レコードも格下げされます。三語以上か十二文字以上の引用が必要で、引用符で囲んだパスは引用に数えません。レコードは発見と判定のスキーマで検査され、形の崩れたものは理由を添えて退けられます。`01-evidence.md` の出所の規則が、台帳がすべてのレコードに対して行う検査になります。
- 新しいレコードは、反証役が退けたものも含め、これまでに加えたすべてのレコードと重複を照合します。生き残ったものとだけ照合すると、退けた発見が毎ラウンド戻ってきて、ループは収束しません。
- 同じ場所にある二つのレコードは、主張の語の少なくとも 0.25 が重なれば自動的に統合され、0.10 以上で重複の可能性として示されます。同じファイルで 5 行以内にあるレコードは、言い回しがほぼ同じ（0.8）ときだけ自動的に統合され、それ以外は示されるだけです。数行離れた別の欠陥は、よく似た言葉で書かれがちだからです。ある実際の監査では、本当の重複は 0.13〜0.69、同じ行の別の欠陥は 0.02〜0.15 で、自動統合は 22 件のレコードを 15 件にし、誤った統合はありませんでした。示されたものは `ledger.py merge KEEP DUP` で決め、票も移します。
- 発見が生き残るのは、数えられた票のうち反証しなかった票が過半数のときだけで、必要な票数は規模で決まります。標準は 1、フルと網羅は 3 です。票にも発見と同じ出所の規則が適用され、格下げされた票や状態が `blocked` の票は記録されますが数えられません。クイックの規模では票を取らないので、報告は発見を未検証として挙げます。
- `close-round` は新しい発見を数え、枯渇のカウンターを進め、`CONTINUE` か `STOP` を理由とともに出します。枯渇ラウンド数に達したか、ラウンドの上限に達したかです。
- `report` は生き残った発見を深刻度順に層と出所を添えて並べ、次に反証済み、保留、格下げのレコード、次に状態が `done` でないすべての子と `blocked` を返したすべての探索役、最後に上限を挙げます。

台帳ファイルは最後のターンが失われても残るので、ユーザーが見つけられる場所に置きます。Python がなければ、同じ項目を計画の成果物の表に保ち、同じ規則を手で適用し、台帳を手作業で付けたことを報告に書きます。

## 枯れるまでのループ

問題がいくつあるかわからないときに使います。バグ、セキュリティ上の発見、使われていないコード、境界ケース、文書群の中の矛盾です。探索役をひと回り送り、そのレコードを台帳に加え、新しいものを検証し、ラウンドを閉じます。規模が定める回数だけ枯れたラウンドが続いたら止めます。決まった回数で止まるループが裾野の途中で止まり、易しい発見だけを報告して残りを見逃すことを防ぎます。

## マルチモーダルな掃引

ひとつの探索の角度ではすべては見えず、何を見落とすかは角度次第なので、いくつも同時に走らせます。探索役はディレクトリ、シンボル、呼び出しグラフ、最近の変更、テストのカバレッジ、エラー文字列、描画結果で探します。このプラットフォームで最も大事なのは視覚の角度です。すべてのルートを取得画像付きで掃引すると、テキスト検索ではクエリにできない欠陥が見つかります。その欠陥は文字列ではなく描画の結果だからです。関数名で検索しても、それを呼ぶ動的ディスパッチが見つからない、というような単一の角度の死角を防ぎます。

## 審査団

解の空間が広いとき、最初のもっともらしい答えが最善であることはまれです。異なる出発点から独立した試みをいくつか作ります。動く最も単純なもの、リスク優先、性能優先、ユーザー優先です。どれも書いていない新しい審査役に採点させます。勝ったものを土台にし、他の案の最も強い考えを接ぎ木します。一度試してから磨く、つまり最初の枠組みに固定されてその中で反復することを防ぎます。

## 敵対的な反証

各発見を独立した反証役に送り、反証を試み、確信がなければ反証済みとするよう指示します。過半数が反証すれば落とします。フル規模では反証役を 3 人使います。「これを反証せよ」は吟味を促し、「これは正しいか」は同意を促します。もっともらしいが誤った発見が、文章の力で生き残ることを防ぎます。

## 観点の異なる検証

発見が複数の形で誤り得るときは、同じ反証役を送る代わりに、検証役ごとに異なる観点を与えます。正しさ、セキュリティ、性能、再現するかです。過半数を必要とします。同じ問いを投げる三つのエージェントは、ひとつの死角を共有し、それを合意と呼びます。

## 網羅性の批評

報告のたびに走らせます。`gravitas-completeness-critic` は台帳と作業リストを読み、何が欠けているかというひとつの問いに答えます。どの角度が探されず、どの主張が検証されず、どのファイルが開かれず、どの状態が試されず、どのルートが描画されず、どの子が失敗したか。挙げられたものが次のラウンドになります。自信に満ちた部分的な答え、つまり徹底して見える監査が間違う最もよくある形を防ぎます。

## 段階的な格上げ

ほとんどの項目が安く、一部だけが高いとき、どこでも高い代価を払えば予算の大半が無駄になります。すべてに `flash_lite` のパスを通し、シグナルに引っかかったものだけを格上げします。両方向の件数を記録します。格上げ率がゼロや一に近いなら、作業が一様なのではなく、シグナルの調整がずれているからです。

## アンチパターン

- 推測した作業リストに対してファンアウトすること。
- 下流で発見を比べる手順がないのに、すべての探索役を待ってから検証を始めること。
- 何かが正しいかを尋ねる、確認の枠組みの検証。
- これまでに見たすべてではなく、生き残ったものとだけ重複を照合すること。
- 黙った上限：報告に書かれていない抽出、上位 N 件、早期停止。
- 実行中のシステムを見に行けるのに、ソースから推論すること。
