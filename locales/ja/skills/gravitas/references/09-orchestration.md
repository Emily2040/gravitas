# モジュール 09 - オーケストレーション

## 目的

ファンアウトをどう組み立てるかをまとめたモジュールです。結果を待つべき場面と待たなくてよい場面、状況に合ったパターンの選び方、そして台帳（ledger）を使って件数と重複排除を正確に保つ方法を扱います。規模が standard 以上のときに読み込んでください。各パターンには、解決する問題、構成、防げる失敗を記載しています。パターン同士は自由に組み合わせて構いません。

どのパターンも特定の分野に依存しません。探索役（finder）は欠陥の種類を一つに絞り、作業リスト全体を探します。作業リストの中身はファイルでも、法令の条文でも、論文でも、帳簿の各行でも構いません。多角的スイープ（multi-modal sweep）は、複数の切り口から同時に探す手法です。コードベースならディレクトリ、コールグラフ、レンダリング結果から、文献レビューなら引用グラフ、キーワード、著者、再現に失敗した研究から探すことになります。

## パターンの選び方

| 状況 | パターン |
| :--- | :--- |
| 独立した確認手段がある | まずは観察から始める検証（`04-runtime-verification.md` を参照） |
| 問題が何件あるか見当がつかない | 指摘が出尽くすまでループ |
| 一つの切り口では見落としが出る | 多角的スイープ |
| 解空間が広い | 判定パネル |
| もっともらしいのに誤っている指摘があり得る | 敵対的反証 |
| 指摘の誤り方が何通りも考えられる | 多視点の検証 |
| 何かを見落としているかもしれない | 網羅性の批評役 |
| 項目ごとのコストの差が大きい | 段階的エスカレーション |
| 数百件の項目を正確な件数で扱う | スクリプトによるオーケストレーション（`13-platform.md` を参照） |
| テストがグリーンになるまで修正を詰める必要がある | 収束型ループ（`10-iteration.md` を参照） |
| 出力に必要なのは誤りの訂正ではなく磨き込み | 勾配型ループ（`10-iteration.md` を参照） |

## まず偵察し、ファンアウトはフェーズごとに 1 回

作業リストは、まず依頼が挙げた範囲の中で洗い出します。ファイルを一覧する、検索をかける、法令の索引を取り出す、目次を読む、といった作業です。ファイルの洗い出しには、使えるなら `list_dir`、`find_by_name`、`grep_search` を使います。agy CLI のメインエージェントには 1.2.7 以降これらがないので（`13-platform.md`）、フォルダの絶対パスを渡して `gravitas-scout` に任せます。シェルコマンドで一覧を取るのは代わりになりません。常時適用ルールは文脈探しのための一覧を禁じており、既定の設定のヘッドレス実行ではコマンドが拒否されて、そのターンの作業がすべて失われます。ファンアウトするのは、そうして見つかったものに対してです。複数フェーズにまたがる作業では、フェーズ（理解、設計、実装、レビュー）ごとに 1 回ずつファンアウトを順に実行し、親は各フェーズの結果を読んでから次を計画します。最初に巨大なファンアウトを 1 回だけ計画してしまうと、まだ何も分かっていない段階で書いた作業リストに縛られることになります。

## 基本はパイプライン

指摘は出た時点ですぐに検証します。早く返ってきた探索役の指摘は、遅い探索役がまだ動いている間に、もう反証役（refuter）の手元に届いているべきです。

全件がそろうのを待つのは、次のステップが全件を一度に必要とする場合に限ります。具体的には、コストの高い検証に入る前に全探索役の結果をまたいで重複排除する場合、合計がゼロなら早期に終了する場合、プロンプトで指摘同士を比較させるステップの場合です。フラット化、フィルタリング、整形には待ちは要りません。項目ごとに処理してください。探索役を 5 つ走らせ、最も遅いものが最も速いものの 3 倍かかる場合、本来不要な待ちのせいで、先に返った結果は実行時間の 3 分の 2 にわたって手つかずになります。

## 台帳

件数の数え上げ、重複排除、票の集計は帳簿付けであり、帳簿付けはコードに任せるべき仕事です。3 ラウンドにわたる 40 件の指摘を頭の中だけで追っていると、モデルは数を見失い、すでに却下した指摘を再検証し、ループを止めるタイミングも早すぎたり遅すぎたりします。`scripts/ledger.py` はこうした状態を JSON ファイルに保持し、判定を決定論的にします。必要なのは Python 3.8 以降だけで、ほかには何も要りません。

実行するときは、インストール済みプラグイン内のフルパス `<home>/.gemini/config/plugins/gravitas/skills/gravitas/scripts/ledger.py` を指定してください。台帳ファイルは、実行が終わっても残るようにワークスペースかアーティファクトのディレクトリに置きます。以下の例ではパスを短縮して書いています。

```bash
python scripts/ledger.py init  run.ledger.json --scale full
python scripts/ledger.py add   run.ledger.json finder-security.json --round 1 --by gravitas-finder
python scripts/ledger.py verdict run.ledger.json <key> --by gravitas-refuter --refuted no \
    --tier executed --source "pytest tests/test_session.py::test_logout -> 1 failed"
python scripts/ledger.py verdicts run.ledger.json refuter-verdicts.json --by gravitas-refuter
python scripts/ledger.py child run.ledger.json --id <conversation-id> --agent gravitas-finder --status denied \
    --note "read_file denied on src/auth"
python scripts/ledger.py close-round run.ledger.json --round 1
python scripts/ledger.py report run.ledger.json
```

台帳が強制するルールは次のとおりです。

- ティアが `observed`、`executed`、`read` のいずれかなのに `source` が空のレコードは、`inferred` に格下げされます。`read` のレコードで、source が内容を何も引用していないものも同様に格下げされます。引用として認められるのは 3 語以上、または 12 文字以上のもので、パスだけを引用しても、内容の引用とはみなされません。レコードは finding と verdict のスキーマで検証され、形式が不正なものは理由付きで却下されます。これにより、`01-evidence.md` の出所明記のルールは、台帳がすべてのレコードに対して実行するチェックになります。
- 新しいレコードは、反証役に却下されたものも含め、これまでに追加されたすべてのレコードと照合して重複排除します。生き残ったレコードとだけ照合すると、却下済みの指摘が毎ラウンド舞い戻ってきて、ループがいつまでも収束しません。
- 同じ位置にある 2 つのレコードは、主張に含まれる語の重なりが 0.25 以上なら自動でマージされ、0.10 以上なら重複の可能性ありとしてフラグが立ちます。同じファイル内で互いに 5 行以内にあるレコードは、文言がほぼ同一（0.8）の場合に限ってマージされ、それ以外はフラグが立つだけです。数行しか離れていない別々の欠陥は、似た書き方をされることが多いためです。ある実際の監査では、本当の重複のスコアは 0.13〜0.69、同じ行にある別々の欠陥は 0.02〜0.15 でした。自動マージでレコードは 22 件から 15 件になり、誤ったマージは 1 件もありませんでした。フラグが立ったものの扱いは `ledger.py merge KEEP DUP` で決めます。このとき票もあわせて移されます。
- 指摘が生き残るのは、カウント対象の票のうち、反証しなかった票が過半数を占める場合だけです。必要な票数は規模で決まり、standard では 1、full と exhaustive では 3 です。票にも、指摘と同じ出所明記のルールが適用されます。格下げされた票や、ステータスが `blocked` の票は、記録はされますがカウントには入りません。quick 規模では投票を行わないため、レポートでは指摘が未検証として列挙されます。
- `close-round` は新規の指摘を数えて空振りカウンターを進め、`CONTINUE` か `STOP` を理由付きで出力します。`STOP` の理由は、連続した空振りラウンドが規定回数に達したか、ラウンド数の上限に達したかのいずれかです。
- `report` は、まず生き残った指摘を重大度順にティアと source を添えて一覧にします。続いて反証済み、保留中、格下げされたレコード、その次にステータスが `done` 以外のすべての子エージェントと `blocked` を返したすべての探索役、最後に上限を出力します。

台帳ファイルは最終ターンが失われても残るので、ユーザーが見つけられる場所に置いてください。Python が使えない場合は、同じ項目を計画アーティファクト内の表で管理し、同じルールを手作業で適用したうえで、台帳を手動で管理したことをレポートに明記します。

## 指摘が出尽くすまでループ

問題が何件あるか分からないときに使います。バグ、セキュリティ上の指摘、デッドコード、エッジケース、文書群の中の矛盾などが該当します。探索役を 1 ラウンド分送り出し、返ってきたレコードを台帳に追加し、新規のものを検証してからラウンドを閉じます。新規の指摘が出ない空振りラウンドが、規模で定められた回数だけ連続したら終了します。回数を固定したループでは、ロングテールの途中で止まってしまい、見つけやすい指摘だけを報告して残りを取りこぼします。このパターンはそれを防ぎます。

## 多角的スイープ

一つの切り口ですべてを見通すことはできず、何を見落とすかは切り口によって変わります。だからこそ、複数の切り口を同時に走らせます。探索役ごとに、ディレクトリ、シンボル、コールグラフ、最近の変更頻度（チャーン）、テストカバレッジ、エラー文字列、レンダリング結果といった切り口で探させます。このプラットフォームで特に重要なのは視覚的な切り口です。すべてのルートを巡回してキャプチャを撮ると、テキスト検索ではクエリにしようのない欠陥が見つかります。その欠陥は文字列ではなく、レンダリングの結果として現れるものだからです。このパターンが防ぐのは、単一の切り口による死角です。たとえば関数名で検索しても、その関数を呼び出している動的ディスパッチは決して見つかりません。

## 判定パネル

解空間が広いときは、最初に出てきたもっともらしい答えが最善であることはめったにありません。「動くものの中で一番シンプルな案」「リスク優先」「パフォーマンス優先」「ユーザー優先」といった異なる出発点から、互いに独立した案をいくつか作ります。採点は、どの案の作成にも関わっていない、まっさらな判定役に任せます。勝った案をベースにし、他の案から最も優れたアイデアを取り込みます。一案だけ作ってそれを磨き続けるやり方では、最初の問題設定に固定されたまま、その枠内で反復するだけになります。このパターンはそれを防ぎます。

## 敵対的反証

指摘はそれぞれ、互いに独立した反証役に渡します。その際、反証を試みること、確信が持てないときは「反証済み」と判定することを指示します。過半数が反証したら、その指摘は棄却します。full 規模では反証役を 3 つ使います。「これを反証せよ」は精査を促し、「これは正しいか」は同意を誘います。もっともらしいだけで誤っている指摘が、文章の説得力だけで生き残るのを防ぎます。

## 多視点の検証

指摘の誤り方が何通りも考えられるときは、同じ反証役を並べるのではなく、検証役ごとに異なる観点を与えます。観点は、正確性、セキュリティ、パフォーマンス、再現するかどうかの 4 つです。指摘を残すには過半数の支持が必要です。同じ問いを投げる 3 つのエージェントは、同じ死角を共有しているだけなのに、それを合意と呼んでしまいます。

## 網羅性の批評役

レポートを出す前には毎回実行します。`gravitas-completeness-critic` は台帳と作業リストを読み、「何が欠けているか」という一つの問いに答えます。具体的には、一度も使っていない探索の切り口、検証していない主張、開いていないファイル、動かして確かめていない状態、レンダリングしていないルート、失敗した子エージェントを洗い出します。批評役が挙げたものが、次のラウンドの対象になります。自信満々なのに実は部分的でしかない答えを防ぎます。一見徹底した監査が結局間違っていた、というケースの原因として最も多いのがこれです。

## 段階的エスカレーション

ほとんどの項目は安く済み、高くつくのは一部だけという場合に、全項目へ高いコストを払うと予算の大半を無駄にします。まず `flash_lite` で全項目を一巡し、シグナルに引っかかったものだけを上位に昇格させます。全体と昇格分の両方の件数を記録してください。昇格率がゼロ付近や 1 付近なら、それは作業が均質だからではなく、シグナルの調整がずれていることを示しています。

## アンチパターン

- 推測で作った作業リストに対してファンアウトすること。
- 下流に指摘同士を比較するステップがないのに、全探索役の完了を待ってから検証を始めること。
- 「正しいかどうか」を尋ねる、確認ありきの検証。
- これまでに見たすべてではなく、生き残ったものだけと照合して重複排除すること。
- レポートに明記しない上限（サンプリング、上位 N 件への絞り込み、早期打ち切り）。
- 実際に動いているシステムを見て確かめられるのに、ソースコードから推論すること。
