# モジュール 11 - 発見事項の報告

## 目的

このモジュールは、他の人がそれをもとに行動する発見事項を扱います。バグ報告、監査結果、コードレビュー、インシデントの振り返り、研究の要約、そして誰かの名前で公開されるあらゆるものです。成果物が会話の外に出るときに読み込みます。規則は 2026 年 9 月に `google-antigravity/antigravity-cli` へ Antigravity のバグを報告した経験から来ており、どれも一度間違えてから学んだものです。

## 書き始める前に

1. トラッカー全体を、開いているものも閉じたものも含め、タイトルではなく症状とエラーテキストで重複検索します。Issue #1062 は新規として報告されましたが、2026 年 8 月 14 日から `--json-schema` についてのタイトルで開いていた #794 と同じ欠陥を説明していました。#1062 は重複として閉じられ、その証拠は #794 にコメントとして投稿し直されました。
2. 症状を共有する欠陥を分けます。`--json-schema` の報告（#1064）は最初ひとつのバグとして書かれていましたが、実際は二つでした。読めるファイルでも JSON オブジェクトでもない引数が黙って文字列のスキーマに置き換えられること、そしてルートがオブジェクトでないスキーマは `properties` と `required` が常に出力されるため必ず失敗することです。どちらも同じ API エラーとして現れます。仕組みごとにひとつの報告にするか、ひとつの報告で両方の仕組みを名指しし、それぞれの証拠を分けておきます。
3. 対照の組で仕組みを確定します。合格を失敗に変える最小の変更です。`nosuchfile.json` は正しい "failed to read schema file" エラーになり、`no such file.json` はなりませんでした。最初の草稿はそこで空白を原因としました。`not-json-at-all` には空白がないのに同じく置き換えられたので、空白は欠陥に入る道のひとつにすぎず、原因ではありませんでした。

## すべての数字は保存した実行から

1. ハーネスをファイルとして残し、報告のために再実行します。#1064 の最終的な表は、14 個の引数をそれぞれ 3 回、計 42 回実行したもので、どのケースも自分自身と食い違わず、スクリプトと生の結果は保存されています。
2. コストは述べる前に測ります。ある草稿は、失敗した呼び出しごとに「リクエストを一回消費する」と書いていました。失敗したすべてのケースで使用量は 0 トークンだったため、報告は課金されないと述べ、コストを本当の場所、つまり診断に置いています。
3. 投稿前に数え直します。影響を受けた会話の調査は、ある草稿では 23 件でしたが、投稿時には 32 件でした。内訳は `command` が 28、`read_file` が 2、`mcp` が 2 です。投稿したコメントには、一台のマシンの一日分だけを対象にしていることも書いてあります。
4. 保存したスクリプトから再実行できない結果は逸話です。含めるなら逸話と明記したときだけにします。

## システムを責める前の確認

1. 計測器を疑います。プラットフォームの障害に見えた実行は、ハーネスが途中で自分の権限付与を外していたせいでした。
2. 合格の理由を確かめます。仕込まれた指示にエージェントが抵抗したように見えた注入テストは、実は拒否された `read_file` で止まっており、ペイロードは読まれていませんでした。一般的な扱いは `05-acceptance.md` にあります。
3. 対照を事例と並べて、同じバージョン、同じセッションで再実行します。

## 報告を書く

1. トラッカーのテンプレートに正確に従います。バージョン、環境、番号付きの再現手順、期待される振る舞い、実際の振る舞い、ログです。
2. 手順はまっさらなマシンから再現できるようにし、必要なフィクスチャは手順の中で作ります。
3. 証拠は表にします。入力、終了コード、結果です。表のほうが段落よりも細部をよく運びます。
4. 原因の節は「解釈」と明記します。どの引数をリゾルバーがパスとみなすかなど、把握していないことを述べます。
5. 修正案は証拠が指し示すときだけ出し、番号を付けます。
6. 範囲を述べます。OS、シェル、バージョン、モデル、試していないことです。引数の空白についての欠陥なら、すべての実行が Windows の PowerShell だったという事実が主張の範囲を限定しており、メンテナーはそれを尋ねます。
7. 関連する issue へのリンクを張り、それぞれがどう違うかを書きます。
8. 短く書きます。バグを報告する本物のエンジニアは 400〜700 語で書きます。1,000 語の報告は、中身が何であれ生成されたものに読めます。

## 書き手は署名する人である

誰かの名前で出す発見事項は、その人の文体で書き、その人を書き手とします。アシスタントの口調（「下書きを作成しました」「ご依頼どおり」）は使わず、報告がどう作られたかも書かず、一人称は書き手本人が使う場面だけにします。たとえば "I searched the tracker for `only allowed for OBJECT type` and found nothing." です。

これらの報告の最初の草稿は、禁止語の検査で一件もヒットしなかったにもかかわらず、明らかに機械が書いたものに読めました。決め手は構造でした。1,000 語あたり 14〜21 個のダッシュ、ほぼすべての段落の対比の型、大半の箇条の太字の書き出し、そして同じテンプレートで作られた六つの報告です。`12-prose.md` の基準で書き直すと、一件あたり約 1,050 語から 390〜750 語に縮みました。

投稿の前に、草稿に `scripts/provenance_check.py` と `scripts/slopcheck.py` を実行し、同じトラッカーにある書き手自身の過去の報告を読み、見出し、綴り、数字の書き方の慣習に合わせます。

## チェックリスト

- 開いている issue と閉じた issue の両方を、症状とエラーテキストで重複検索した。
- 報告ひとつに仕組みひとつ、またはそれぞれの仕組みに固有の証拠がある。
- 対照の組をハーネスに保存した。
- すべての数字が、保存され再実行できる実行にたどれ、実行回数と繰り返し回数が書いてある。
- コストを測った。
- ハーネスを疑い、すべての合格に説明がある。
- 原因を解釈と明記し、把握していないことを書いた。
- 範囲を書いた。
- すべての証拠ラベルを `provenance_check.py` で確かめた。
- 書き手の文体で書き、`slopcheck.py` で測った。
