# モジュール 11 - 調査結果の報告（Findings）

## 目的

このモジュールが扱うのは、他の人が受け取って対応することになる調査結果です。バグ報告、監査結果、コードレビュー、インシデントレポート、調査のまとめ、そして個人の名前で公開されるものすべてが含まれます。成果物がこの会話の外に出ていくときに読み込んでください。ここにあるルールは、2026 年 9 月に `google-antigravity/antigravity-cli` へ Antigravity のバグを報告した経験から生まれたものです。どれも、一度失敗してから身についたものばかりです。

## 書き始める前に

1. 重複検索は、トラッカー全体を対象に、Open の Issue も Closed の Issue も含めて行います。検索の手がかりにするのはタイトルではなく、症状とエラーメッセージの文言です。#1062 は新規 Issue として起票されましたが、実は #794 と同じ不具合を扱っていました。#794 は `--json-schema` に関するタイトルで、2026 年 8 月 14 日から Open のままだったものです。結局 #1062 は duplicate としてクローズされ、そこにあった証拠は #794 へのコメントとして投稿し直されました。
2. 症状が共通する不具合は、別々に切り分けます。`--json-schema` の報告（#1064）は当初 1 件のバグとして書かれていましたが、実際には 2 件でした。一つは、読み取れるファイルでも JSON オブジェクトでもない引数が、何の警告もなく文字列のスキーマとして置き換えられてしまう問題。もう一つは、ルートがオブジェクトでないスキーマでも `properties` と `required` が無条件に出力されるため、必ず失敗する問題です。どちらも表面上は同じ API エラーとして現れます。報告はメカニズムごとに 1 件とするか、1 件にまとめるなら両方のメカニズムを明記し、それぞれの証拠を混ぜないようにします。
3. メカニズムは対照ペアで確定させます。対照ペアとは、パスするケースを失敗に変える最小の差分のことです。`nosuchfile.json` では正しく "failed to read schema file" エラーが出ましたが、`no such file.json` では出ませんでした。そこで最初の下書きでは、空白が原因だと書いてしまいました。ところが空白を含まない `not-json-at-all` も同じように置き換えられていました。つまり空白は、この不具合に至る経路の一つにすぎず、原因ではありませんでした。

## 数字はすべて保存済みの実行結果から

1. ハーネスはファイルとして残し、報告を書くときに再実行します。#1064 の最終的な表は、14 個の引数をそれぞれ 3 回、計 42 回実行した結果です。同じケースで結果が食い違ったものは一つもなく、スクリプトと生の結果も保存してあります。
2. コストについて書くなら、先に測ります。ある下書きには、失敗する呼び出しのたびに「リクエストを 1 回消費する（"spends a request"）」と書かれていました。しかし usage ブロックを見ると、失敗したケースはどれも 0 トークンでした。そのため報告では、トークンは課金されないと書いたうえで、本当のコストは診断のほうにあると明記しています。
3. 投稿前に数え直します。調査で見つかった影響ありの会話の数は、ある下書きでは 23 件と書かれていましたが、投稿時点では 32 件になっていました。内訳は `command` 関連が 28 件、`read_file` が 2 件、`mcp` が 2 件です。投稿したコメントには、対象が 1 台のマシンの 1 日分だけであることも書き添えています。
4. 保存したスクリプトから再実行できない結果は、逸話的な証拠（anecdote）です。載せるのは、そう明記した場合に限ります。

## システムのせいにする前に確認すること

1. まず計測する側が原因でないことを確かめます。プラットフォームの障害に見えた実行が、実はハーネスが途中で自分に付与した権限を取り消していたせいだった、ということがありました。
2. パスしたときは、なぜパスしたのかを確かめます。仕込んだ指示にエージェントが抵抗したように見えたインジェクションテストがありましたが、実際には `read_file` が拒否された時点で止まっていて、ペイロードは一度も読まれていませんでした。この問題の一般論は `05-acceptance.md` で扱っています。
3. 対照は、検証対象のケースと並べて、同じバージョン・同じセッションで再実行します。

## 報告の書き方

1. トラッカーのテンプレートにそのまま従います。項目は、バージョン、環境、番号付きの再現手順、期待される動作、実際の動作、ログです。
2. 手順は、クリーンなマシンで再現できるように書き、フィクスチャも手順の中で作成します。
3. 証拠は、入力・終了コード・結果を列にした表にまとめます。細かな情報は、段落で書くより表のほうが確実に伝わります。
4. 原因の節には、それが解釈（reading）であることを明記します。たとえば、リゾルバがどの引数をファイルパスとみなすのかなど、調べきれていない部分も書いておきます。
5. 修正案を出すのは、証拠がその方向を示している場合だけです。案には番号を振ります。
6. 検証範囲（OS、シェル、各バージョン、モデル、試していないこと）を明記します。引数の空白に関する不具合なら、すべて Windows 上の PowerShell で実行したという事実が主張の範囲を限定します。メンテナにも必ずそこを聞かれます。
7. 関連する Issue にはリンクを張り、それぞれとの違いを説明します。
8. 水増しは削ります。ただし、読み手に必要な手順、表、ログ、検証範囲の記述は、どれほど長くなってもすべて残します。最初の下書きが機械の書いた文章に見えた原因が構造にあったことは、次の節で説明します。

## 書き手は、署名する本人

誰かの名前で出す報告は、その人自身の文体で書きます。書き手はあくまでその人です。アシスタント的な言い回し（"I have drafted"＝「下書きしました」、"as requested"＝「ご依頼どおり」など）は使わず、報告をどう作成したかにも触れません。一人称は、書き手本人が使うような場面に限ります。たとえば "I searched the tracker for `only allowed for OBJECT type` and found nothing." といった使い方です。

これらの報告の最初の下書きは、一目で機械が書いたとわかる文章でした。禁止語スキャンでは 1 件も引っかからなかったにもかかわらず、です。機械らしさが表れていたのは構造でした。1,000 語あたり 14〜21 個の em ダッシュ、ほぼすべての段落に出てくる「〜ではなく〜」型の対比の構文、大半の箇条書きの冒頭に置かれた太字の見出し語、そして同じテンプレートで組み立てられた 6 件の報告。`12-prose.md` の基準に沿って書き直したところ、1 件あたり約 1,050 語だったものが 390〜750 語に収まりました。

投稿前には、下書きに対して `scripts/provenance_check.py` と `scripts/slopcheck.py` を実行します。あわせて、同じトラッカーにある書き手自身の過去の報告を読み、見出しの付け方、綴り、数値の書き方を書き手本人の流儀に合わせます。

## チェックリスト

- Open と Closed の両方の Issue を、症状とエラーメッセージの文言で重複検索した。
- 報告 1 件につきメカニズムは 1 つにした。または、各メカニズムを明記し、それぞれに固有の証拠を付けた。
- 対照ペアをハーネスに保存した。
- すべての数値が、保存済みで再実行可能な実行結果までたどれる。実行回数と繰り返し回数も明記した。
- コストを実測した。
- ハーネスが原因でないことを確認し、パスしたケースすべてについて理由を説明できる。
- 原因を解釈として明示し、調べきれていない部分も書いた。
- 検証範囲を明記した。
- すべての証拠ラベルを `provenance_check.py` で確認した。
- 書き手本人の文体で書き、`slopcheck.py` で測定した。
