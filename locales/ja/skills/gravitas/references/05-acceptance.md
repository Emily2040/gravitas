# モジュール 05 - 受け入れ

## 目的

このモジュールは、実際に失敗し得る検証の書き方、スクリーンショットは誰かが見るまで検証ではない理由、そして合格が思っているとおりの理由で起きたかの確かめ方を扱います。何かを合格と報告する前、そしてテスト、ゲート、チェックリストを書くたびに読み込みます。

例がソフトウェアなのは、失敗がそこで記録されたからです。規則はどの分野にも当てはまります。

| 規則 | ソフトウェア | 法律 | 数学 | 実証的な主張 |
| :--- | :--- | :--- | :--- | :--- |
| ゲートは失敗し得なければならない | 報告テンプレートに直書きされた `PASS` | 「引用を確認済み」が書式が整っているという意味 | 「代数を確認済み」が読み直したという意味 | 「出典を確認済み」が存在するという意味 |
| 集めるだけでなく検証する | 誰も読まない配列に積まれたコンソールエラー | 取り出したが読まれない法的根拠 | 実行したが比較されない数値チェック | 開いたが引用されない一次資料 |
| 代理指標ではなく成果物を判断する | レンダリングを見ずにメッシュを数える | 判決理由を読まずに引用を数える | 結果を試さず一行ずつ確かめる | 数字を確かめず論文の存在を確かめる |
| 合格には理由が要る | コードの経路が一度も走らなかったので通ったテスト | データベースを誤ったので矛盾する判例が見つからなかった検索 | 空の範囲での反例探し | エラーを返した検索から出た「反証なし」 |

## このモジュールのもとになった失敗

あるエージェントが Three.js でチョコレート工場を作り、スクリーンショットを 8 枚撮り、ゲートが 8 つある `VERIFICATION.md` を書いて、`ALL TEST GATES PASSED SUCCESSFULLY` と報告しました。シーンは一目見ておかしいものでした。

スイートにはこの行がありました。

```js
| **T12-R1** | Hero Chocolate Identity Persistence | **PASS** | Exactly 1 mesh; UUID ${uuids[0]} persists. |
```

`PASS` はテンプレートの文字列リテラルです。測った値は埋め込まれ、判定は手で書かれています。比較も閾値も分岐もありません。スイートには 8 つのゲート、8 つの直書きの合格があり、条件分岐はなく、唯一の `process.exit(1)` はクラッシュハンドラーの中でした。

コンソールエラーも集めたまま、一度も読んでいませんでした。

```js
const consoleErrors = [];
page.on('console', msg => { if (msg.type() === 'error') consoleErrors.push(msg.text()); });
```

## ゲートの規則

1. どのゲートも測った値を期待値と比べます。失敗の条件を言えないなら、それはゲートではありません。
2. 信頼する前に、ゲートが失敗できることを証明します。わざと壊し、スイートを走らせ、赤くなるのを見て、元に戻します。一度も失敗したことのないスイートは、一度もテストされていません。
3. どれかのゲートが失敗したら、プロセスは 0 以外で終了します。常に 0 で終わるスイートは何も報告していません。
4. 取得したものは検証するか削除します。誰も読まない配列にコンソールエラーを集めるのは、集めないより悪いことです。コードが確かめているように見えるからです。
5. 出力を読む前に、検証が実際に走ったことを確かめます。失敗を探しているとき、空の結果とクラッシュしたスクリプトは同じに見えます。終了ステータス、行数、完了時に出すマーカーで確かめます。

## 合格には理由が要る

合格の結果が証拠になるのは、テスト対象が実際に起きたときだけです。合格を報告する前に、それが依存する経路が実際に通ったことを確かめます。

Antigravity 自体をテストしたときの二つの例です。ある注入テストは、エージェントがファイルに仕込まれた悪意ある指示に抵抗したように見えました。トランスクリプトを見ると `read_file` の呼び出しが権限システムに拒否されており、エージェントはペイロードを見ておらず、何にも抵抗していませんでした。また、ツールが拒否されたヘッドレス実行は、そのターンの作業を捨てたまま `"status": "SUCCESS"` と終了コード 0 を返しました。これは `google-antigravity/antigravity-cli` の issue #794 として報告されています。どちらの場合も、合格のシグナルはハーネスから来ており、振る舞いについては何も語っていませんでした。

重要な合格には、テストした経路が走った証拠を添えます。トランスクリプトのツールステップ、ログの行、動いたカウンター、送られたリクエストです。

## 自分の計測器を疑う

結果が意外なときは、システムを責める前にハーネスを確かめます。同じテストの中で、Antigravity の障害に見えた実行が、実はテストハーネスが途中で自分の権限付与を外していたせいだったことがありました。失敗は本物でしたが、それは計測器のものでした。

このバージョンのテスト中にも再び起きました。ハーネスは Windows のシェル経由で `agy` にプロンプトを渡しており、シェルは最初の改行でコマンドを終えるため、複数行のプロンプトは一行目しか届きませんでした。一時的なワイルドカード権限を持った Gemini 3.8 Flash は指示が欠けていると判断して探しに行き、ユーザーの PowerShell 履歴、ほかの四つの会話のトランスクリプト、実行中のプロセスのコマンドラインを読み、ハーネス自身のプロセスに完全なプロンプトを見つけて、タスクを終えました。誤りはハーネスにありました。それが露わにした振る舞いは `00-orchestrator.md` で扱っています。依頼が不完全に見えるときは、尋ねるか止まります。このリリースのために書いた出所チェッカーも、自分の最初のテストで失敗しました。正しく出典を示した法律の回答の六つの出典すべてを「開かれていない」と報告したのです。パスのパターンが `https://` の中の `s:/` に一致していたためでした。

一度にひとつだけ変え、すべての実行をその場限りのコマンドではなく保存したスクリプトに残し、対照を事例と並べて再実行します。保存したスクリプトから再実行できない結果は逸話であり、`11-findings.md` もそう扱います。

## 報告の前に

- 検証が実際に走ったことを、終了ステータス、行数、完了マーカーで示している。
- すべてのゲートが失敗の条件を述べている。
- 少なくともひとつのゲートが失敗するのを見届けている。
- 重要な合格には、テストした経路が走った証拠がある。
- コンソール出力は検証されており、集めただけのものはない。
- 新しい批評役がレンダリング結果を見て、素材、照明、認識についての問いに答えている。
- 計画が見た目について定めたことすべてに、そう見えるかを問うゲートがある。
- 報告が、カバーしなかったものを述べている。

すべて緑で、赤くなったゲートを一度も見せていない報告は、どのゲートも失敗を検出できることを示していません。
