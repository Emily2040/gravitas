# モジュール 08 - 委任

## 目的

サブエージェントに仕事を任せるときの進め方をまとめたモジュールです。扱うのは、結果を検証できる形での指示の出し方、完了の待ち方、そしてサブエージェントの主張を報告に載せる前に、実際に何をしたのかを確かめる方法です。`07-subagents.md` とセットで読み込んでください。

## 指示書の要件

使い物にならない出力を生む指示書は、トークンを消費するうえに、やり直しの必要な結果しか残しません。どの `Prompt` にも、次の 6 点を必ず書きます。

1. 担当範囲：対象とするファイル、主張、ルート（routes）、情報源を、絶対パスまたは完全な URL で指定し、それ以外は含めません。範囲が重なれば結果が重複し、範囲と範囲の間に隙間があれば、誰も気づかない見落としが生まれます。
2. 問い：答えを検証できるところまで絞り込んだ、一つの問い。
3. 返却形式：同梱のエージェントなら、そのエージェント自身の指示に定められた JSON です。スキーマファイルの名前を挙げてはいけません。そのパスは子エージェントが場所を知らないスキルフォルダを基準にした相対パスなので、名前を渡された子エージェントはそのファイルを探しに行ってしまいます。`define_subagent` で作るエージェントには、`schemas/finding.schema.json` または `schemas/verdict.schema.json` のフィールドを一つの例のオブジェクトにまとめて `system_prompt` に書き写し、探すべきファイルはないと伝えます。何を探すかだけを伝えられたエージェントは、作文を書いて返してきます。
4. 証拠：どの主張にも、ティアと出典を同じフィールドに付けます。ティア 4 のものは仮説であると明記します。
5. 停止条件：担当範囲を網羅した時点、または指定した件数に達した時点で終了します。
6. ブロック時の動作：ツールが拒否されたり、ファイルが見つからなかったりした場合は、手元にあるものを、ステータス `blocked` とエラーの文面を添えて返します。拒否を回避しようとすることは禁止です。プラットフォーム自身が出す拒否メッセージにも、同じことが書かれています。

子エージェントは結果だけを返し、途中経過は報告しません。

サブエージェントに相対パスを渡してはいけません。2026-09-24 に agy 1.2.9 で確認したところ、`view_file` は相対パスをワークスペース基準ではなく、`~/.gemini/antigravity-cli/scratch/` 基準で解決しました。このフォルダは、CLI のすべての会話で共有されています。"in the current workspace" にある `draft.md` を編集するよう指示された `gravitas-prose-editor` は、5 日前のテストがこのフォルダに残していた別の `draft.md` を編集し、エラーも出さずにその結果を返しました。`gravitas-refuter` と `gravitas-visual-critic` も同じフォルダを見に行き、何も見つからずに `blocked` を返しています。失敗の仕方としては、こちらのほうがまだましです。

どの子エージェントにも、必要な情報はすべてプロンプトと指示の中にある、と伝えてください。監査のテストでは、出力を "the Gravitas finding schema" に合わせるよう指示された探索役（finder）が、127 ステップの大半を費やしてユーザーのフォルダからそのファイルを探し回り、途中で git の内部ファイルや無関係なテスト出力まで読んでいました。現在同梱しているエージェントには、スキーマ全体が例として書き込まれており、探すべきものは何もないとも伝えてあります。再実行では、探索役と反証役のすべてが 4〜8 ステップで完了し、担当範囲の外のものは一つも開きませんでした。

パストラバーサル、インジェクション、データ漏えいを実証するチェッカーは、一時フォルダに自分で作った無害なカナリアを標的にします。同じテストでは、チェッカーが欠陥のある関数を通して `C:\Windows\win.ini` を読み出し、トラバーサルを実証しました。この環境では無害で済みましたが、本物の機密情報があるマシンで同じことをするのは悪い癖です。

```text
Role: Refuter, session handling
Territory: the claim below and C:/work/app/src/auth/session.ts. Nothing else.
Claim: "logout() leaves the refresh token valid" (C:/work/app/src/auth/session.ts:88-120)
Question: can you show this claim is false?
Return: one JSON object with exactly the fields in your instructions.
Evidence: every statement carries its tier and source, e.g. read (C:/work/app/src/auth/session.ts:97, "...").
Stop: after one verdict.
If a tool is denied, return status "blocked" with the error text.
```

## 委任結果の確認

親エージェント自身のステータスを見ても、子エージェントの状態は何もわかりません。結果を統合する前に、子を一つずつ確認します。

1. すべての子を、会話 ID と最終ステータス（`done`、`failed`、`denied`、`empty`、`killed` のいずれか）とあわせて台帳に記録します。
2. `manage_subagents` を `list` で呼び出して実行中の子が残っていないことを確かめ、上限を超えたものは `kill` します。子が実行中のあいだは、タイマーをセットしてある場合（後述の「サブエージェントの完了を待つ」）を除き、ターンを終えてはいけません。タイマーがない状態で「批評役を待っています」のようなテキストを返してターンを終えると、実行全体が終了してしまうことがあり、その後に届いた結果は失われます。
3. 失敗した子、拒否された子、何も返さなかった子は、一つ残らず名前を挙げ、報告ファイルにカバレッジの欠落として記載します。
4. 子が返した主張のうち結論を支えるものについては、`logAbsoluteUri` にある子のトランスクリプトで、ラベルの裏付けとなるツールのステップを確認します。`scripts/provenance_check.py <child answer> --conversation <child id>` を使えば、すべてのラベルをまとめて確認できます。規則は `02-evidence-traps.md` の「委任先から返ってきた主張」の節にあります。
5. 各主張は、ティアと作成者を添えて報告ファイルに転記します（例：`read by gravitas-reader (...)`）。返答そのものでは、エージェント名を一切出しません（`00-orchestrator.md` の「出力のまとめ方」）。

こうした気づかれない失敗は、このプラットフォームで実際に起きています。2026-09-24、agy 1.2.9 でのヘッドレス実行では、サブエージェントの最初の `read_file` が拒否され、サブエージェントは何も出力しませんでした。それでも親は開始から 5.4 秒後に `"status": "SUCCESS"` で終了し、返答は "I am waiting for its response." でした。権限を与えた状態で同種の実行を行うと、親はサブエージェントを 63 秒待ち、その回答を報告しました。もう一つの早期終了には、拒否がまったく絡んでいません。フル監査が `manage_subagents` を 1 分間ポーリングしたあと、"Waiting for the Completeness Critic subagent to complete its evaluation" と書いてターンを終え、その 29 秒後に CLI が実行を終了させました。批評役の結果は届いたものの、そのときログに記録されたのは "Failed to wake idle agent on message: run state not found" でした。

## サブエージェントの完了を待つ

`schedule` は呼び出すとすぐに戻り、ターンを止めてはくれません。そのため「待つ」とは、タイマーをセットしたままターンを終えることを指します。このパターンは、2026 年 10 月 3 日に agy 1.2.16 で検証しました。条件は、`--sandbox --dangerously-skip-permissions` 付きのヘッドレス実行で、親が Gemini 3.8 Flash、サブエージェントが `Model: "pro"` です。既定のヘッドレス設定では検証していません。既定の設定では `run_command` と `read_url_content` が拒否されるため（`13-platform.md`）、そのどちらかを必要とする子は何も返さない可能性があり、その場合に動くのはタイマーのプロンプトです。常時適用ルールの「セカンドオピニオン」も、プラグインを `--review` 付きでインストールした場合にこのパターンを使います。

1. `invoke_subagent` を呼び出します。
2. `schedule` を呼び出します。`DurationSeconds` には許容できる最長の待ち時間を設定し、`TimerCondition: "any"` を指定したうえで、`Prompt` には何も届かなかった場合にどうするかを書きます。
3. 短い一行だけを書いてターンを終えます。ほかのテキストも、追加のツール呼び出しも付けません。ヘッドレス実行では、ツール呼び出しと並べて書いたテキストも出力されるからです。8 回中 1 回の実行では、これが原因で待機の一行が二度表示されました。かといって、agy 1.2.16 と Gemini 3.8 Flash の組み合わせでは、テキストもツール呼び出しもないターンは "model output must contain either output text or tool calls, these cannot both be empty" で拒否されました。ヘッドレス実行ではこの一行が返答より先に表示されるので、読む人に向けた文面にしてください。
4. 子の完了メッセージが届くと親が起こされ、タイマーは取り消されます。先にタイマーが発火した場合は、そのプロンプトに従って対応します。

子が `send_message` を呼ばずに終了した場合、親を起こすメッセージの送信者は子の会話 ID ではなく `system` になり、その中に子の最後の返答が入っています。そのため、子の ID をキーにしたタイマーは、このメッセージでは取り消されません。該当する実行では 7 回中 7 回とも 240 秒のタイマーが最後まで動き、親が二度目の返答をしました。うち 1 回は、メールを丸ごと繰り返していました。一方、子が自分で `send_message` を使って送ったメッセージには子の ID が付いており、その ID をキーにした待機中のタイマーを 3 回中 3 回取り消しました。また、4 回中 4 回とも、そのあとに `system` メッセージは届きませんでした。`"any"` を指定した場合は、8 回中 8 回とも、開始から 45〜167 秒後に一度だけ返答しています。一回限りのタイマーが待機している間、ヘッドレス実行は stderr に `root agent idle; waiting up to 30m0s for 1 background task(s)` と出力し、タイマーが発火するか取り消されるまで終了しません。タイマーを設定せずにターンを終えた親は、待つことなく実行そのものを終えてしまいました。返答は待機の一行だけで、子の結果は最後まで届きませんでした。子が複数いる場合は、メッセージが届くたびに `"any"` のタイマーが取り消され、しかもツール宣言上、このタイマーは同時に一つしか置けません。そのため、まだ実行中の子が残っているなら、もう一度ターンを終える前に新しいタイマーを設定します。この方法はツール宣言に沿ったもので、このスキルではまだ検証していません。

## 独立性

書き込める批評役は、自分が誤診した箇所をそのまま修正し、成功したと報告します。そして、その修正が証拠の一部になってしまいます。同梱エージェントのうち、観察や判断を担う役割に編集ツールを一つも持たせていないのはこのためです。

批評役に成果物を渡すときは、「あなたの前回の試み」としてではなく、第三者の出力として渡します。モデルは、他者が作ったと思っている成果物のほうが、誤りを大幅によく見つけます。ラベルを貼り替えるだけでも検出精度は上がります。検証を、その主張を出したエージェント自身に戻してはいけません。

カスタマイズは、エージェントファイルで無効にしない限りサブエージェントにも及びます。agy 1.2.9 では、`gravitas-reader` が 3 ステップで答えを見つけたあと、プラグインの常時適用ルールの指示どおりにこのスキルを読み込み、そこに 35 秒を費やしました。実行全体では 63 秒かかっています。エージェントファイルに `inheritCustomizations: false` を設定すると、同じタスクが 40 秒で終わり、スキルのファイルは一つも開かれませんでした。同梱のエージェントはすべてこの設定を入れており、親のルールや問題の捉え方（フレーミング）が批評役のコンテキストに入り込むことも防いでいます。また、サブエージェント用のツールを持つものは一つもありません。

## 書き込み役の並行実行

同じファイルを二つの書き込み役が扱うと、互いの変更を上書きしてしまいます。作業をファイル単位で分けるか、書き込み役を順番に実行するか、`Workspace: "branch"` または `Workspace: "share"` で、それぞれに隔離されたワークスペースを与えてください。隔離モードはツール宣言に記載されているものの、このスキルではまだ検証していません。どの方法をとる場合も、マージは親を通して行います。

## アンチパターン

- 編集ツールを持つ批評役、またはレビュー対象の作業を担当範囲に含むチェッカー。
- 主張を出したエージェント自身による検証。
- すべての専門役に `enable_subagent_tools` を付けること。階層が深く遅いツリーになり、誰にも監査できなくなります。
- 返却形式を指定していない指示書。
- 結論の根拠となる主張について、子の要約だけを読み、トランスクリプトを一度も確認しないこと。
- `manage_subagents` で確認すれば実行中の子が表示されたはずの状態で、実行完了と報告すること。
- `TimerCondition` に子の会話 ID を設定すること。`system` から届く完了メッセージでは、このタイマーは取り消されません。
