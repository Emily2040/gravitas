# モジュール 04 - 実行時検証

## 目的

このモジュールでは、実際に動作するもの、あるいは描画されて目に見える形になるもの全般の検証を扱います。アプリケーション、Web ページ、3D シーン、グラフ、生成画像、レイアウト済みの文書などが対象です。`03-domain-checks.md` で定めた一般原則、つまり「自分の推論を経由しないチェックを見つける」を、ひとつの分野に当てはめたものと考えてください。ソフトウェアの場合、そのチェックとは実際に動かして目で確かめることです。

## 最初にツールセットを確認する

検証の計画は、このセッションに実際にあるツールを前提に立てます。計画を書き始める前に、どのツールが使えるのかを確認してください。

| 環境 | ブラウザ系・ランタイム系のツール |
| :--- | :--- |
| agy CLI | なし。2026-09-24 に agy 1.2.9 で取得したツール一覧には `run_command`、`view_file`、`read_url_content`、`search_web`、`generate_image` とサブエージェント系のツールがありましたが、ブラウザ系のツールはありませんでした |
| Antigravity デスクトップアプリ | `open_browser_url`、`capture_browser_screenshot`、`capture_browser_console_logs`、`browser_list_network_requests`、`browser_get_network_request`、`execute_browser_javascript`、`browser_click_element`、`browser_input`、`browser_select_option`、`browser_resize_window`、`read_browser_page`、`browser_subagent`（ブラウザ連携が有効な場合） |
| どちらでも（プラグインがある場合） | Chrome DevTools プラグインが `mcp_` ツールとして提供するブラウザ操作（プラグインがインストール済みで、有効になっている場合） |
| どちらでも（常に使える） | Playwright または Puppeteer のハーネスをファイルに書き出し、`run_command` で実行する方法 |

デスクトップアプリで記録したある実行では、ブラウザ系のツールが一つもありませんでした。使えたのは `view_file`、`grep_search`、`list_dir`、`find_by_name`、`run_command`、`replace_file_content`、`write_to_file`、`schedule`、`manage_task` だけです。それでもエージェントは `run_command` 経由で Playwright のハーネスを組み、スクリーンショットを取得しました。この判断は正解でした。問題はハーネスそのものではなく、そのハーネスで何をチェックしたかにありました。その点は `06-perceptual-gates.md` で扱います。

## まずは観察から

描画結果や動作中の画面があるものについては、これが基本の進め方です。コードを読むレビューでわかるのは「コードが正しそうに見えるか」までです。本当に問うべきは「それが期待どおりに動くか」であり、こちらは直接見て確かめられます。

1. まず動く状態にします。`run_command` でサーバーを起動します。その環境で `restart_dev_server` が提供されていれば、それを使ってもかまいません（デスクトップアプリのバイナリには含まれていますが、記録したどのツール一覧にも出てきていません）。そのうえで、`open_browser_url` かハーネスから開きます。
2. 変更前のベースラインとして、スクリーンショットとコンソールログを取得します。
3. 変更を加えます。
4. 変更後にも、同じビューポートで同じものを取得します。
5. 変更前後のキャプチャを両方 `gravitas-visual-critic` に渡し、何が違うのか、その違いは意図したとおりなのかを説明させます。このエージェントはコードを見ておらず、何も編集できません。

`view_file` は画像を画像のままモデルに渡します。agy 1.2.9 では、批評役がテスト用 PNG の内容を正しく説明できました。実際には存在しない図形について尋ねたときも、「ない」と正しく答えています。実際に画像を見る批評役なら、コードレビューでは見えない種類の欠陥を拾えます。たとえば、要素同士の重なり、コンテナに収まらず切れてしまったテキスト、コントラスト不足の配色、画面外に描画された要素、幅 400 px で崩れるレイアウト、いつまでも終わらないスピナー、DOM 上には存在するのに人の目には見えないコントロールなどです。

コンソールは毎回必ず確認してください。正しく描画されたコンポーネントの中で起きているランタイム例外こそ、スクリーンショットだけのチェックが最も見落としやすい欠陥です。

## 契約（コントラクト）の検証

API 呼び出し、fetch、フォーム送信、その他のリクエスト全般については、クライアントとハンドラーのコードを読んで整合しているかを推論するのではなく、実際にその処理を動かし、ネットワーク上を流れた通信そのものを確認します。

- `browser_list_network_requests` では、どのリクエストが、どの順序で、何回送信されたかがわかります。
- `browser_get_network_request` では、メソッド、ヘッダー、ペイロード、ステータス、レスポンスボディを確認できます。
- ブラウザ系のツールがない場合は、ハーネスで同じ通信を記録できます。あるいは `run_command` から `curl` でエンドポイントを直接叩いても構いません。

こうすれば、コードを読むだけのレビューでは推測するしかなかった問題に決着がつきます。二重送信、一度も送信されないリクエスト、クライアントは送っているのにサーバー側で無視されているフィールド、ステータスは 200 なのにボディにエラーが入っているレスポンス、リトライストームといった問題です。

## 状態を実際に再現する

空状態、エラー状態、ローディング状態について、静的レビューは推論で判断しようとしますが、その判断はよく外れます。こうした経路は、開発中に実行される機会が最も少ないからです。推論に頼らず、実際にその状態まで持っていきます。

- `execute_browser_javascript` を使えば、状態を直接作り出せます。
- `browser_input`、`browser_click_element`、`browser_select_option` で、実際の操作フローをたどります。
- `browser_resize_window` を使い、メディアクエリを読むのではなく、ブレークポイントを実際に試します。

状態ごとにキャプチャを取り、視覚批評役に確認させます。

## ターゲットとの差分

モック、デザインファイル、参照実装といった見た目の仕様がある場合は、そのターゲットと実装のキャプチャを視覚批評役に渡し、余白、ウェイト（太さ）、配置の揃え、色、比率について、具体的な相違点を列挙させます。ターゲットがない場合は `generate_image` で作ることもできますが、その際は生成したものであることを明記します。こうすることで、テキストだけで判断するエージェントには答えられない「見た目は合っているか」という問いが、結果を一覧で示せる比較作業に置き換わります。

## 画像・文書・音声は証拠として扱う

Gemini は画像、PDF、Office ファイル、音声をそのまま読み込めます。そのため、ユーザーから渡されたものは「受け取りました」と流すだけの参考情報ではなく、証拠として扱ってください。バグのスクリーンショットは、それ自体がバグの再現です。デザインのモックは、差分を取るべき仕様です。ホワイトボードの写真は、アーキテクチャの設計書です。グラフはデータです。ユーザーがエラー画面のスクリーンショットを貼り付けたら、画像からエラー内容を読み取って対応してください。テキストで打ち直してもらうよう頼むと、せっかくの手がかりを捨てることになります。

タスクに視覚的な手がかりがある場合は、画像そのものを批評役に渡します。画像を直接見られるモデルに、わざわざ言葉で説明し直して渡しても、情報をむだに削ぎ落とすだけです。

## ブラウザ観察とコード実装を並行させる

作業が実装と動作の両方にまたがる場合は、実装を進める一方で、別のエージェントが動作中のアプリケーションを観察します。両者はラウンドごとに `send_message` で突き合わせを行います。観察役は「アプリケーションが実際にどう動いているか」という事実を押さえ、実装役は「どう動くべきか」に合わせてアプリケーションを変えていきます。

両者の役割ははっきり分けておきます。観察役がコードを編集し始めたり、実装役が描画結果を推測し始めたりした時点で独立性は失われ、役割を分けた意味がなくなります。

## 観察できない場合

主張の中には、実行して確かめようのないものもあります。アーキテクチャ上の判断、安全には発動させられない経路に関するセキュリティ上の推論、まだ動かないコードなどです。こうした主張はティア 3 とティア 4 にとどまります。テキストに対する敵対的レビューが適切な手段となるのは、この場合に限られます。

1. 主張を、互いに独立した複数の反証役に送ります。各反証役には「この主張を反証せよ。確信が持てないときは『反証された』と判定せよ」と指示します。
2. 主張の誤り方が複数考えられる場合は、検証役ごとに異なる観点を割り当てます。正しさ、セキュリティ、パフォーマンス、再現性といった観点です。
3. 主張を通すには、過半数の承認を必須とします。
4. 残った主張は、そのティアを明記したうえで仮説として報告します。

なお、観察できないと結論づける前に、手軽なハーネスで観察できるようにならないかを確認してください。使い捨てのスクリプト、テスト 1 本、クエリ 1 回で済むこともあります。それを作るほうが、コードがどう動くのかを 5 つのエージェントが推測で議論するより、ほとんどの場合安く済みます。しかも得られるのは多数決ではなく、実際の結果です。
