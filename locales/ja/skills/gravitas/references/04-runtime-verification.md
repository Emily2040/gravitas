# モジュール 04 - 実行時の検証

## 目的

このモジュールは、実行中またはレンダリングされた表面を持つもの全般の検証を扱います。アプリケーション、ウェブページ、3D シーン、グラフ、生成画像、組版された文書などです。これは `03-domain-checks.md` の一般則、つまり自分の推論を経由しない検証を見つけるという規則の、ひとつの分野での具体例です。ソフトウェアにとってその検証とは、実際に動かして見ることです。

## まずツールセットを確認する

このセッションに実在するツールを前提に検証を計画し、計画を書く前にそれらを確認します。

| 環境 | ブラウザと実行時のツール |
| :--- | :--- |
| agy CLI | なし。2026-09-24 に agy 1.2.9 で取得したツール一覧には `run_command`、`view_file`、`read_url_content`、`search_web`、`generate_image` とサブエージェント用ツールがあり、ブラウザツールはありませんでした |
| Antigravity デスクトップアプリ | ブラウザ連携が有効なとき、`open_browser_url`、`capture_browser_screenshot`、`capture_browser_console_logs`、`browser_list_network_requests`、`browser_get_network_request`、`execute_browser_javascript`、`browser_click_element`、`browser_input`、`browser_select_option`、`browser_resize_window`、`read_browser_page`、`browser_subagent` |
| どちらでも、プラグイン経由 | Chrome DevTools プラグインをインストールして有効にすると、ブラウザ操作が `mcp_` ツールとして提供されます |
| どちらでも、常に | ファイルに書き出して `run_command` で実行する Playwright または Puppeteer の検証ハーネス |

記録されたデスクトップアプリでの実行には、ブラウザツールがまったくありませんでした。ツールセットは `view_file`、`grep_search`、`list_dir`、`find_by_name`、`run_command`、`replace_file_content`、`write_to_file`、`schedule`、`manage_task` だけでした。エージェントはそれでも `run_command` で Playwright のハーネスを組み、スクリーンショットを撮りました。これは正しい判断でした。問題はハーネスではなく、それが何を確かめたかであり、その部分は `06-perceptual-gates.md` で扱います。

## まず観察する

レンダリングされた、または実行中の表面を持つものについては、これが既定の方法です。テキストのレビューは「コードが正しく見えるか」に答えます。重要なのは「それが正しいことをするか」であり、これは直接見に行けます。

1. 動かす：`restart_dev_server` のあと `open_browser_url`、または `run_command` でサーバーを起動してハーネスから開きます。
2. 変更前の基準を取得する：スクリーンショットとコンソールログ。
3. 変更を加える。
4. 変更後に、同じビューポートで同じ表面を取得する。
5. 両方の取得結果を `gravitas-visual-critic` に渡し、何が違うか、その違いが意図したものかを説明させます。このエージェントはコードを見ておらず、何も編集できません。

`view_file` は画像を画像としてモデルに渡します。agy 1.2.9 では、批評役がテスト用 PNG を正しく説明し、尋ねられたが存在しない図形についても「ない」と答えました。見る批評役は、コードレビューには見えない種類の欠陥を捕まえます。要素の重なり、コンテナに切り取られた文字、コントラスト不足の色、画面外に描画された要素、400 px で崩れるレイアウト、終わらないスピナー、DOM には存在するが人には見えないコントロールなどです。

毎回コンソールを読みます。正しく描画されたコンポーネントの中で起きた実行時例外は、スクリーンショットだけの検証が最も見逃しやすい欠陥です。

## 契約の検証

API 呼び出し、fetch、フォーム送信、リクエストについては、クライアントとハンドラーを読んで両者が一致するかを推論するのではなく、その経路を実際に通して通信内容を読みます。

- `browser_list_network_requests` は、何が、どの順番で、何回送られたかを示します。
- `browser_get_network_request` は、メソッド、ヘッダー、ペイロード、ステータス、レスポンス本文を示します。
- ブラウザツールがない場合は、ハーネスで同じ通信を記録するか、`run_command` から `curl` でエンドポイントを直接呼びます。

これで、テキストのレビューでは推測するしかないことが決着します。二重送信、送られないリクエスト、クライアントが送ってサーバーが無視するフィールド、エラー本文を運ぶ 200、再試行の嵐です。

## 状態を実際に動かす

静的レビューは空の状態、エラー状態、読み込み中の状態について推論しますが、しばしば間違えます。これらの経路は開発中にいちばん通られないからです。代わりに実際に動かします。

- `execute_browser_javascript` で状態を直接つくり出します。
- `browser_input`、`browser_click_element`、`browser_select_option` で実際の流れをたどります。
- `browser_resize_window` でメディアクエリを読む代わりにブレークポイントを試します。

各状態を取得し、視覚批評役に見せます。

## 目標との差分

モックアップ、デザインファイル、参照実装などの視覚的な仕様があるときは、目標と実装の取得画像を視覚批評役に渡し、余白、太さ、揃え、色、比率の具体的な違いを列挙させます。目標がない場合は `generate_image` で作り、生成物であると明記します。これで、テキストのエージェントには答えられない「見た目は正しいか」が、結果の一覧を伴う比較に変わります。

## 画像、文書、音声は証拠である

Gemini は画像、PDF、Office ファイル、音声をそのまま読めます。ユーザーが渡したものは、受け取ったと伝えるだけの文脈ではなく、証拠として扱います。バグのスクリーンショットは再現そのものです。デザインのモックアップは差分を取るための仕様です。ホワイトボードの写真はアーキテクチャ文書です。グラフはデータです。ユーザーがエラーのスクリーンショットを貼ったら、画像からエラーを読み取って対応します。打ち直しを頼めば、その手がかりを捨てることになります。

タスクに視覚的な手がかりがあるときは、画像そのものを批評役に渡します。画像を見られるモデルに言葉で画像を説明するのは、理由もなく情報を捨てることです。

## ブラウザとコードの並行作業

作業が実装と振る舞いの両方にまたがるときは、一方のエージェントが実行中のアプリケーションを観察し、その間に実装が進み、両者は各ラウンドで `send_message` を通じてすり合わせます。観察役はアプリケーションが実際に何をしているかという事実を握り、実装役はそれが何をすべきかを変えます。

役割は分けておきます。コードを編集し始めた観察役や、描画結果を推測し始めた実装役は、この分担に価値を与えていた独立性を失っています。

## 観察できないとき

実行時の表面を持たない主張もあります。アーキテクチャの判断、安全に発動できない経路についてのセキュリティ上の推論、まだ動かないコードなどです。これらは第 3 層と第 4 層にとどまり、ここでだけ、テキストへの敵対的レビューが適切な道具になります。

1. 主張を独立した反証役に送り、それぞれに反証を試み、確信がなければ反証済みとするよう指示します。
2. 主張が複数の形で間違い得るときは、検証役ごとに異なる観点を与えます。正しさ、セキュリティ、性能、再現性です。
3. 多数が通したときだけ成立とします。
4. 残った主張は、その層を添えて仮説として報告します。

主張を観察不能と受け入れる前に、安価なハーネスで観察可能にならないか確かめます。使い捨てのスクリプト、テストひとつ、クエリ一回です。それを作るほうが、コードがおそらく何をするかについて五つのエージェントが議論するよりほぼ必ず安く、票ではなく結果を生みます。
