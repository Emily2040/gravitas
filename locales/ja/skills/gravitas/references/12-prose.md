# モジュール 12 - 文章

## 目的

このスキルが人に向けて作るあらゆる成果物は、このモジュールを通します。報告書、要約、コミットメッセージ、ドキュメント、プルリクエストの説明、リリースノート、バグ報告、コメントです。正しい仕事でも機械が書いたように読めれば、誰かが評価する前に捨てられます。公開のトラッカーでは、書き手の信用も損なわれます。

## 語彙は決め手ではない

禁止語リストは肝心なものを何も捕まえません。`delve`、`leverage`、`robust` を一語も含まなくても、文章は紛れもなく生成されたものに読めます。特徴は構造にあるからです。読み手が気づくのは、次のような目印です。おおよそ目立つ順に並べています。

| 目印 | 現れ方 | 目標 |
| :--- | :--- | :--- |
| ダッシュの多用 | 二文に一度はダッシュ（英語の em-dash、日本語の「――」） | ゼロ。読点、句点、括弧を使う |
| 対比の型 | "Not X, it's Y"、日本語なら「〜ではなく〜だ」「これはバグではなく、ドキュメントの問題だ」 | 癖として使わない |
| 文の長さの均一さ | 似た長さの文ばかりが並ぶ | 標準偏差 6 超、本当に短い文もある |
| 太字の書き出し | すべての箇条が太字の語句とコロンで始まる | 本文の箇条ではゼロ |
| 強調のぼかし語 | `precisely`、`genuinely`、`deliberately`、`notably`、`arguably`、`effectively`、`worth noting`、日本語なら「注目すべきは」「本質的に」 | ゼロ |
| メタな注釈 | 「リファクタリングで失われないよう明記しておく」 | ゼロ |
| 同じ骨組み | 複数の文書が同じ見出しを同じ順で持つ | 文書ごとに内容で形を決める |
| 修辞疑問 | 問いを立ててすぐ自分で答える | 答えが欲しいときだけ問う |

## 二人目の書き手に見える構文

このスキルの初期の草稿を作者の公開リポジトリと比べたレビュアーは、情報ではなくリズムのために組まれた文を約 20 見つけました。それらは節の書き出しと締めくくりに集中していました。注意深い読み手が二人目の書き手に気づくのは、まさにそこです。どの文にも、それが代わりに立っていた事実をそのまま言う平易な書き換えがありました。以下の例は英語の原文で、日本語の同じ型にも当てはまります。

| 構文 | 例 | 平易な書き方 |
| :--- | :--- | :--- |
| リズムのための断片の連続 | "Thoroughly. It passes." | "It gets checked, it passes, and the work is reported as verified." |
| 二語の劇的な文 | "Gemini sees." | ツールができることを挙げる：スクリーンショット、コンソールの取得、ネットワークの調査 |
| 独立した格言 | "Repetition is not improvement." | "Repeating a pass does not reliably improve it." |
| 決め台詞としての対句 | "Word choice is not the tell. Structure is." | "The tell is structural rather than lexical." |
| 交差配列（キアスムス） | "Every claim carries a label, and the label carries its provenance." | "Every claim carries a tier label, and every label states what produced it." |
| 場所の倒置 | "Between that and a full pass lies most real work." | "Most real work sits between that gate and a full pass." |
| 首句反復 | "What changes is X. What does not change is Y." | Y を事実として述べる |
| 警句での締め | "...and is the opposite." | 帰結で終える |
| 三拍子の型 | 三つの段落がどれも "X fixes this." で終わる | 形を変えるか、表にする |

## 代わりにどうするか

各節は、それが何であるか、何をするかを述べて始め、詳細は表、箇条書き、コードブロックに任せ、さらに詳しいファイルやコマンドを指して締めます。

文の長さは意図して変えます。3〜8 語の短い平叙文と、25〜40 語の複文を並べます（日本語では文字数に置き換えて考えます）。短い文は事実を運びます。たとえば「まず `01-evidence.md` を読み込みます。」です。飾りを運ぶことはありません。

抽象的な言葉はすべて観察できる仕組みに結びつけます。「権限の仕組みが不安定だ」は何も言っていません。「許可はコマンドの文字列そのままで保存されるため、175 件たまって一件も再一致しなかった」は同じことを言い、しかも確かめられます。

すべての平叙文を反証可能にします。文の反対が不合理なら、その文は空です。「私たちはスケーラブルなソリューションを提供します」は不合格です。「ノードあたり毎秒 40,000 書き込み、99 パーセンタイルで 12 ms 未満、同一の NVMe ドライブが必要、マルチリージョン複製なし」は合格です。

測った数字は算用数字で書きます。22 件、301 KB、97.5%、20,595 出力トークン。ひとつの箇条書きの項目は同じ形にそろえます。意味を失わずに削れる語、文、節はすべて削り、ちょうどよいと思うより簡潔に書きます。

## 書き手は署名する人である

成果物が誰かの名前で公開、送信、提出されるなら、その人の文体で書き、その人を書き手とします。まずその人の既存の作品を読み、慣習に合わせます。見出しの大文字小文字、綴り（英式か米式か）、数字の書き方、一人称を使うか、節をどう始めて終えるか、リポジトリをどう構成しているかです。

アシスタントの存在をうかがわせるものは入れません。「下書きを作成しました」「ご依頼どおり」「こちらが一案です」、文章がどう作られたかの説明、書き手本人なら書かないぼかしです。

## 耳ではなく測定に頼る

構造上の癖は内側からは見えません。このスキルに同梱の `scripts/slopcheck.py` は、すべてのダッシュとその 1,000 語あたりの割合、文の長さの平均と標準偏差、短い文、太字の書き出し、対比の型、強調のぼかし語、締めくくりの決まり文句、修辞疑問、禁止語、閉じていないコードブロックを報告します。英語の文章向けに作られているため、日本語では比率と構文の目安として使います。

```bash
python scripts/slopcheck.py <files>            # --strict を付けると、警告が一つでもあれば 1 で終了
```

目標は、ダッシュゼロ、太字で始まる箇条ゼロ、標準偏差 6 超、8 語以下の文が実際にあること、対比やぼかしの警告がないことです。引用符、引用ブロック、コードの中の問いは飛ばされますが、警告はひとつずつ読んでから対処します。耳では通り、測定では落ちる草稿が普通です。

`slopcheck.py` は行と文を測るため、段落の形の繰り返しや上の表の構文は見えません。それは `gravitas-prose-editor` が読み、残りは書き手の作品を知る二人目の読み手が読みます。

## 当てはまらない場合

自明でない仕組みを説明するコードコメントは平易にし、短くてかまいません。ログメッセージは文章ではありません。コミットの件名はリポジトリの既存の慣習に従います。このモジュールに合わせるより、周りのコードに合わせるほうが優先です。
