# モジュール 12 - 文章

## このモジュールの目的

このスキルが人に向けて作る成果物は、どれもこのモジュールを通してから出します。対象は、レポート、要約、コミットメッセージ、ドキュメント、プルリクエストの説明文、リリースノート、バグ報告、コメントです。内容が正しくても、機械が書いたように見える文章は、中身を評価される前に捨てられます。公開のイシュートラッカーでは、著者の信用まで落とします。

## 手がかりは語彙にはない

禁止語リストを作っても、肝心なものは何ひとつ引っかかりません。`delve`、`leverage`、`robust` を一語も使っていなくても、ひと目で機械生成とわかる文章になることがあります。痕跡が残るのは構造のほうだからです。読み手が気づくのは次のような目印で、目立ちやすい順におおよそ並べています。

| 目印 | 具体的な現れ方 | 目標 |
| :--- | :--- | :--- |
| em ダッシュの多用 | 二文に一度は em ダッシュが入る | 0。読点、句点、括弧で書く |
| 対比の構文 | 「X ではなく Y だ」「これはバグではなく、ドキュメントの問題です」 | 癖としては使わない |
| 文の長さがそろいすぎる | どの文も同じくらいの長さ（英語なら 15〜20 語あたり）に集中している | 標準偏差が英語（語数）で 6 超、日本語（字数）で 14 超。短い文も実際に入れる |
| 太字の書き出し | 箇条書きの各項目が、太字の語句とコロンで始まる | 文章で書く箇条書きでは 0 |
| 強調語・ヘッジ表現 | `precisely`、`genuinely`、`deliberately`、`notably`、`arguably`、`effectively`、`worth noting` | 0（英語の文章） |
| メタコメント | 「リファクタリングで埋もれないよう、ここで明記しておきます」 | 0 |
| 判で押したような構成 | 複数の文書に、同じ見出しが同じ順番で並ぶ | 文書ごとに、内容に合わせて形を決める |
| 修辞疑問 | 問いを立てて、すぐ自分で答える | 答えを求めるときだけ問う |

上の表の目標は、従うべき慣習がほかにない文章のためのものです。既存の文章に書き加えるとき（著者が公開している文章、まとまった文書群、リポジトリのドキュメントや変更履歴など。この作業の中で先に書いた文章は含みません）は、その一部として読めるように書きます。ダッシュ、太字の書き出し、箇条書きの形、文のリズムは、上の目標と違っていても、その既存の文章が実際にしているとおりにします。項目が太字のパラメーター名で始まる API リファレンスなら、新しい項目も同じ形で書きます。ダッシュを使って書く著者なら、ダッシュは残します。そうした文章が目の前にないときは、上の目標のとおりに書きます。

## 別の書き手を感じさせる構文

このスキルの初期の草稿を著者が公開しているリポジトリと読み比べたレビュアーが、情報よりリズムを優先して組まれた文を約 20 文見つけました。こうした文は節の書き出しと締めくくりに集中していました。注意深い読み手が別の書き手の気配に気づくのも、この位置です。どの文にも、本来伝えるはずの事実をそのまま書いた平易な言い換えがありました。

| 構文 | 例 | 平易な書き方 |
| :--- | :--- | :--- |
| リズムのために細切れの文を並べる | "Thoroughly. It passes." | "It gets checked, it passes, and the work is reported as verified." |
| 芝居がかった二語だけの文 | "Gemini sees." | ツールにできること（スクリーンショット、コンソール出力の取得、ネットワーク通信の確認）を具体的に挙げる |
| 単独で置かれた格言 | "Repetition is not improvement." | "Repeating a pass does not reliably improve it." |
| オチに使う対比 | "Word choice is not the tell. Structure is." | "The tell is structural rather than lexical." |
| 交差配列（キアスムス） | "Every claim carries a label, and the label carries its provenance." | "Every claim carries a tier label, and every label states what produced it." |
| 場所句の倒置 | "Between that and a full pass lies most real work." | "Most real work sits between that gate and a full pass." |
| 首句反復（アナフォラ） | 「変わるのは X です。変わらないのは Y です。」 | Y を事実として書く |
| 警句で締める | "...and is the opposite." | 帰結を書いて終える |
| 三拍子の型 | 三つの段落が、どれも「X がこれを解決します。」で終わる | 形を変えるか、表にまとめる |

## 代わりにどう書くか

各節は、対象が何であるか、何をするかを述べるところから始めます。形は中身で選びます。いくつもの項目が同じ欄を持つなら表、順序に意味があるなら番号付きの箇条書き、読み手が実行したり写したりするコマンドやコードならコードブロック、それ以外はふつうの文章です。最後は事実か、その先の詳細がわかるファイルやコマンドで締めくくり、教訓めいた一文では終えません。

手順、作業手順書、技術報告は、常時適用ルールの項目 7 に従います。一文を短くし、一つの文には一つのことだけを書き、日本語なら「公用文作成の考え方」、英語なら ASD-STE100、ほかの言語ならその言語の平易な技術文の書き方に 8 割がた沿わせます。変化をつけるために文を長くしてはいけません。それ以外の文章では、文の長さを意図して変えます。英語なら、3〜8 語の短い平叙文の隣に、節をつないだ 25〜40 語の文を置きます。日本語なら、24 字以下の短い文の隣に、節をつないだ 70 字以上の文を置きます。短い文で書くのは、「まず `01-evidence.md` を読み込む。」のような事実です。飾りを短い文で書いてはいけません。

抽象的な主張は、必ず観察できる仕組みに結びつけて書きます。「権限システムが信頼できない」と書いても、何も言っていないのと同じです。「許可がコマンド文字列のまま保存されるため、175 件たまり、どれも一度も再マッチしなかった」と書けば、同じ内容を伝えたうえで、確かめることもできます。

平叙文は、どれも反証可能な形で書きます。その文の逆がばかげて聞こえるなら、その文には中身がありません。「当社はスケーラブルなソリューションを提供します」は不合格です。「1 ノードあたり毎秒 40,000 件の書き込み、99 パーセンタイルで 12 ms 未満、同一の NVMe ドライブが必須、マルチリージョンレプリケーションは非対応」は合格です。

測定した数値は算用数字で書きます。22 件、301 KB、97.5%、出力 20,595 トークンといった具合です。一つのリストの中では、すべての項目を同じ形にそろえます。意味を失わずに削れる語、文、節は残らず削ります。

## 著者は、署名する本人

成果物が誰かの名前で公開・送信・起票されるなら、その人の文体で書きます。著者はその人です。まず本人のこれまでの文章を読み、その慣習に合わせてください。確認するのは、見出しの大文字・小文字の使い方、綴り（英国式か米国式か）、数値の書式、句読点や記号の使い方（ダッシュを含む）、箇条書きの形、文のリズム、一人称を使うかどうか、節の始め方と終わり方、リポジトリの構成です。

アシスタントの存在をにおわせるものは入れません。「下書きを作成しました」「ご依頼のとおり」「こちらが一案です」といった言い回し、文章をどう作ったかの説明、著者なら張らない予防線がこれにあたります。

## 語感に頼らず、測る

構造に出るクセは、書いている側からは見えません。このスキルに同梱の `scripts/slopcheck.py` は、次の項目を報告します。em ダッシュの全出現箇所と 1,000 語あたりの頻度、文の長さの平均と標準偏差、短い文、太字の書き出し、対比の構文、強調語・ヘッジ表現、締めの常套句、修辞疑問、禁止語、閉じ忘れたコードフェンスです。

```bash
python scripts/slopcheck.py <files>            # --strict exits 1 when anything is flagged
```

目標は、em ダッシュ 0、太字で始まる箇条書き 0、文の長さの標準偏差が英語で 6 超・日本語で 14 超、短い文（英語 8 語以下、日本語 24 字以下）が実際に一定数あること、英語の文章では対比の構文とヘッジ表現の警告が出ないことです。対比の構文、ヘッジ表現、禁止語、締めの常套句の検出は英語の文章だけが対象で、日本語の文章には行われません。行わなかったことは、スクリプトが注記として表示します。引用符、引用ブロック、コードの中にある疑問文は検出対象から外れます。それでも、警告はひとつずつ中身を読んでから対処してください。em ダッシュは引用符の中でも数えられます。他人の言葉をそのまま引いた箇所で警告が出ても、引用は記録どおりに残してください。語感で問題がなくても測定で引っかかるのは、草稿では普通のことです。項目 7 に沿って書いた手順や作業手順書では、標準偏差が低く出るのが当然なので、その警告を消すために文を長くしてはいけません。既存の文章の慣習に合わせて書き加えた文章でも、その文章が使っているダッシュ、太字の書き出し、文のリズムに警告が出るのは当然です。慣習のほうを守ってください。

`slopcheck.py` が測るのは行と文なので、段落の形の繰り返しや、上の表にある構文は検出できません。そこは `gravitas-prose-editor` が読んで確認し、残りは著者の文章をよく知る別の読み手が確認します。

## 適用しない場面

自明でない仕組みを説明するコードコメントは平易に書きます。短くてもかまいません。ログメッセージは文章として扱いません。コミットの件名は、そのリポジトリの既存の慣習に従います。このモジュールより、周囲のコードに合わせることを優先してください。
