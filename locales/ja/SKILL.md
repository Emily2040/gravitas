# gravitas

質の低いエージェント出力のほとんどは、三つの失敗に集約される。

**もっともらしい不完全さ。** 問題の一部だけを見て、本物の何かを見つけ、そこで止まる。ファンアウトがこれを解決する。

**合意による幻覚。** 複数のエージェントが同じテキストを読み、そろって同じ誤った結論に達する。これを解決するのは証拠だけで、投票者を増やしても決して解決しない。

**機械的な文体。** 内容は正しいのに生成物のように読め、誰も信用しない。文章基準がこれを解決する。

本スキルはこの三つすべてを扱う。参照ファイルは必要に応じて読み込み、このページはコンテキストに保持しておくこと。

## 証拠の階層

すべての主張を、どうやって確立されたかで格付けする。報告する前に、できるだけ上へ押し上げること。

| 階層 | 根拠 | 例 |
|---|---|---|
| 1. **`observed`** 観測済み | 動いているものを実際に見た | スクリーンショット、コンソールログ、ネットワークのペイロード、描画後の DOM |
| 2. **`executed`** 実行済み | 実行し、その結果を確認した | テスト通過、終了コード 0、クエリが行を返した |
| 3. **`read`** 読んだ | ソースにそう書いてある | そのハンドラは入力を検証している |
| 4. **`inferred`** 推論 | エージェントがそう推論した | 「おそらく競合状態だろう」 |

**階層名はこの四つの英単語で固定である。翻訳も置換も造語も認めない：`observed`、`executed`、`read`、`inferred`。** 報告時はこの四語をそのまま使うこと。

第 4 階層の主張は仮説である。敵対的な投票は主張を第 4 階層の内部で動かすだけで、決して昇格させない。昇格には何かを実行することが必要で、このプラットフォームではほぼ常に何かを実行できる。

発見ごとに階層を併記すること。あわせて、カバーできなかった範囲も述べること。

## 視覚を使う

Gemini は見える。ほとんどのエージェント基盤は見えないため、オーケストレーションに関する助言の多くはこの点を無視している。その助言は、最も強力な検証シグナルをそのまま放置している。

描画または実行される画面がある作業では、既定でこれらを使うこと。

- `capture_browser_screenshot` は批評役に「見るもの」を与える。要素の重なり、切れたテキスト、コントラスト不足、画面外に描画された要素、狭い幅で崩れるレイアウト、終わらないスピナー、DOM には存在するのに人間には見えないコントロールを検出できる。コードを読むだけでは、どれ一つ見つからない。
- `capture_browser_console_logs` は「描画は正常に見えるコンポーネントの中で発生した実行時例外」を捕まえる。
- `browser_list_network_requests` と `browser_get_network_request` は、想定した契約ではなく実際のリクエストとレスポンスを検証する。
- `execute_browser_javascript` は空状態、エラー状態、ローディング状態を強制的に発生させ、推論ではなく実際に通す。
- `browser_resize_window` はブレークポイントを実際に検証する。
- `generate_image` は比較対象となる目標画像を合成し、「見た目が正しいか」という問いを検証可能な比較に変える。
- `browser_subagent` はコードエージェントと並行してブラウザを操作し、実際の挙動についての事実を保持する。
- `read_terminal` はコマンドが役目を果たしたと仮定せず、実際に何が起きたかを読む。

詳細な手法は [references/verification.md](./references/verification.md) を参照。

## サブエージェントは二段階

サブエージェントは**定義してからでなければ呼び出せない**。定義の省略が最も多い失敗であり、`invoke_subagent` は宣言されていない専門家を見つけられない。

1. `define_subagent` が専門家を一つ宣言する。`subagent_name`、明確な職務範囲、必要な道具だけの付与、そして仕事に応じて選ぶ `subagent_model`。
2. `invoke_subagent` が派遣する。`subagent_count` で作業リストに対して N 体を並行実行できる。
3. `send_message` がエージェント間の連絡を担う。子エージェントは自己完結した結果を返し、経過を語らない。

モデルは役割が実際に行う仕事で選ぶ。機械的な抽出と振り分けには `MODEL_TIER_FLASH_LITE`、探索役と読解役には `MODEL_TIER_FLASH`、判定役・反証役・視覚批評役・最終統合には `MODEL_TIER_PRO`、実装には `MODEL_TIER_INHERIT` を使い、利用者が選んだモデルに従わせる。

`enable_subagent_tools: true` は、その専門家が自分の職務をさらに細分する必要がある場合にのみ設定する。深い木構造は遅く、監査しにくい。

役割一覧と職務契約は [references/subagents.md](./references/subagents.md) を参照。

## 基本ループ

1. **範囲を決める。** サブエージェントを起動する前に、自分の道具で作業リストを作る。推測したリストでファンアウトしてはならない。
2. **ファンアウト。** 項目ごと、または観点ごとに専門家を一体、並行して走らせる。職務は結果を検証できる程度に狭くする。
3. **観測可能にする。** 実行時の画面がある作業なら、今すぐ `restart_dev_server` と `open_browser_url` で動かす。後続の検証はこれが存在することに依存する。
4. **経験的に検証する。** すべての主張を階層の上へ押し上げる。本当に観測できない主張に限って、敵対的なテキスト批評に戻る。
5. **批評。** 新しいエージェントが、欠けているものを指摘する。一度も探さなかった観点、一度も検証しなかった主張、一度も通らなかった状態。それが次の周回の作業になる。
6. **統合。** 統合し、重複を除き、深刻度で並べ、階層と欠落を報告する。

## 規律をもって反復する

繰り返しは自動的に改善にはならない。ループを始める前に、自分がどちらのループにいるかを決めること。

**収束ループ**は正しさを追う。各周回は新しい外部シグナルを必ず消費し、そのシグナルは**エラーの位置を特定できる**ものでなければならない。失敗したアサーション、スタックトレース、コンソール例外、スクリーンショットの差分、期待した契約と矛盾するネットワーク応答。モデルは位置を教えられれば直せるが、自分の出力の中からその位置を確実に見つけることはできない。新しいシグナルがなければ止める。

**勾配ループ**は品質を追う。文章、命名、API の使い心地、レイアウトなど、逸脱する唯一の正解が存在しない領域。**既定で 3 周、5 周を超えてはならない。** これは別々の二つの数字である。3 は既定で止まる地点、5 は越えてはならない上限。改善は最初の二周に集中し、およそ三周を超えると逆転しうる。

**決して反復しない**のは、得られるシグナルがなく反証もできない判断。独立した意見を一度取り、仮説として明記し、先へ進む。

閾値、根拠、出典は [references/iteration.md](./references/iteration.md) を参照。

## パターンの選択

| 状況 | パターン |
|---|---|
| 描画または実行される画面がある | 観測優先の検証 |
| 問題が何件あるか不明 | 枯れるまでループ |
| 単一の探索観点では取りこぼす | 多モーダル探索 |
| 解空間が広く開かれている | 判定パネル |
| 一つの発見が複数の形で誤りうる | 多視点検証 |
| 何かを見落とした疑いがある | 網羅性の批評役 |
| 項目ごとのコスト差が大きい | 段階的エスカレーション |
| 修正を全部グリーンまで持っていく必要がある | 収束ループ |
| 誤りの修正ではなく仕上げが必要 | 勾配ループ |

構造は [references/patterns.md](./references/patterns.md) を参照。

## 譲れない条件

- 先に作業リストを作る。推測は体系的で自信に満ちた盲点を生む。
- 検証役は独立、かつ読み取り専用であること。批評役に書き込み権限を与えなければ、誤診したものを自分で直してしまうことがない。
- 出所を付け替える。成果物は第三者の出力として批評役に渡し、「あなたの前回の試み」とは決して言わない。検出率が実測で向上する。
- 確認ではなく反証を求める。「これを反証してみよ、確信が持てなければ反証済みとせよ」は「これは正しいか」に勝る。
- 一致は証拠ではない。検証不能な推論に対する複数エージェントの一致は、相関した推論にすぎない。
- 第 4 階層の主張を事実として報告しない。
- すべての打ち切りを明示する。断りのないサンプリングや早期終了は、部分的な答えを「網羅した」という虚偽の主張に変える。
- 各周回が新しいものを出さなくなったら止める。費やした労力は停止条件ではない。

## 人間のように書く

正しくても生成物のように読めるものは、評価される前に捨てられる。本スキルが生み出すすべての成果物、不具合報告、要約、コミットメッセージ、ドキュメントは [references/prose.md](./references/prose.md) の文章基準に従う。

要約すると、文の長さを意図的に変え、すべての抽象を観測可能な仕組みか数値に接地させ、対比構文、修辞疑問、曖昧な強調語、ダッシュのリズムを削る。語彙は手がかりではない。構造が手がかりである。

日本語についての補足：`slopcheck.py` の対比構文、強調語、語彙ブラックリストの検査は英語向けであり、日本語では明示的に飛ばされる。文長とリズムの検査は日本語でも有効で、語数ではなく文字数で計測する。日本語における機械的な文体は別の形をとる。「〜することができます」の多用、全段落が同じ長さ、体言止めの連発、「いかがでしたでしょうか」の類の締め、そして助詞を省いた名詞の積み重ね。

## プラットフォームを知る

Antigravity には、無視すると作業が黙って無駄になる検証済みの制約がある。ワークスペースの `.agents/` ディレクトリに置いたスキルは決して読み込まれない。壊れた `SKILL.md` は読み飛ばされ、解析エラーは利用者が決して見ないローテーションログにしか書かれないため、そのスキルは単に存在せず、どこにも警告は出ない。詳細と回避策は [references/platform.md](./references/platform.md) を参照。

## 規模を合わせる

「ちょっと見て」ならエージェント二体と検証一周で足りる。「きちんと監査して」なら、広い探索役のプール、画面がある箇所すべてでの視覚と実行時の検証、本当に観測できない部分への三票から五票の敵対的反証、そして網羅性の批評役が必要になる。着手する前に規模を決めること。
