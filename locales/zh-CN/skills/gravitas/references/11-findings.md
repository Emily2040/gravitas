# 模块 11 - 发现报告

## 用途

本模块说明会被他人据以行动的发现：缺陷报告、审计结果、代码审查、事故复盘、研究摘要，以及任何以某人名义发布的内容。当交付物要离开对话时加载本模块。这些规则来自 2026 年 9 月在 `google-antigravity/antigravity-cli` 上提交 Antigravity 缺陷的经历，每一条都是先做错一次才学到的。

## 动笔之前

1. 在整个问题追踪器中搜索重复项，包括已打开和已关闭的，按症状和错误文本搜索，而不是按标题。Issue #1062 被当作新问题提交，结果它描述的缺陷与 #794 相同，而 #794 自 2026 年 8 月 14 日起就以一个关于 `--json-schema` 的标题开着。#1062 被作为重复关闭，其证据改以评论形式贴到了 #794 下。
2. 把症状相同的缺陷分开。`--json-schema` 的报告（#1064）起初描述的是一个缺陷，实际上是两个：一个既不是可读文件、也不是 JSON 对象的参数会被悄悄替换成字符串 schema；而根节点不是对象的 schema 总会失败，因为 `properties` 和 `required` 无论如何都会被输出。两者表现为同一个 API 错误。一个机制写一份报告，或者一份报告点名两个机制并把各自的证据分开。
3. 用对照组确立机制：能把通过变成失败的最小改动。`nosuchfile.json` 会得到正确的 “failed to read schema file” 错误，而 `no such file.json` 不会。初稿随后把空格说成了原因。`not-json-at-all` 不含空格，同样被替换了，所以空格只是进入这个缺陷的一条途径，而不是原因。

## 每个数字都来自保存的运行

1. 把检验装置保存为文件，并为报告重新运行。#1064 的最终表格来自 14 个参数、每个运行 3 次，共 42 次运行，没有任何用例与自身不一致，脚本和原始结果都被保留了。
2. 先测量成本，再陈述成本。一份草稿说每次失败的调用都“消耗一次请求”。可每个失败用例的用量块都显示 0 token，所以报告写的是不计费，并把成本放在它真正所在的地方：诊断上。
3. 发布前重新计数。一份受影响会话的统计在某份草稿中写的是 23，到发布时已是 32：28 个涉及 `command`，2 个 `read_file`，2 个 `mcp`。发布的评论也写明它只覆盖一台机器、一天之内的数据。
4. 无法从保存的脚本重跑的结果只是轶事。只有在标明它是轶事时才可以写进去。

## 在怪罪系统之前的核查

1. 排除仪器问题。一次看似平台故障的运行，其实是检验装置在中途撤销了自己的权限授权。
2. 确认通过的原因。一次看似显示代理抵御了植入指令的注入测试，实际上死在了一次被拒绝的 `read_file` 上，载荷根本没被读到。`05-acceptance.md` 对此有一般性说明。
3. 在同一版本、同一会话中，把对照组与测试用例一起重跑。

## 撰写报告

1. 严格遵循追踪器的模板：版本、环境、带编号的复现步骤、预期行为、实际行为、日志。
2. 让步骤在一台干净的机器上也能复现，所需的测试夹具在步骤中自行创建。
3. 把证据放进表格：输入、退出码、结果。表格比段落更能承载细节。
4. 把原因部分标注为“解读”。说明哪些没有摸清，例如解析器把哪些参数当作路径。
5. 只在证据指向某个修复时才提出修复建议，并给建议编号。
6. 写明范围：操作系统、shell、版本、模型，以及哪些没有测试。对于一个关于参数中空格的缺陷，每次运行都用的是 Windows 上的 PowerShell 这一事实限定了结论的范围，维护者一定会问。
7. 链接相关的 issue，并说明每一个的区别。
8. 写短。真正提交缺陷的工程师写 400 到 700 个词。一份 1,000 词的报告，无论内容如何，读起来都像是生成的。

## 作者是署名的那个人

以某人名义提交的发现，用这个人的口吻来写，作者就是这个人。不要有助手口吻（“我已起草”“如您所要求”），不要描述报告是如何产生的，只在作者本人会用第一人称的地方用第一人称：“I searched the tracker for `only allowed for OBJECT type` and found nothing.”

这些报告的初稿读起来明显是机器写的，尽管对它们做的禁用词扫描结果为零。破绽在结构上：每千词 14 到 21 个破折号，几乎每段都用对比式框架，大多数列表项以加粗引导开头，六份报告套用同一个模板。按照 `12-prose.md` 的标准重写后，它们从每份约 1,050 词缩减到 390 到 750 词之间。

发布前，对草稿运行 `scripts/provenance_check.py` 和 `scripts/slopcheck.py`，阅读作者本人在同一追踪器上较早的报告，并遵循其标题、拼写和数字格式的惯例。

## 检查清单

- 已按症状和错误文本搜索全部已打开和已关闭的 issue 以查重。
- 一份报告一个机制，或每个机制都有各自的证据。
- 检验装置中保存了一组对照。
- 每个数字都能追溯到一次保存的、可重跑的运行，并写明运行次数和重复次数。
- 成本经过测量。
- 已排除检验装置的问题，每个通过都有解释。
- 原因部分标注为解读，并写明哪些没有摸清。
- 写明了范围。
- 每个证据标签都经过 `provenance_check.py` 核查。
- 用作者的口吻撰写，并用 `slopcheck.py` 测量过。
