# 模块 12：文风

## 作用

本技能写给人看的每一份产出都要过这个模块：报告、摘要、commit message、文档、PR 描述、发布说明、bug 报告和评论。活儿做对了，读起来却像机器生成的，还没等人细看就会被扔掉；要是发在公开的 issue 追踪平台上，作者的信誉也会跟着受损。

## 破绽不在用词

禁用词表抓不到真正要紧的东西。一段文字里一个 `delve`、`leverage`、`robust` 都没有，照样一看就是生成的，因为特征藏在结构里。读者注意到的是下面这些特征，大致按扎眼程度从高到低排列。

| 特征 | 表现 | 目标 |
| :--- | :--- | :--- |
| 破折号节奏 | 每隔一句就来一个破折号 | 零。改用逗号、句号和括号 |
| 对比句式 | “不是 X，而是 Y”“这不是 bug，是文档问题” | 不能成为习惯 |
| 句长整齐划一 | 句子长度扎堆在 15 到 20 个词 | 标准差大于 6 个词（中文按字数算，大于 14 个字），并且真有短句 |
| 加粗开头 | 每个列表项都以加粗短语加冒号开头 | 行文里的列表，一项都不要这样开头 |
| 含糊或强调的修饰语 | `precisely`、`genuinely`、`deliberately`、`notably`、`arguably`、`effectively`、`worth noting` | 零 |
| 元评论 | “值得在这里明确写一句，免得重构时弄丢” | 零 |
| 结构千篇一律 | 几份文档用同样的标题、同样的顺序 | 每份文档的结构由它的内容决定 |
| 设问 | 抛出一个问题，紧接着自己回答 | 只有真想要答案时才提问 |

上表的目标，针对的是没有现成惯例可循的文字。如果这段文字要并入已有的作品（作者本人已发表的文字、一套文档、仓库里的文档或更新日志，但不包括本次任务里前面写的文字），它读起来就要像那份作品的一部分：那份作品在标点（含破折号）、加粗开头、列表形式和句子节奏上实际怎么做，就照着做，哪怕和上表的目标不一致。API 参考文档的条目如果都以加粗的参数名开头，新加的条目也用这个格式；作者本人写东西惯用破折号，破折号就留着。手头没有这样的作品可以参照时，按上表的目标来。

## 读着像换了个人写的句式

有位审阅者把本技能的早期草稿和作者已公开的仓库放在一起对比，挑出了大约 20 个只为凑节奏、而非为传递信息而写的句子。这些句子集中在各节的开头和结尾，细心的读者也就是在这些位置察觉到换了个人在写。每一句都能换成一句平实的话，把它本该交代的事实直接说出来。

| 句式 | 例子 | 平实写法 |
| :--- | :--- | :--- |
| 为节奏连用碎句 | “查得很彻底。通过了。” | “检查过了，也通过了，这项工作就报为已验证。” |
| 两个词的戏剧化短句 | “Gemini 看得见。” | 直接写出工具能做什么：截图、抓取控制台输出、检查网络请求 |
| 独立成句的格言 | “重复不等于改进。” | “重跑一轮，不能保证结果变好。” |
| 拿对比句抖包袱 | “破绽不在用词。在结构。” | “破绽出在结构上，不在用词上。” |
| 回环 | “每条结论都带一个标签，标签又带着它的来历。” | “每条结论都带层级标签，每个标签都写明它是由什么得出的。” |
| 方位倒装 | “在它和完整一轮之间，横亘着大部分真正的工作。” | “大部分实际工作落在那道关卡和完整一轮之间。” |
| 句首反复 | “变的是 X。不变的是 Y。” | 直接把 Y 当事实陈述 |
| 警句式收尾 | “……其实恰恰相反。” | 结尾落在后果上 |
| 三段式模板 | 连续三段都以“X 解决了这个问题。”结尾 | 换个结构，或者改用表格 |

## 该怎么写

每一节开头先说清楚这个东西是什么、做什么。用什么形式，看内容：几项内容字段相同，用表格；有先后顺序，用编号列表；读者要运行或复制的命令和代码，放进代码块；其余都写成段落。结尾落在一个事实上，或者指向能深入了解的文件或命令，绝不以说教收尾。

操作步骤、流程和技术报告按常驻规则第 7 条来写：句子短，一句只讲一件事，大体按所用语言的简明技术写法做到八成（中文按阮一峰的规范，英文按 ASD-STE100）。这类文字绝不为了长短错落去拉长句子。其他文字，句子长短要有意拉开。写英文，就让 3 到 8 个词的短陈述句和 25 到 40 个词的复合句挨着用。写中文就按字数算：穿插一些 24 个字以内的短句，空格和标点也算字数；长句也只讲一件事。短句用来交代事实，比如“先加载 `01-evidence.md`”，不要拿来卖弄文采。

每个抽象说法都要落到能观察到的机制上。“权限系统不可靠”等于什么都没说。“授权按命令原文逐字保存，所以攒下了 175 条，没有一条再被匹配上过”，说的是同一件事，而且能核实。

每个陈述句都要可证伪。一句话如果反过来说显得荒唐，那这句话就是空的。“我们提供可扩展的解决方案”不合格。“单节点每秒写入 40,000 次，P99 低于 12 ms，必须用同型号的 NVMe 盘，不支持多区域复制”合格。

测出来的数字一律写成阿拉伯数字：22 个用例、301 KB、97.5%、20,595 个输出 token。同一个列表里，每一项都用同一种写法。凡是删了不丢意思的词、句、节，统统删掉。

## 谁署名，谁就是作者

产出要是以某个人的名义发布、发送或提交，就要用这个人的口吻来写，作者就是署名人本人。先读署名人已有的作品，照着其中的惯例来：标题大小写、拼写（英式还是美式）、数字格式、标点（含破折号）、列表形式、句子节奏、用不用第一人称、各节怎么开头和收尾，以及仓库怎么组织。

凡是会暴露助手身份的内容都去掉：“我已经起草好了”“按您的要求”“这里给出一个版本”这类话，交代这段文字是怎么写出来的说明，以及作者自己不会写的含糊措辞。

## 要测量，别信语感

结构上的破绽，写的人自己是看不出来的。本技能自带 `scripts/slopcheck.py`，它会报告每一个破折号及其每 1,000 词的出现率、句长均值和标准差、短句、加粗开头、对比句式、含糊或强调的修饰语、收尾套话、设问句、禁用词，还有任何没闭合的代码块。其中对比句式、含糊或强调的修饰语、收尾套话和禁用词这四项只查英文；碰到中文文本，脚本会跳过这几项，只在报告里注明已跳过。

```bash
python scripts/slopcheck.py <files>            # 加 --strict 时，只要报出任何问题就以退出码 1 退出
```

目标：破折号为零，加粗开头的列表项为零；句长标准差英文大于 6 个词，中文大于 14 个字；短句确实有一定数量（英文 8 个词及以下，中文 24 个字及以下）；英文文本里，对比句式和含糊或强调的修饰语一条都不报。引号、引用块和代码里的问句会被跳过，但每条报出来的问题都要先看清楚再处理。引号里的破折号照样计数，所以报出的破折号如果落在逐字引用的别人原话里，引文保持原样。语感上过得去、一测却不过关，这种稿子是常态。按常驻规则第 7 条写的步骤和流程，句长标准差偏低是正常的，不要为了消掉这条提示去拉长句子。文字照着它要并入的那份作品的惯例来写时，脚本报出那份作品本来就用的破折号、加粗开头或句子节奏，也是正常的；这些惯例照旧保留。

`slopcheck.py` 按行和句子统计，所以看不出反复出现的段落结构，也看不出前面那张句式表里的写法。这些由 `gravitas-prose-editor` 去查，其余的再交给另一位熟悉作者作品的读者去看。

## 哪些情况不适用

解释不直观机制的代码注释要写得平实，短一点也没关系。日志信息不是文章。commit 的标题行沿用仓库现有的约定。和周围代码保持一致，比遵守本模块更要紧。
