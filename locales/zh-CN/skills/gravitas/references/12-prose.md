# 模块 12 - 文风

## 用途

本技能为人产出的每一份文本都要经过本模块：报告、摘要、提交信息、文档、拉取请求描述、发布说明、缺陷报告和评论。正确的工作如果读起来像机器生成的，会在有人评估之前就被丢弃；在公开的问题追踪器上，它还会损害作者的信誉。

## 用词并不是破绽所在

禁用词表抓不到任何要紧的东西。一段文字可以没有 `delve`、`leverage` 或 `robust`，读起来却依然明显是生成的，因为特征在结构里。下面这些标记，大致按暴露程度从高到低排列，才是读者会注意到的。

| 标记 | 表现 | 目标 |
| :--- | :--- | :--- |
| 破折号节奏 | 每隔一句就有一个破折号（英文 em-dash，中文“——”） | 零。用逗号、句号和括号 |
| 对比式框架 | “Not X, it's Y”；中文里的“不是……而是……”“这不是缺陷，而是文档问题” | 不作为习惯 |
| 句长均一 | 句子集中在相近的长度 | 标准差高于 6，并且确实有短句 |
| 加粗引导 | 每个列表项都以加粗短语加冒号开头 | 正文列表中为零 |
| 强调性修饰 | `precisely`、`genuinely`、`deliberately`、`notably`、`arguably`、`effectively`、`worth noting`；中文里的“值得注意的是”“真正地”“本质上” | 零 |
| 元评论 | “在此明确说明，以免在重构中丢失” | 零 |
| 结构雷同 | 几份文档使用同样顺序的同样标题 | 每份文档按内容组织 |
| 反问句 | 作者提出问题后立刻自答 | 只在真的需要答案时提问 |

## 读起来像出自另一位作者的句式

一位审阅者把本技能的早期草稿与作者已发布的仓库对照，发现约 20 个句子是为了节奏而不是为了信息而写的。它们集中在各节的开头和结尾，而那正是细心的读者察觉到“第二位作者”的地方。每一句都有一个平实的替代写法，直接说出它所代替的事实。以下示例为英文原句，中文里的对应句式同样适用。

| 句式 | 示例 | 平实写法 |
| :--- | :--- | :--- |
| 为节奏而连用碎句 | "Thoroughly. It passes." | "It gets checked, it passes, and the work is reported as verified." |
| 两个词的戏剧化短句 | "Gemini sees." | 说出工具能做什么：截图、控制台采集、网络检查 |
| 独立成段的格言 | "Repetition is not improvement." | "Repeating a pass does not reliably improve it." |
| 以对偶作结的妙语 | "Word choice is not the tell. Structure is." | "The tell is structural rather than lexical." |
| 回环句 | "Every claim carries a label, and the label carries its provenance." | "Every claim carries a tier label, and every label states what produced it." |
| 方位倒装 | "Between that and a full pass lies most real work." | "Most real work sits between that gate and a full pass." |
| 排比 | "What changes is X. What does not change is Y." | 直接把 Y 作为事实陈述 |
| 以警句收尾 | "...and is the opposite." | 以后果收尾 |
| 三段式模板 | 三段各以 "X fixes this." 结尾 | 变换形式，或改用表格 |

## 应该怎么写

每一节开头先说明这个东西是什么或做什么，然后把细节交给表格、列表或代码块，最后指向能进一步说明的文件或命令。

有意识地变化句长：3 到 8 个词的短陈述句，与 25 到 40 个词的复合句相间（中文可按字数类推）。短句承载事实，例如“先加载 `01-evidence.md`。”，从不用来装饰。

每个抽象概念都要落到可观察的机制上。“权限系统不可靠”什么也没说。“授权以命令原文保存，因此积累了 175 条，却没有一条再被匹配上”说的是同一件事，而且可以核查。

让每个陈述句都可证伪。如果一句话的反面荒谬到不可能成立，这句话就是空的。“我们提供可扩展的解决方案”不合格。“每节点每秒 40,000 次写入，99 分位低于 12 ms，要求相同的 NVMe 硬盘，不支持多区域复制”合格。

测量得到的数字用阿拉伯数字书写：22 个案例、301 KB、97.5%、20,595 个输出 token。一个列表里的所有条目保持同一种形式。任何去掉后不损失含义的词、句或段都删掉，写得比你觉得合适的还要简练。

## 作者是署名的那个人

当产出将以某人的名义发布、发送或提交时，它要用这个人的口吻来写，作者就是这个人。先读他们已有的作品，并遵循其惯例：标题大小写、拼写（英式或美式）、数字格式、是否使用第一人称、各节如何开头和结尾、仓库如何组织。

去掉任何暴露助手身份的内容：“我已起草”“如您所要求”“这是一个版本”，对文本产生过程的描述，以及作者本人不会写的含糊措辞。

## 靠测量，不靠语感

结构上的破绽从内部是看不见的。本技能附带的 `scripts/slopcheck.py` 会报告每千词的破折号密度、句长均值与标准差、短句数量、加粗引导、对比式句型、强调性修饰、反问句以及禁用词。它按英文文本设计，用于中文时以其中的比例和句式为参考。

```bash
python scripts/slopcheck.py <files>
```

目标：零破折号，零加粗引导的列表项，标准差高于 6，确实存在 8 个词以内的短句，没有对比式或强调性修饰的标记。被引用的提示语和示例问题可能触发反问句检查；处理每条标记前先读一读它。凭语感通过、却未通过测量的草稿，才是常态。

`slopcheck.py` 按行和句子测量，所以看不到重复的段落形状，也看不到上表中的句式。`gravitas-prose-editor` 会专门读这些，其余的则交给一位熟悉作者作品的第二读者。

## 不适用的情形

解释非显而易见机制的代码注释应当平实，可以很短。日志信息不是文章。提交信息的标题行遵循仓库已有的惯例。与周围代码保持一致，比与本模块保持一致更重要。
