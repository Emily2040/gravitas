# 模块 04：运行时验证

## 本模块讲什么

凡是能跑起来、或能渲染出画面的东西，都归本模块管：应用、网页、3D 场景、图表、生成的图片，以及排好版的文档。`03-domain-checks.md` 里有一条通用规则：找一种不靠你自己推理的核查方式。本模块就是这条规则在一个具体领域里的落地。对软件来说，这种核查就是把东西跑起来，亲眼去看。

## 先确认手头有哪些工具

验证计划要围绕本次会话里实际有的工具来定。写计划之前，先确认这些工具确实存在。

| 运行环境 | 浏览器与运行时工具 |
| :--- | :--- |
| agy CLI | 没有。2026-09-24 在 agy 1.2.9 上抓取的工具列表里有 `run_command`、`view_file`、`read_url_content`、`search_web`、`generate_image` 和 subagent 相关工具，没有任何浏览器工具 |
| Antigravity 桌面应用 | 开启浏览器集成后提供：`open_browser_url`、`capture_browser_screenshot`、`capture_browser_console_logs`、`browser_list_network_requests`、`browser_get_network_request`、`execute_browser_javascript`、`browser_click_element`、`browser_input`、`browser_select_option`、`browser_resize_window`、`read_browser_page`、`browser_subagent` |
| 两种环境均可，需装插件 | 安装并启用 Chrome DevTools 插件后，浏览器控制能力以 `mcp_` 工具的形式提供 |
| 两种环境均可，始终可用 | 自己写一个 Playwright 或 Puppeteer 验证脚本（harness），存成文件，再通过 `run_command` 运行 |

有一次桌面应用的运行记录里压根没有浏览器工具，全部工具只有 `view_file`、`grep_search`、`list_dir`、`find_by_name`、`run_command`、`replace_file_content`、`write_to_file`、`schedule` 和 `manage_task` 这几个。agent 照样通过 `run_command` 搭了一个 Playwright 验证脚本并截了图，这么做是对的。问题从来不在脚本本身，而在它检查了什么，这部分见 `06-perceptual-gates.md`。

## 先观察

只要东西能渲染或能运行，默认就先观察。读代码做审查，回答的是“代码看上去对不对”；真正要紧的是“它实际做得对不对”，而这一点可以直接看到。

1. 先让它跑起来：用 `run_command` 启动服务；所在环境提供 `restart_dev_server` 的话也可以用它（桌面版二进制里有这个工具，但目前记录到的工具列表里都没出现过）。然后用 `open_browser_url` 打开，或者在验证脚本里打开。
2. 改动之前先采集基线：一张截图，加上控制台日志。
3. 做改动。
4. 改动之后，在相同的视口下把同样的内容再采集一遍。
5. 把前后两份采集结果交给 `gravitas-visual-critic`。它没看过代码，也改不了任何东西。让它说明两者有哪些差异，以及这些差异是不是这次改动想要的效果。

`view_file` 交给模型的就是图片本身：在 agy 1.2.9 上，评审者正确描述了一张测试用的 PNG；提问里问到、图中其实并不存在的那个形状，它也如实指出没有。真正去“看”的评审者，能抓到代码审查看不见的一类缺陷：元素互相重叠、文字被容器截断、颜色对比度不达标、元素渲染到了屏幕外、布局在 400 px 宽时塌掉、加载圈一直转个不停，还有 DOM 里明明存在、人却看不见的控件。

每次都要看控制台。组件渲染得好好的，内部却抛了运行时异常，只看截图的检查最常漏掉的就是这种缺陷。

## 接口契约验证

凡是 API 调用、fetch、表单提交或其他任何请求，都要把这条路径实际跑一遍，直接看网络上真正收发了什么。不要分别去读客户端代码和服务端 handler，再靠推理判断两边是否对得上。

- `browser_list_network_requests`：看发出了哪些请求、按什么顺序、每个发了几次。
- `browser_get_network_request`：看请求方法、请求头、请求体、状态码和响应体。
- 没有浏览器工具时，可以让验证脚本录下同样的流量，或者用 `run_command` 直接 `curl` 这个接口。

这样一来，那些光读代码只能靠猜的问题就有了定论：重复提交、根本没发出去的请求、客户端发了但服务端忽略的字段、状态码是 200 而响应体却是错误信息、重试风暴。

## 把各种状态实际触发出来

空状态、错误状态、加载中状态，静态审查只能靠推理，而且经常推错，因为开发过程中这几条路径走得最少。所以要实际把它们触发出来。

- `execute_browser_javascript`：直接强制进入某个状态。
- `browser_input`、`browser_click_element`、`browser_select_option`：按真实流程一步步走。
- `browser_resize_window`：直接把窗口调到各个响应式断点去测，不要靠读媒体查询来判断。

每个状态都截下来，交给视觉评审者去看。

## 与目标比对

如果有视觉规范，比如设计稿、设计源文件或参考实现，就把目标和实现的截图一起交给视觉评审者，让它逐条列出间距、字重、对齐、颜色和比例上的具体差异。没有目标时，可以用 `generate_image` 生成一个，并标明是生成的。这样一来，“看起来对不对”这个纯文本 agent 回答不了的问题，就变成了一次比对，产出的是一份差异清单。

## 图片、文档和音频都是证据

Gemini 原生就能读图片、PDF、Office 文件和音频，所以用户给的任何东西都要当证据用，而不是当成回一句“收到”就完事的背景信息。bug 截图就是一次复现；设计稿就是拿来比对的规范；白板照片就是架构文档；图表就是数据。用户贴来一张报错截图，就直接从截图里读出报错信息，然后着手处理；让用户再手打一遍，等于把这个锚点扔了。

任务里有视觉锚点时，把图片本身交给评审者。模型本来可以直接看图，你却用文字转述给它，只会白白丢掉信息。

## 浏览器观察与写代码并行

工作既涉及实现、又涉及行为时，让一个 agent 在实现推进的同时观察运行中的应用，双方每一轮通过 `send_message` 对一次账。应用实际在做什么，以观察者看到的为准；实现者负责动手修改，让它做到应该做的事。

两边的职责要分开。观察者一旦动手改代码，或者实现者开始猜渲染效果，这种分工赖以成立的独立性就没了。

## 无法观察时

有些结论根本没有能跑起来观察的对象：架构层面的判断、针对无法安全触发的路径所做的安全推理、还跑不起来的代码。这类结论只能停留在第 3、4 级，也只有在这种情况下，对文本做对抗性审查才是合适的手段。

1. 把结论交给几个相互独立的反驳者，要求每一个都去反驳它，拿不准时一律判为“已驳倒”。
2. 如果一个结论可能从好几个方面出错，就给每个验证者分配不同的视角：正确性、安全性、性能、可复现性。
3. 必须多数通过才算过关。
4. 经受住反驳的结论，按假设上报，并注明所属层级。

在认定某个结论无法观察之前，先看看能不能花点小成本，搭个验证手段让它变得可观察：一个临时脚本、一个测试、一条查询。搭这么个东西，几乎总比让五个 agent 争论“这段代码大概会干什么”便宜，而且它给出的是结果，不是票数。
