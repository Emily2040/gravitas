# 模块 04 - 运行时验证

## 用途

本模块说明如何验证一切有运行界面或渲染界面的东西：应用程序、网页、3D 场景、图表、生成的图像以及排版后的文档。它是 `03-domain-checks.md` 中通用规则在一个领域的具体实例，即找到不经过你自己推理的核查。对软件而言，这个核查就是把东西运行起来，然后去看。

## 先确认工具集

围绕本次会话中实际存在的工具来规划验证，并在写计划之前确认它们。

| 界面 | 浏览器与运行时工具 |
| :--- | :--- |
| agy CLI | 没有。2026-09-24 在 agy 1.2.9 上获取的工具列表包含 `run_command`、`view_file`、`read_url_content`、`search_web`、`generate_image` 和子代理工具，没有浏览器工具 |
| Antigravity 桌面应用 | 开启浏览器集成时提供 `open_browser_url`、`capture_browser_screenshot`、`capture_browser_console_logs`、`browser_list_network_requests`、`browser_get_network_request`、`execute_browser_javascript`、`browser_click_element`、`browser_input`、`browser_select_option`、`browser_resize_window`、`read_browser_page`、`browser_subagent` |
| 两者皆可，借助插件 | 安装并启用 Chrome DevTools 插件后，浏览器控制以 `mcp_` 工具的形式提供 |
| 两者皆可，始终可用 | 写入文件并通过 `run_command` 运行的 Playwright 或 Puppeteer 检验装置 |

一次有记录的桌面应用运行完全没有浏览器工具。它的全部工具集是 `view_file`、`grep_search`、`list_dir`、`find_by_name`、`run_command`、`replace_file_content`、`write_to_file`、`schedule` 和 `manage_task`。代理仍然通过 `run_command` 搭建了一个 Playwright 检验装置并截了图，这样做是对的。问题从来不在检验装置本身，而在于它检查了什么，这部分见 `06-perceptual-gates.md`。

## 先观察

对任何有渲染或运行界面的东西，这是默认做法。文本审查回答的是“代码看起来对不对”。真正重要的问题是“这个东西是否做对了事”，而这是可以直接去看的。

1. 让它运行起来：先 `restart_dev_server` 再 `open_browser_url`，或者用 `run_command` 启动服务，再从检验装置中打开。
2. 在改动之前采集基线：一张截图和控制台日志。
3. 做出改动。
4. 在同样的视口下，改动之后再采集同样的界面。
5. 把两份采集交给 `gravitas-visual-critic`，它没有看过代码，也不能编辑任何东西；请它描述有何不同，以及这种不同是否是预期的。

`view_file` 会把图像作为图像交给模型：在 agy 1.2.9 上，评审者正确描述了一张测试 PNG，包括一个被问到但并不存在的形状。会“看”的评审者能发现代码审查看不到的一类缺陷：元素重叠、文字被容器截断、颜色对比度不达标、元素渲染到屏幕之外、布局在 400 px 宽度下崩溃、永远转不完的加载图标，以及存在于 DOM 中却无法被人看到的控件。

每次都要读控制台。一个渲染正常的组件内部抛出的运行时异常，是只看截图的核查最常漏掉的缺陷。

## 契约验证

对任何 API 调用、fetch、表单提交或请求，都要实际走一遍这条路径并读取线上的真实流量，而不是分别读客户端和处理程序、再推理两者是否一致。

- `browser_list_network_requests` 显示发出了哪些请求、顺序如何、各发了几次。
- `browser_get_network_request` 显示方法、请求头、请求体、状态码和响应体。
- 没有浏览器工具时，检验装置可以记录同样的流量，或者用 `run_command` 通过 `curl` 直接调用端点。

这能解决文本审查只能猜测的问题：重复提交、从未发出的请求、客户端发送而服务端忽略的字段、携带错误内容的 200 响应、重试风暴。

## 状态演练

静态审查会推理空状态、错误状态和加载状态，却常常推理错，因为这些路径在开发中被走到的次数最少。应该把它们实际驱动起来。

- `execute_browser_javascript` 直接强制进入某个状态。
- `browser_input`、`browser_click_element` 和 `browser_select_option` 走真实的流程。
- `browser_resize_window` 直接测试断点，而不是去读媒体查询。

把每个状态都截图，交给视觉评审者去看。

## 目标比对

当存在视觉规格时，例如设计稿、设计文件或参考实现，把目标和实现的截图一起交给视觉评审者，请它列出间距、字重、对齐、颜色和比例上的具体差异。没有目标时，`generate_image` 可以生成一个，并标注为生成的。这样就把文本代理无法回答的“看起来对不对”，变成了一次带结果清单的比对。

## 图像、文档和音频都是证据

Gemini 原生读取图像、PDF、Office 文件和音频，因此用户提供的任何东西都应当作证据，而不是只需知会一声的上下文。一张缺陷截图就是一次复现。一份设计稿就是可以比对的规格。一张白板照片就是一份架构文档。一张图表就是数据。用户贴出错误截图时，直接从图中读出错误并处理；让用户重新打一遍字，就丢掉了这个锚点。

当任务有视觉锚点时，把图像本身交给评审者。向一个本可以直接看图的模型用文字描述图像，只会白白丢失信息。

## 浏览器与代码并行

当工作同时涉及实现和行为时，一个代理观察运行中的应用，同时另一个进行实现，两者在每一轮通过 `send_message` 对齐。观察者掌握应用实际在做什么的事实，实现者改变它应该做什么。

保持两者的职责分离。开始编辑代码的观察者，或开始猜测渲染效果的实现者，都已失去了让这种分工有价值的独立性。

## 无法观察时

有些结论没有运行界面：架构判断、针对无法安全触发的路径的安全推理、尚不能运行的代码。这些结论停留在第 3 和第 4 层，只有在这里，对文本的对抗性审查才是合适的工具。

1. 把结论交给独立的反驳者，每人都被要求去反驳它，并在不确定时默认判为已反驳。
2. 当一个结论可能以多种方式出错时，给每位验证者一个不同的视角：正确性、安全性、性能、可复现性。
3. 需要多数通过才算成立。
4. 把幸存的结论作为假设连同其层级一起报告。

在接受一个结论无法观察之前，先看看一个廉价的检验装置能否让它变得可观察：一个临时脚本、一个测试、一次查询。搭建它几乎总是比让五个代理争论代码大概会做什么更便宜，而且它产出的是结果，而不是票数。
