# 模块 09 - 编排

## 用途

本模块说明如何组织一次扇出：何时等待结果、何时不等，哪种模式适合哪种情形，以及如何用台账让计数和去重保持精确。标准规模及以上时加载本模块。每种模式都说明它解决的问题、它的结构，以及它所防止的失败，各模式可以自由组合。

这些模式与领域无关。搜寻者在工作清单上搜寻某一类缺陷，而工作清单可以是文件、法条、论文或账目行。多模态扫描同时从多个角度搜索，在代码库中意味着按目录、调用图和渲染结果，在文献综述中意味着按引用网络、关键词、作者和未能复现的研究。

## 选择模式

| 情形 | 模式 |
| :--- | :--- |
| 存在独立核查 | 先观察的验证，见 `04-runtime-verification.md` |
| 不知道有多少问题 | 循环直到干涸 |
| 单一搜索角度会有遗漏 | 多模态扫描 |
| 解空间很宽 | 评审团 |
| 发现可能看似合理实则错误 | 对抗性反驳 |
| 发现可能以多种方式出错 | 多视角验证 |
| 可能有遗漏 | 完整性评审 |
| 每项成本差异很大 | 分级升级 |
| 数百项且需精确计数 | 脚本化编排，见 `13-platform.md` |
| 修复必须推进到通过 | 收敛型循环，见 `10-iteration.md` |
| 输出需要打磨而非纠错 | 梯度型循环，见 `10-iteration.md` |

## 先侦察，每个阶段一次扇出

先用你自己的工具发现工作清单：列出文件、运行搜索、调出法条目录、读目录页。然后针对你找到的东西扇出。多阶段工作按一系列扇出来进行，每个阶段一次（理解、设计、实现、审查），父代理读完每个结果再规划下一步。在一开始就规划好的一次巨型扇出，会把自己绑定在一份尚未学到任何东西时写下的工作清单上。

## 默认流水线

每个发现一出现就去验证。先返回的搜寻者，它的发现应当在较慢的搜寻者还在工作时就摆到反驳者面前。

只有当下一步需要一次拿到全部结果时，才等待整组结果：在昂贵的验证之前对所有搜寻者的结果去重、在总数为零时提前退出，或者一个需要在发现之间相互比较的步骤。展平、过滤和重新格式化都不需要等待，逐项处理即可。当五个搜寻者同时运行、最慢的用时是最快的三倍时，一次没有必要的等待会让快的结果在三分之二的时间里闲置。

## 台账

计数、去重和计票都是簿记，而簿记应当交给代码。一个在脑子里跟踪三轮中四十个发现的模型会数错，会重新验证已经否决过的发现，并且会过早或过晚地停止循环。`scripts/ledger.py` 把这些状态保存在一个 JSON 文件中，让决策变得确定。它只需要 Python 3.8 或更高版本。

用它在已安装插件中的完整路径运行它，即 `<home>/.gemini/config/plugins/gravitas/skills/gravitas/scripts/ledger.py`，并把台账文件放在工作区或产物目录中，使它在运行结束后仍然保留。下面的示例缩短了路径。

```bash
python scripts/ledger.py init  run.ledger.json --scale full
python scripts/ledger.py add   run.ledger.json finder-security.json --round 1 --by gravitas-finder
python scripts/ledger.py verdict run.ledger.json <key> --by gravitas-refuter --refuted no \
    --tier executed --source "pytest tests/test_session.py::test_logout -> 1 failed"
python scripts/ledger.py child run.ledger.json --id <conversation-id> --agent gravitas-finder --status denied \
    --note "read_file denied on src/auth"
python scripts/ledger.py close-round run.ledger.json --round 1
python scripts/ledger.py report run.ledger.json
```

它强制执行的规则：

- 层级为 `observed`、`executed` 或 `read` 而 `source` 为空的记录会被降为 `inferred`，`source` 中没有任何引文的 `read` 记录也会被降级。`01-evidence.md` 中的来源规则，由此成为台账对每条记录都执行的检查。
- 新记录要与曾经加入过的每一条记录去重，包括被反驳者否决的记录。只与幸存记录去重，会让被否决的发现每一轮都卷土重来，循环永远无法收敛。
- 同一位置的两条记录，当它们的结论有至少 0.25 的词重叠时自动合并，从 0.10 起标记为可能重复。在一次真实审计中，真正的重复得分为 0.13 到 0.69，同一行上的不同缺陷为 0.02 到 0.15；自动合并把 22 条记录减为 15 条，没有一次合并错误。被标记的记录用 `ledger.py merge KEEP DUP` 决定，它会把票数一并转移。
- 一个发现只有在未被拒绝的票中获得多数“未反驳”时才幸存，所需票数随规模而定：标准规模 1 票，完整和穷尽规模 3 票。
- `close-round` 统计新发现，推进“干涸”计数，并打印 `CONTINUE` 或 `STOP` 及原因：达到干涸轮数，或达到轮数上限。
- `report` 按严重程度列出幸存的发现及其层级和来源，然后是被反驳、待定和被降级的记录，然后是每一个状态不是 `done` 的子代理，最后是各项上限。

台账文件在最后一轮丢失时也能保留下来，所以把它放在用户找得到的地方。如果没有 Python，就在计划产物中用表格记录同样的字段，手工执行同样的规则，并在报告中说明台账是手工维护的。

## 循环直到干涸

在你不知道有多少问题时使用：缺陷、安全发现、死代码、边界情况、一组文档中的矛盾。派出一轮搜寻者，把它们的记录加入台账，验证新的记录，然后结束这一轮。在连续出现规模所设定的干涸轮数后停止。它防止固定轮数的循环在长尾中途停下，只报告容易的发现而漏掉其余的。

## 多模态扫描

单一的搜索角度看不到一切，而它漏掉什么取决于角度，所以同时运行多个角度。搜寻者按目录、按符号、按调用图、按近期改动、按测试覆盖、按错误字符串、按渲染结果来搜索。在这个平台上，视觉角度最重要：对每条路由截图扫描，能找到任何文本搜索都无法用查询表达的缺陷，因为缺陷是一种渲染结果，而不是一个字符串。它防止单一角度的盲点，例如搜索函数名永远找不到调用它的动态分发。

## 评审团

当解空间很宽时，第一个看似合理的答案很少是最好的。从不同的起点生成几个独立的尝试：最简单可行、风险优先、性能优先、用户优先。由没有参与编写任何一个的新裁判来打分。以胜出者为基础，嫁接其他方案中最强的想法。它防止“一次尝试然后打磨”，那样会锁定第一个框架，只在其中迭代。

## 对抗性反驳

把每个发现交给独立的反驳者，要求他们去反驳，并在不确定时默认判为已反驳。多数反驳就淘汰它。完整规模下用 3 名反驳者。“反驳它”引来审视，“这对吗”引来附和。它防止看似合理却错误的发现凭借文字本身存活下来。

## 多视角验证

当一个发现可能以多种方式出错时，给每位验证者一个不同的视角，而不是派出相同的反驳者：正确性、安全性、性能、能否复现。需要多数通过。问同一个问题的三个代理共享同一个盲点，还把它叫作共识。

## 完整性评审

每次报告之前都要运行。`gravitas-completeness-critic` 阅读台账和工作清单，只回答一个问题：缺了什么。哪个角度从未搜索过，哪个结论从未核实过，哪个文件从未打开过，哪个状态从未演练过，哪条路由从未渲染过，哪个子代理失败了。它指出的东西成为下一轮。它防止自信的片面答案，这是一次看起来很彻底的审计最常见的出错方式。

## 分级升级

当大多数条目都便宜、只有少数昂贵时，处处都付昂贵的价钱会浪费大部分预算。先用 `flash_lite` 扫一遍全部条目，只把触发信号的条目升级。记录两个方向的数量，因为升级率接近零或接近一，说明是信号校准有问题，而不是工作本身均匀。

## 反模式

- 在一份猜出来的工作清单上扇出。
- 在下游没有任何步骤比较发现时，却要等所有搜寻者都完成才开始验证。
- 以确认为框架的验证，问某样东西是否正确。
- 只与幸存记录去重，而不是与见过的一切去重。
- 无声的上限：报告中没有说明的抽样、前 N 项或提前停止。
- 在可以直接去看一个运行中的系统时，却从源代码去推理它。
