# 模块 09：编排

## 用途

本模块讲怎么组织一次扇出（fan-out）：什么时候该等结果、什么时候不该等，什么情况用哪种模式，以及怎样用台账（ledger）把计数和去重做到分毫不差。standard 及以上规模加载本模块。每种模式都交代三件事：解决什么问题、怎么搭、防住哪种失败。模式之间可以自由组合。

这些模式不限领域。每个搜寻者（finder）只盯一类缺陷，在整份工作清单上排查，清单里可以是文件，也可以是法条、论文或账目明细。多角度扫描（multi-modal sweep）是同时从几个角度去搜：放在代码库里，就是按目录、调用图和渲染结果搜；放在文献综述里，就是按引用网络、关键词、作者和复现失败的研究搜。

## 怎么选模式

| 情形 | 模式 |
| :--- | :--- |
| 有独立的核查手段 | 先观察再验证，见 `04-runtime-verification.md` |
| 不知道问题到底有多少 | 循环到出现空轮为止 |
| 只从一个角度搜会有遗漏 | 多角度扫描 |
| 解空间很大 | 多方案评审 |
| 某条发现可能听着有理、实际是错的 | 对抗式反驳 |
| 某条发现可能有好几种错法 | 多视角验证 |
| 可能漏了东西 | 完整性评审 |
| 每一项的成本差别很大 | 分级升级 |
| 几百项，且计数必须精确 | 脚本化编排，见 `13-platform.md` |
| 修复必须一直推进到变绿 | 收敛型循环，见 `10-iteration.md` |
| 输出要的是打磨，不是纠错 | 梯度型循环，见 `10-iteration.md` |

## 先摸底，再每个阶段扇出一次

先在请求点名的范围里把工作清单摸出来：列文件、跑搜索、调出法规的索引、读文档的目录（table of contents）。找文件时，手上有 `list_dir`、`find_by_name`、`grep_search` 就用它们；agy CLI 的主 agent 从 1.2.7 起没有这几个工具（`13-platform.md`），这时把文件夹的绝对路径交给 `gravitas-scout` 去找。别拿 shell 命令列目录来顶替：常驻规则禁止为找上下文去列目录，而且默认设置下的 headless 运行会拒绝这条命令，整轮的工作都会丢掉。然后在摸到的东西上扇出。多阶段的工作拆成一串扇出，每个阶段一次（理解、设计、实现、审查），父 agent 读完上一次的结果，再规划下一次。要是一开始就规划好一次超大的扇出，就等于在什么都还没弄清的时候，把工作清单定死了。

## 默认走流水线

每条发现一出来就去验证。哪个搜寻者先返回，它的发现就该马上交到反驳者（refuter）手上，不必等还在跑的慢搜寻者。

只有下一步必须一次拿到全部结果时，才等整批结果：在代价高的验证之前，把所有搜寻者的结果统一去重；总数为零时提前退出；或者某一步的 prompt 要拿发现互相比较。展平、过滤、改格式都不用等，逐条做就行。假设五个搜寻者同时跑，最慢的耗时是最快的三倍，这时如果做了一次其实没有哪一步用得上的等待，先出来的结果就要白白闲置整个运行时长的三分之二。

## 台账

计数、去重、计票都是记账的活，记账就该交给代码。让模型在脑子里跟踪三轮共四十条发现，它会数错，会把已经否掉的发现再验一遍，还会让循环停得过早或过晚。`scripts/ledger.py` 把这些状态存进一个 JSON 文件，让每个判定都是确定性的。它只需要 Python 3.8 或更高版本，别的什么都不用装。

运行时要用它在已安装插件里的完整路径：`<home>/.gemini/config/plugins/gravitas/skills/gravitas/scripts/ledger.py`。台账文件放在工作区或产物（artifact）目录里，这样运行结束后它还在。下面的示例用的是简写路径。

```bash
python scripts/ledger.py init  run.ledger.json --scale full
python scripts/ledger.py add   run.ledger.json finder-security.json --round 1 --by gravitas-finder
python scripts/ledger.py verdict run.ledger.json <key> --by gravitas-refuter --refuted no \
    --tier executed --source "pytest tests/test_session.py::test_logout -> 1 failed"
python scripts/ledger.py verdicts run.ledger.json refuter-verdicts.json --by gravitas-refuter
python scripts/ledger.py child run.ledger.json --id <conversation-id> --agent gravitas-finder --status denied \
    --note "read_file denied on src/auth"
python scripts/ledger.py close-round run.ledger.json --round 1
python scripts/ledger.py report run.ledger.json
```

它会强制执行以下规则：

- 证据层级是 `observed`、`executed` 或 `read` 但 `source` 为空的记录，一律降为 `inferred`；`read` 记录的来源里如果没有引用任何内容，同样降级：引文至少要有三个词或十二个字符，只引一个路径不算。每条记录都要按发现（finding）和裁决（verdict）的 schema 校验，格式不对的直接拒收，并说明原因。这样一来，`01-evidence.md` 里的来源规则就成了台账对每条记录都会跑的一项检查。
- 新记录要和历史上加进来的所有记录去重，包括被反驳者否掉的那些。如果只和存活的记录去重，被否掉的发现每一轮都会卷土重来，循环永远收敛不了。
- 同一位置的两条记录，结论的用词重合比例至少 0.25 就自动合并，从 0.10 起标记为疑似重复。同一文件里相距 5 行以内的记录，只有措辞几乎一样（0.8）才合并，否则只做标记，因为相隔几行的不同缺陷，描述起来往往很像。在一次真实审计中，真正重复的记录得分在 0.13 到 0.69 之间，同一行上的不同缺陷在 0.02 到 0.15 之间；自动合并把 22 条记录并成 15 条，没有一次合错。被标记的记录用 `ledger.py merge KEEP DUP` 来定夺，DUP 上的票会一并转到 KEEP 上。
- 一条发现要保留下来，计入的票里，没有反驳它的票必须过半数；所需票数由规模决定：standard 规模 1 票，full 和 exhaustive 规模 3 票。票和发现一样要守来源规则：被降级的票，或者状态为 `blocked` 的票，会记下来，但不计数。quick 规模不投票，所以它的报告会把发现列为未验证。
- `close-round` 统计本轮的新发现，推进空轮计数，然后打印 `CONTINUE` 或 `STOP` 并附上原因：连续空轮数已达到要求，或者轮数已到上限。
- `report` 先按严重程度列出存活的发现，附上证据层级和来源；接着是被反驳、待定和被降级的记录；再往后是所有状态不为 `done` 的 subagent，以及所有返回 `blocked` 的搜寻者；最后列出各项上限。

就算最后一个回合（turn）的输出丢了，台账文件也还在，所以要把它放在用户找得到的地方。如果没有 Python，就在计划产物里用一张表记下同样的字段，手工执行同样的规则，并在报告里写明台账是手工维护的。

## 循环到出现空轮为止

不知道问题到底有多少时用它：缺陷、安全类发现、死代码、边界情况、一批文档之间的矛盾。派出一轮搜寻者，把它们的记录加进台账，验证其中新出现的记录，然后关闭这一轮。连续空轮（一整轮没有新发现）的轮数达到规模规定的数目，就停。它防的是固定轮数的循环：在长尾中途停下，只报出容易找的发现，其余的全漏掉。

## 多角度扫描

单一的搜索角度看不全，而且漏掉什么取决于用的是哪个角度，所以要同时从几个角度搜。搜寻者分别按目录、按符号、按调用图、按近期改动、按测试覆盖、按错误字符串、按渲染结果来搜。在这个平台上，视觉角度最要紧：把每条路由都截图扫一遍，能找出任何文本搜索都写不出查询条件的缺陷，因为这种缺陷是渲染出来的结果，不是一个字符串。它防的是单一角度的盲区，比如按函数名搜索，永远找不到通过动态分发调用这个函数的地方。

## 多方案评审

解空间很大时，第一个说得通的答案很少是最好的。从不同的出发点生成几个独立的方案：最简单的可行做法、风险优先、性能优先、用户优先。由全新的、没写过其中任何一个方案的裁判来打分。以胜出的方案为底子，再把其他方案里最强的想法嫁接过来。它防的是“试一次、然后一直打磨”：那样会锁死在第一种思路里，之后只在这个框框里迭代。

## 对抗式反驳

把每条发现交给几个独立的反驳者，明确要求它们去反驳，拿不准时默认判为已反驳。过半数反驳，就毙掉这条发现。full 规模下用 3 个反驳者。要它“反驳这条”，招来的是挑刺；问它“这对不对”，招来的是附和。它防的是看似有理、实则错误的发现靠文笔蒙混过关。

## 多视角验证

一条发现如果可能错在不止一个方面，就别派一模一样的反驳者，而是给每个验证者一个不同的视角：正确性、安全性、性能、能不能复现。要求过半数通过。三个 agent 问同一个问题，共享的是同一个盲区，却把它叫作共识。

## 完整性评审

每次出报告之前都要跑。`gravitas-completeness-critic` 读台账和工作清单，只回答一个问题：还缺什么。哪个角度从没搜过，哪个结论从没验证过，哪个文件从没打开过，哪个状态从没被触发过，哪条路由从没渲染过，哪个 subagent 失败了。它点出来的东西，就是下一轮要做的事。它防的是自信却不完整的答案；一份看起来很周全的审计，最常见的翻车方式就是这个。

## 分级升级

如果大部分条目处理起来很便宜，只有少数很贵，那每一条都按高价处理，大部分预算就白花了。先用 `flash_lite` 把所有条目过一遍，只把触发了信号的条目升级。过一遍的条目数和升级的条目数都要记下来，因为升级率接近 0 或接近 1，说明是信号没校准好，而不是工作本身就这么均匀。 当问题不是花多少钱而是怎么写简报时，就在同一个条目上跑两份简报，让一个两份都没跑过的 agent 合成出更好的那份（`15-harness-probing.md`）。

## 反模式

- 在凭猜测列出的工作清单上扇出。
- 下游没有任何一步要比较发现，却要等所有搜寻者都跑完才开始验证。
- 验证时用确认式的问法，问“这对不对”。
- 只和存活的记录去重，而不是和见过的所有记录去重。
- 静默设限：抽样、只取前 N 项或提前停止，却不在报告里写明。
- 明明可以直接去看一个正在运行的系统，却只凭源码去推断它。
