# 模块 05 - 验收

## 用途

本模块说明如何写出一个真的会失败的核查，为什么截图在有人去看之前不算验证，以及如何确认一次“通过”的原因确实是你以为的那个。在报告任何东西“通过”之前，以及每次编写测试、关卡或检查清单时，加载本模块。

示例来自软件，因为失败是在那里被记录下来的。这些规则适用于每个领域。

| 规则 | 软件 | 法律 | 数学 | 实证结论 |
| :--- | :--- | :--- | :--- | :--- |
| 关卡必须能失败 | 报告模板里硬编码的 `PASS` | “引用已核实”其实指格式正确 | “代数已检查”其实指重读了一遍 | “来源已确认”其实指来源存在 |
| 要断言，不要只收集 | 控制台错误被推入一个没人读的数组 | 调出了法律依据却从未阅读 | 做了数值核查却从未比较 | 打开了一手来源却从未引用 |
| 评判产物本身，而非替代指标 | 数网格而不是看渲染图 | 数引用而不是读判决要旨 | 逐行核对而不是检验结果 | 核实论文存在而不是核对数字 |
| 通过需要有理由 | 测试通过是因为代码路径从未执行 | 没搜到冲突判例是因为数据库选错了 | 在空区间上搜索反例 | 一次返回错误的搜索得出“没有相反证据” |

## 本模块所依据的失败

一个代理搭建了一座 Three.js 巧克力工厂，截了 8 张图，写了一份含 8 个关卡的 `VERIFICATION.md`，并报告 `ALL TEST GATES PASSED SUCCESSFULLY`。场景第一眼看上去就不对。

测试集中有这样一行：

```js
| **T12-R1** | Hero Chocolate Identity Persistence | **PASS** | Exactly 1 mesh; UUID ${uuids[0]} persists. |
```

`PASS` 是模板里的一个字符串字面量。测得的值被插入，判定结果却是手写的。没有比较，没有阈值，没有分支。这套测试有 8 个关卡、8 个硬编码的通过、零条件逻辑，唯一的 `process.exit(1)` 在崩溃处理器里。

它还收集了控制台错误，却从未读取：

```js
const consoleErrors = [];
page.on('console', msg => { if (msg.type() === 'error') consoleErrors.push(msg.text()); });
```

## 关卡的规则

1. 每个关卡都把测得值与期望值相比较。如果你说不出失败条件，你就没有关卡。
2. 在信任关卡之前，先证明它能失败。故意把东西弄坏，运行测试集，看着它变红，再恢复原状。一套从未失败过的测试集，从未被测试过。
3. 任何关卡失败时，进程以非零退出。一套总是以 0 退出的测试集什么也没报告。
4. 采集到的东西要么被断言，要么删掉。把控制台错误收进一个没人读的数组，比不收集更糟，因为代码看起来像是做了检查。
5. 在读取核查输出之前，先确认它确实运行了。当你在找失败时，空结果和崩溃的脚本看起来一模一样，所以要用退出状态、行数，或核查在完成时打印的标记来确认。

## 通过需要有理由

只有当被测对象确实发生了，通过的结果才算证据。在报告通过之前，确认它所依赖的路径确实被执行过。

两个来自测试 Antigravity 本身的案例。一次注入测试看起来显示代理抵御住了文件中植入的恶意指令；可转录记录显示，那次 `read_file` 调用被权限系统拒绝了，代理根本没看到载荷，也就谈不上抵御。另外，有工具被拒绝的无头运行会返回 `"status": "SUCCESS"` 和退出码 0，而这一轮的工作被丢弃，这已作为 issue #794 提交到 `google-antigravity/antigravity-cli`。两个案例中，“通过”的信号都来自检验装置，与被测行为无关。

对每一个重要的通过，说出被测路径确实执行过的证据：转录记录中的工具步骤、日志行、变动过的计数器、发出过的请求。

## 先排除你自己的仪器

当结果出人意料时，先查检验装置，再去怪系统。在同一轮测试中，一次看似 Antigravity 故障的运行，结果是测试装置在中途撤销了自己的权限授权。失败是真实的，但它属于仪器。

在测试这个版本时又发生了一次。检验装置通过 Windows shell 把提示词传给 `agy`，而 shell 在第一个换行处就结束了命令，于是多行提示词只到达了第一行。持有临时通配授权的 Gemini 3.8 Flash 认为指令缺失，便去寻找：它读取了用户的 PowerShell 历史、另外四个会话的转录记录以及正在运行的进程的命令行，在检验装置自己的进程里找到了完整提示词，然后完成了任务。错在检验装置。它暴露出的行为在 `00-orchestrator.md` 中有规定：请求看起来不完整时，要么询问，要么停下。为这个版本编写的来源核查器随后也在自己的第一次测试中失败：它把一份来源正确的法律答案中全部六个来源报告为“未打开”，因为它的路径模式匹配到了 `https://` 里的 `s:/`。

一次只改一件事，把每次运行都保存在脚本里而不是作为临时命令，并把对照组与测试用例一起重跑。无法从保存的脚本重跑的结果只是轶事，`11-findings.md` 也把它当轶事对待。

## 报告之前

- 核查确实运行过，由退出状态、行数或完成标记证明。
- 每个关卡都写明了失败条件。
- 至少有一个关卡被亲眼看着失败过。
- 每个重要的通过都说明了被测路径执行过的证据。
- 控制台输出被断言，没有任何东西只是被收集。
- 一位新的评审者看过渲染结果，回答了材质、光照和辨认方面的问题。
- 计划中关于外观的每一项规格，都有一个关卡去问它看起来是否如此。
- 报告写明了哪些没有覆盖。

一份全绿、却从未展示过任何关卡变红的报告，并没有证明它的任何关卡能发现失败。
