# gravitas

绝大多数低质量的代理输出，源于三种失败。

**貌似完整。** 代理只看了问题的一部分，找到了一些真实的东西，然后停下了。扇出可以解决这个问题。

**共识性幻觉。** 多个代理读了同一份文本，于是一起得出同一个错误结论。只有证据能解决这个问题，增加投票者永远不能。

**机器腔调。** 工作本身是正确的，读起来却像生成的，于是没人信任它。一套文风标准可以解决这个问题。

本技能同时处理这三者。参考文件按需加载，本页请保留在上下文中。

## 证据分层

按照结论的确立方式给每一条主张分层。上报之前，尽可能把它往上推。

| 层级 | 依据 | 例子 |
|---|---|---|
| 1. **`observed`** 已观察 | 你亲眼看了正在运行的东西 | 截图、控制台日志、网络负载、渲染后的 DOM |
| 2. **`executed`** 已执行 | 它跑过了，并且结果被检查过 | 测试通过、退出码为 0、查询返回了行 |
| 3. **`read`** 已读取 | 源码这么写的 | 该处理函数校验了输入 |
| 4. **`inferred`** 已推断 | 某个代理推理出来的 | “这里大概是竞态条件” |

**层级名称固定为这四个英文单词，不得翻译、不得替换、不得自行造词：`observed`、`executed`、`read`、`inferred`。** 上报时必须逐字使用这四个词。

第 4 层的主张是假设，不是结论。对抗式投票只能在第 4 层内部移动一条主张，永远无法把它提升一层。提升需要真正运行点什么，而在这个平台上，你几乎总能运行点什么。

每条发现都要标注层级。同时说明哪些范围没有覆盖到。

**几何验证与观感验证不能互相替代。** 用脚本断言场景图或 DOM 属于几何验证；把截图交给评审者去看、去判断，才是观感验证。一次运行可以通过全部几何检查，产物依然难看，因为没有任何一步问过“它看起来对不对”。**写死 PASS 的关卡不是关卡。** 详见 [references/acceptance.md](./references/acceptance.md)。

## 代理性陷阱

这是所有其他防护都挡不住的失败，所以在规划任何验证之前先读这一节。

**当真正要问的问题难以核查、而旁边有个容易核查的问题时，被核查的就会是那个容易的。** 而且查得很彻底。它通过了。工作被当作已验证上报。

| 真正重要的问题 | 实际被核查的代理指标 |
|---|---|
| 这个场景看起来像巧克力工厂吗 | 是不是有 10 个载具和 6 个滚筒 |
| 这份合同是否真的产生了我主张的义务 | 文件里有没有出现"赔偿"二字 |
| 这个证明正确吗 | 每一行的形式是否合法 |
| 这个物理答案对吗 | 量纲能否约掉 |
| 这项研究支持该结论吗 | 被引用的论文是否存在 |

右侧每一项都是必要条件，没有一项是充分条件。每一项都会在真正的属性失败时给出干净的通过。

**判定代理指标的方法：** 确认这项检查能否在你真正关心的东西为假时依然通过。如果能，它就是代理指标。保留它，并在旁边补上真正的检查。

实测案例：某次运行确认场景中恰好有一个巧克力网格，且其 UUID 在所有阶段保持不变。这是真的。而一个只拿到渲染图的独立评审者报告：巧克力**不存在**，因为它从未被渲染出来。两个陈述都正确。计数替代了可见性，而没有任何一步发现这个差别。

## 让它可核查

找到那个不经过你自己推理的检查。这种独立性就是全部价值所在。

- **数学。** 在随机点上做数值验算、测试边界情形、检查极限、用第二种方法独立验证、主动构造反例。
- **物理与工程。** 先做量纲分析，再做数量级比对，然后是极限情形与守恒律。
- **法律。** 调出条文原文，引用真正产生义务的那几个词。确认该权威依据现行有效、管辖适用、未被推翻。区分判决理由与附带意见。
- **事实与经验性主张。** 追到一手来源。核对数字一致、范围一致、且未被更新的资料取代。
- **统计。** 从原始数据重算，核对总计，检查分母，与基础比率作比较。
- **软件与渲染产物。** 把它跑起来，然后去看。

## 用上视觉能力

Gemini 能看见。多数代理框架不能，所以多数编排方面的建议忽略了这一点。那些建议把最强的验证信号白白放在了桌上。

只要工作涉及可渲染或可运行的界面，默认就用这些工具：

- `capture_browser_screenshot` 给评审者一样可以看的东西。它能发现元素重叠、文字被裁切、对比度不达标、元素渲染到了屏幕外、布局在窄宽度下塌陷、转圈动画永远不结束、控件存在于 DOM 中却对人不可见。这些没有任何代码阅读者能发现。
- `capture_browser_console_logs` 捕获那种“组件渲染看起来正常、运行时却抛异常”的情况。
- `browser_list_network_requests` 与 `browser_get_network_request` 验证真实的请求与响应，而不是假定的接口契约。
- `execute_browser_javascript` 强制进入空态、错误态和加载态，让它们被真正走一遍，而不是靠推理。
- `browser_resize_window` 真实地测试响应式断点。
- `generate_image` 合成一个目标图像用于比对实现，把“看起来对不对”这种问题转化成可核查的比较。
- `browser_subagent` 与代码代理并行驱动浏览器，持有关于实际行为的事实基准。
- `read_terminal` 读取真正发生了什么，而不是假定命令已经完成了它该做的事。

完整方法见 [references/verification.md](./references/verification.md)。

## 子代理分两步

子代理必须**先定义、后调用**。跳过定义是最常见的失败，`invoke_subagent` 找不到一个从未声明过的专家。

1. `define_subagent` 声明一个专家：`subagent_name`、明确的职责范围、仅授予它需要的工具，以及按任务选择的 `subagent_model`。
2. `invoke_subagent` 派发它。`subagent_count` 可在一个任务清单上并发运行 N 份。
3. `send_message` 在代理之间传递信息。子代理返回自包含的结果，不做过程叙述。

按每个角色实际做的事来选模型。`MODEL_TIER_FLASH_LITE` 用于机械性抽取与初筛，`MODEL_TIER_FLASH` 用于查找者与阅读者，`MODEL_TIER_PRO` 用于裁判、反驳者、视觉评审与最终综合，`MODEL_TIER_INHERIT` 用于实现，这样工作会沿用用户自己选的模型。

只有当某个专家确实需要再细分自己的职责时，才设置 `enable_subagent_tools: true`。层级太深既慢又难以审计。

角色清单、职责契约见 [references/subagents.md](./references/subagents.md)。

## 主循环

1. **划定范围。** 在派发任何子代理之前，用你自己的工具把任务清单建出来。绝不要在猜测出来的清单上做扇出。
2. **扇出。** 每个条目或每个维度一个专家，并发执行，每份职责窄到其结果可被核查。
3. **让它可观察。** 如果工作有运行时界面，现在就用 `restart_dev_server` 和 `open_browser_url` 把它跑起来。后续验证依赖它存在。
4. **以经验验证。** 把每条主张尽可能往证据分层上方推。只有对确实无法观察的主张，才退回到对抗式文本评审。
5. **批判。** 一个全新的代理指出缺了什么：从未搜过的角度、从未验证的主张、从未走过的状态。它指出的内容成为下一轮的工作。
6. **综合。** 合并、去重、按严重性排序，报告层级与缺口。

## 有纪律地迭代

重复不等于改进。开始任何循环之前，先判断你处在哪一种循环里。

**收敛型循环**追求正确性。每一轮都必须消费一个新的外部信号，且该信号必须能**定位错误**：失败的断言、堆栈跟踪、控制台异常、截图差异、与预期契约矛盾的网络响应。模型通常能在被告知错误位置后修好它，却无法可靠地在自己的产出中找到这个位置。没有新信号就停。

**梯度型循环**追求质量，用于散文、命名、接口手感和布局，这些地方不存在唯一正解可供偏离。**默认跑 3 轮，绝不超过 5 轮。** 这是两个不同的数字：3 是默认停下的地方，5 是不可逾越的上限。收益集中在前两轮，超过大约三轮后会开始反转。

**永不迭代**那些没有可获取信号、无法证伪的判断。取一次独立意见，标注为假设，然后继续往前走。

阈值、证据与出处见 [references/iteration.md](./references/iteration.md)。

## 模式选择

| 情境 | 模式 |
|---|---|
| 存在可渲染或可运行的界面 | 观察优先验证 |
| 不知道总共有多少问题 | 循环至枯竭 |
| 单一搜索角度必然会漏 | 多模态扫描 |
| 解空间宽阔开放 | 评审团 |
| 一条发现可能以多种方式出错 | 多视角验证 |
| 怀疑遗漏了什么 | 完整性批判者 |
| 单项成本差异极大 | 分级升级 |
| 必须把修复推到全绿 | 收敛型循环 |
| 产物需要打磨而非纠错 | 梯度型循环 |

结构见 [references/patterns.md](./references/patterns.md)。

## 不可让步的条款

- 先建任务清单。靠猜会产出系统性的、自信的盲区。
- 验证者必须独立且只读。定义评审者时不要给写权限，这样评审者无法去修它可能误判的东西。
- 重新标注来源。把产物作为第三方输出交给评审者，绝不说“你之前的那次尝试”。错误检出率会实测提升。
- 反驳，而非确认。“试着反驳这一条，不确定就默认为已被反驳”优于“这样对吗”。
- 一致不等于证据。多个代理对无法验证的推理达成一致，只是相关性推断。
- 绝不把第 4 层的主张当作事实上报。
- 声明每一处截断。未加说明的抽样或提前停止，会把一个部分答案变成一个虚假的完整性声明。
- 当各轮不再产出新东西时停下。已经花掉的力气不构成停止条件。

## 像人一样写

正确却读起来像生成的东西，会在被评估之前就被丢掉。本技能产出的每一件东西，包括缺陷报告、摘要、提交信息与文档，都遵循 [references/prose.md](./references/prose.md) 中的文风标准。

简短版本：刻意变化句长，把每个抽象说法落到可观察的机制或指标上，剔除对比式句式、反问句、模糊的强调副词和破折号节奏。用词不是破绽，结构才是。

关于中文的补充：`slopcheck.py` 的对比式句式、强调副词与词汇黑名单检查是针对英文的，对中文会被跳过并明确提示。句长与节奏检查对中文有效，按字符数而非词数统计。中文里对应的机器腔调另有其形：四字短语堆砌、每段都以“不仅……而且……”收束、通篇句长整齐、以及“综上所述”一类的收尾套话。

## 了解平台

Antigravity 有一些已验证的约束，忽略它们会让你的工作悄无声息地白费。放在工作区 `.agents/` 目录下的技能永远不会被加载。格式错误的 `SKILL.md` 会被跳过，解析错误只写进一个用户永远看不到的滚动日志文件，所以该技能就是不存在，且任何地方都不会有警告。细节与绕行办法见 [references/platform.md](./references/platform.md)。

## 按需调整规模

“快速看一下”只需两个代理和一轮验证。“好好审计一遍”则需要更宽的查找者池、在任何存在界面的地方做视觉与运行时验证、对确实无法观察的部分做三到五票的对抗式反驳，以及一个完整性批判者。动手之前先定好规模。
