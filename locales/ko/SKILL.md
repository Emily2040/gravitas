# gravitas

품질이 낮은 에이전트 결과물은 대부분 세 가지 실패로 설명된다.

**그럴듯한 불완전성.** 문제의 일부만 보고, 진짜인 무언가를 찾아내고, 거기서 멈춘다. 팬아웃이 이것을 해결한다.

**합의된 환각.** 여러 에이전트가 같은 텍스트를 읽고, 함께 같은 잘못된 결론에 도달한다. 이것을 해결하는 것은 증거뿐이며, 투표자를 늘리는 것으로는 결코 해결되지 않는다.

**기계적인 문체.** 내용은 맞는데 생성된 것처럼 읽혀서 아무도 신뢰하지 않는다. 문장 기준이 이것을 해결한다.

이 스킬은 셋 모두를 다룬다. 참조 파일은 필요할 때 읽고, 이 페이지는 컨텍스트에 유지할 것.

## 증거 계층

모든 주장을 어떻게 확립되었는지로 등급을 매긴다. 보고하기 전에 가능한 한 위로 끌어올릴 것.

| 계층 | 근거 | 예시 |
|---|---|---|
| 1. **`observed`** 관찰됨 | 실행 중인 것을 직접 보았다 | 스크린샷, 콘솔 로그, 네트워크 페이로드, 렌더링된 DOM |
| 2. **`executed`** 실행됨 | 실행했고 그 결과를 확인했다 | 테스트 통과, 종료 코드 0, 쿼리가 행을 반환 |
| 3. **`read`** 읽음 | 소스에 그렇게 쓰여 있다 | 해당 핸들러가 입력을 검증한다 |
| 4. **`inferred`** 추론됨 | 어떤 에이전트가 그렇게 추론했다 | "아마 경쟁 상태일 것이다" |

**계층 이름은 이 네 영어 단어로 고정한다. 번역하거나 바꾸거나 새로 만들지 말 것: `observed`, `executed`, `read`, `inferred`.** 보고할 때 이 네 단어를 그대로 쓴다.

4계층 주장은 가설이다. 적대적 투표는 주장을 4계층 안에서 움직일 뿐 결코 승격시키지 못한다. 승격하려면 무언가를 실제로 실행해야 하고, 이 플랫폼에서는 거의 항상 무언가를 실행할 수 있다.

발견마다 계층을 함께 적을 것. 그리고 다루지 못한 범위도 밝힐 것.

**기하 검증과 지각 검증은 서로를 대체하지 못한다.** 씬 그래프나 DOM 을 스크립트로 재는 것은 기하 검증이고, 스크린샷을 비평자에게 보여 판단하게 하는 것이 지각 검증이다. 기하 검사를 전부 통과하고도 결과물이 잘못 보일 수 있다. 아무도 "보기에 맞는가"를 묻지 않았기 때문이다. **PASS 를 하드코딩한 게이트는 게이트가 아니다.** 자세한 내용은 [references/acceptance.md](./references/acceptance.md) 참조.

## 시각을 활용하라

Gemini 는 볼 수 있다. 대부분의 에이전트 환경은 보지 못하므로, 오케스트레이션에 관한 조언 대부분이 이 점을 무시한다. 그 조언들은 가장 강력한 검증 신호를 그대로 남겨두고 있다.

렌더링되거나 실행되는 화면이 있는 작업이라면 기본으로 이 도구들을 쓸 것.

- `capture_browser_screenshot` 은 비평 역할에게 볼 것을 제공한다. 요소 겹침, 잘린 텍스트, 미달하는 명암비, 화면 밖으로 렌더링된 요소, 좁은 폭에서 무너지는 레이아웃, 끝나지 않는 스피너, DOM 에는 있지만 사람 눈에는 보이지 않는 컨트롤을 잡아낸다. 코드만 읽어서는 어느 것도 찾을 수 없다.
- `capture_browser_console_logs` 는 정상적으로 렌더링된 컴포넌트 안에서 발생한 런타임 예외를 잡는다.
- `browser_list_network_requests` 와 `browser_get_network_request` 는 가정된 계약이 아니라 실제 요청과 응답을 검증한다.
- `execute_browser_javascript` 는 빈 상태, 오류 상태, 로딩 상태를 강제로 만들어 추론 대신 실제로 통과시킨다.
- `browser_resize_window` 은 반응형 분기점을 실제로 시험한다.
- `generate_image` 는 비교 대상이 될 목표 이미지를 합성해, "보기에 맞는가"라는 질문을 검증 가능한 비교로 바꾼다.
- `browser_subagent` 는 코드 에이전트와 나란히 브라우저를 조작하며 실제 동작에 대한 사실 기준을 유지한다.
- `read_terminal` 은 명령이 제 역할을 했다고 가정하지 않고 실제로 무슨 일이 있었는지 읽는다.

전체 방법은 [references/verification.md](./references/verification.md) 참조.

## 서브에이전트는 두 단계다

서브에이전트는 **정의한 뒤에야 호출할 수 있다.** 정의를 건너뛰는 것이 가장 흔한 실패이며, `invoke_subagent` 는 선언된 적 없는 전문가를 찾지 못한다.

1. `define_subagent` 가 전문가 하나를 선언한다. `subagent_name`, 명확한 임무 범위, 필요한 도구만 부여, 그리고 일에 맞춰 고른 `subagent_model`.
2. `invoke_subagent` 가 파견한다. `subagent_count` 로 작업 목록에 대해 N 개를 동시에 돌릴 수 있다.
3. `send_message` 가 에이전트 사이의 연락을 맡는다. 자식 에이전트는 자족적인 결과를 반환하며 진행 상황을 서술하지 않는다.

모델은 각 역할이 실제로 하는 일에 따라 고른다. 기계적 추출과 분류에는 `MODEL_TIER_FLASH_LITE`, 탐색과 독해에는 `MODEL_TIER_FLASH`, 판정·반증·시각 비평·최종 종합에는 `MODEL_TIER_PRO`, 구현에는 `MODEL_TIER_INHERIT` 를 써서 사용자가 고른 모델을 그대로 따르게 한다.

`enable_subagent_tools: true` 는 그 전문가가 자신의 임무를 실제로 더 쪼개야 할 때만 설정한다. 깊은 트리는 느리고 감사하기 어렵다.

역할 목록과 임무 계약은 [references/subagents.md](./references/subagents.md) 참조.

## 기본 루프

1. **범위를 정한다.** 서브에이전트를 띄우기 전에 자신의 도구로 작업 목록을 만든다. 추측한 목록으로 팬아웃하지 말 것.
2. **팬아웃.** 항목당 또는 관점당 전문가 하나씩 동시에 돌린다. 임무는 결과를 검증할 수 있을 만큼 좁게.
3. **관찰 가능하게 만든다.** 실행 화면이 있는 작업이면 지금 `restart_dev_server` 와 `open_browser_url` 로 띄운다. 이후 검증이 이것의 존재에 의존한다.
4. **경험적으로 검증한다.** 모든 주장을 계층 위로 끌어올린다. 정말로 관찰할 수 없는 주장에 한해서만 적대적 텍스트 검토로 되돌아간다.
5. **비평.** 새로운 에이전트가 빠진 것을 짚는다. 한 번도 찾아보지 않은 관점, 한 번도 검증하지 않은 주장, 한 번도 통과시키지 않은 상태. 그것이 다음 회차의 작업이 된다.
6. **종합.** 합치고, 중복을 제거하고, 심각도로 정렬하고, 계층과 공백을 보고한다.

## 규율 있게 반복하라

반복이 곧 개선은 아니다. 루프를 시작하기 전에 자신이 어느 루프에 있는지 정할 것.

**수렴 루프**는 정확성을 좇는다. 매 회차는 새로운 외부 신호를 소비해야 하고, 그 신호는 **오류의 위치를 짚어주는** 것이어야 한다. 실패한 단언, 스택 트레이스, 콘솔 예외, 스크린샷 차이, 기대한 계약과 어긋나는 네트워크 응답. 모델은 위치를 알려주면 대개 고칠 수 있지만, 자기 결과물 안에서 그 위치를 안정적으로 찾아내지는 못한다. 새 신호가 없으면 멈춘다.

**경사 루프**는 품질을 좇는다. 문장, 이름 짓기, API 사용감, 레이아웃처럼 벗어날 단일 정답이 없는 영역. **기본 3회, 5회를 절대 넘기지 않는다.** 이것은 서로 다른 두 숫자다. 3은 기본적으로 멈추는 지점, 5는 넘어서는 안 되는 상한. 개선은 처음 두 회차에 몰리고, 대략 세 회차를 넘기면 뒤집힐 수 있다.

**절대 반복하지 않을 것**은 얻을 수 있는 신호가 없고 반증도 불가능한 판단이다. 독립적인 의견을 한 번 받고, 가설로 표기하고, 넘어간다.

임계값, 근거, 출처는 [references/iteration.md](./references/iteration.md) 참조.

## 패턴 선택

| 상황 | 패턴 |
|---|---|
| 렌더링되거나 실행되는 화면이 있다 | 관찰 우선 검증 |
| 문제가 몇 건인지 모른다 | 소진될 때까지 반복 |
| 단일 탐색 관점으로는 놓친다 | 다중 모드 탐색 |
| 해답 공간이 넓고 열려 있다 | 심사 패널 |
| 하나의 발견이 여러 방식으로 틀릴 수 있다 | 다관점 검증 |
| 무언가 놓쳤다는 의심이 든다 | 완전성 비평 역할 |
| 항목별 비용 차이가 크다 | 단계적 확대 |
| 수정을 전부 통과까지 밀어야 한다 | 수렴 루프 |
| 오류 수정이 아니라 다듬기가 필요하다 | 경사 루프 |

구조는 [references/patterns.md](./references/patterns.md) 참조.

## 양보할 수 없는 것

- 작업 목록을 먼저 만든다. 추측은 체계적이고 자신만만한 사각지대를 만든다.
- 검증자는 독립적이고 읽기 전용이어야 한다. 비평 역할에 쓰기 권한을 주지 않으면, 자기가 오진한 것을 스스로 고쳐버리는 일이 없다.
- 출처를 바꿔 붙인다. 결과물을 제3자의 산출물로 비평 역할에게 건네고, "당신의 지난 시도"라고 말하지 않는다. 오류 검출률이 실측으로 올라간다.
- 확인이 아니라 반증을 요구한다. "이것을 반증해 보라, 확신이 없으면 반증된 것으로 하라"가 "이게 맞나"보다 낫다.
- 일치는 증거가 아니다. 검증 불가능한 추론에 대한 여러 에이전트의 동의는 상관된 추론일 뿐이다.
- 4계층 주장을 사실로 보고하지 않는다.
- 모든 잘라냄을 밝힌다. 밝히지 않은 표본 추출이나 조기 종료는 부분적인 답을 완전하다는 거짓 주장으로 바꾼다.
- 회차가 새로운 것을 내놓지 않으면 멈춘다. 들인 노력은 정지 조건이 아니다.

## 사람처럼 써라

맞더라도 생성된 것처럼 읽히면, 평가받기 전에 버려진다. 이 스킬이 만들어내는 모든 결과물, 즉 결함 보고서, 요약, 커밋 메시지, 문서는 [references/prose.md](./references/prose.md) 의 문장 기준을 따른다.

요약하면, 문장 길이를 의도적으로 바꾸고, 모든 추상을 관찰 가능한 메커니즘이나 수치에 붙이고, 대조 구문과 수사 의문문과 모호한 강조어와 대시 리듬을 걷어낸다. 어휘는 단서가 아니다. 구조가 단서다.

한국어 보충: `slopcheck.py` 의 대조 구문, 강조어, 어휘 블랙리스트 검사는 영어용이며 한국어에서는 명시적으로 건너뛴다. 문장 길이와 리듬 검사는 한국어에도 유효하며, 단어 수가 아니라 글자 수로 센다. 한국어의 기계적 문체는 다른 형태를 띤다. "~할 수 있습니다"의 반복, 모든 문단이 같은 길이, "~적인"의 남발, 그리고 "결론적으로 말하자면" 같은 마무리 상투구.

## 플랫폼을 알아라

Antigravity 에는 무시하면 작업이 조용히 낭비되는 검증된 제약이 있다. 워크스페이스 `.agents/` 디렉터리에 둔 스킬은 결코 로드되지 않는다. 잘못된 `SKILL.md` 는 건너뛰어지고, 파싱 오류는 사용자가 볼 일 없는 순환 로그 파일에만 기록되므로, 그 스킬은 그냥 존재하지 않으며 어디에도 경고가 없다. 세부 사항과 우회 방법은 [references/platform.md](./references/platform.md) 참조.

## 규모를 맞춰라

"빠르게 한번 봐 줘"라면 에이전트 둘과 검증 한 번이면 된다. "제대로 감사해 줘"라면 넓은 탐색자 풀, 화면이 있는 모든 곳에서의 시각·런타임 검증, 정말로 관찰할 수 없는 부분에 대한 3표에서 5표의 적대적 반증, 그리고 완전성 비평 역할이 필요하다. 시작하기 전에 규모를 정할 것.
