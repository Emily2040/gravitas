# 모듈 04 - 런타임 검증

## 목적

이 모듈은 실제로 실행되거나 화면에 렌더링되는 모든 것의 검증을 다룹니다. 애플리케이션, 웹 페이지, 3D 씬, 차트, 생성된 이미지, 조판된 문서가 모두 여기에 해당합니다. `03-domain-checks.md`에는 "내 추론을 거치지 않는 검증 수단을 찾으라"는 일반 원칙이 있고, 이 모듈은 그 원칙을 한 분야에 구체적으로 적용한 것입니다. 소프트웨어라면 그런 검증은 직접 실행해 보고 눈으로 확인하는 것입니다.

## 도구부터 확인하기

검증 계획은 지금 이 세션에 실제로 있는 도구를 기준으로 세웁니다. 계획을 쓰기 전에 어떤 도구가 있는지부터 확인합니다.

| 실행 환경 | 브라우저·런타임 도구 |
| :--- | :--- |
| agy CLI | 없습니다. 2026-09-24에 agy 1.2.9에서 뽑은 도구 목록에는 `run_command`, `view_file`, `read_url_content`, `search_web`, `generate_image`와 서브에이전트 도구가 있었고, 브라우저 도구는 하나도 없었습니다 |
| Antigravity 데스크톱 앱 | 브라우저 연동을 켜 둔 경우 `open_browser_url`, `capture_browser_screenshot`, `capture_browser_console_logs`, `browser_list_network_requests`, `browser_get_network_request`, `execute_browser_javascript`, `browser_click_element`, `browser_input`, `browser_select_option`, `browser_resize_window`, `read_browser_page`, `browser_subagent` |
| CLI·데스크톱 공통 (플러그인 설치 시) | Chrome DevTools 플러그인을 설치하고 활성화해 두면, 이 플러그인이 브라우저 제어 기능을 `mcp_` 도구로 제공합니다 |
| CLI·데스크톱 공통 (항상 가능) | Playwright나 Puppeteer 하네스를 파일로 작성해 `run_command`로 실행 |

데스크톱 앱에서 기록한 실행 사례 중에는 브라우저 도구가 아예 없었던 경우가 있습니다. 쓸 수 있는 도구는 `view_file`, `grep_search`, `list_dir`, `find_by_name`, `run_command`, `replace_file_content`, `write_to_file`, `schedule`, `manage_task`가 전부였습니다. 그래도 에이전트는 `run_command`로 Playwright 하네스를 만들어 스크린샷을 찍었고, 이는 올바른 대응이었습니다. 하네스 자체에는 문제가 없었습니다. 문제는 그 하네스로 무엇을 확인했느냐였고, 이 부분은 `06-perceptual-gates.md`에서 다룹니다.

## 관찰이 먼저

화면에 그려지거나 실제로 실행되는 것이라면 이 방식이 기본입니다. 텍스트 리뷰가 답해 주는 것은 "코드가 맞아 보이는가"까지입니다. 정작 중요한 질문은 "실제로 제대로 동작하는가"이고, 이건 직접 눈으로 확인할 수 있습니다.

1. 띄우기: `run_command`로 서버를 실행합니다. 환경에서 `restart_dev_server`를 제공한다면 그걸 써도 됩니다(데스크톱 바이너리에는 들어 있지만, 기록된 도구 목록 어디에도 나온 적은 없습니다). 그다음 `open_browser_url`이나 하네스로 엽니다.
2. 변경 전 기준 캡처: 스크린샷과 콘솔 로그를 남겨 둡니다.
3. 변경 사항을 적용합니다.
4. 변경 후에도 같은 뷰포트에서 2단계와 같은 대상(스크린샷과 콘솔 로그)을 다시 캡처합니다.
5. 두 캡처를 시각 비평가인 `gravitas-visual-critic`에게 넘기고, 무엇이 달라졌는지, 그 차이가 의도한 변화가 맞는지 설명하게 합니다. 이 에이전트는 코드를 본 적이 없고, 아무것도 수정할 수 없습니다.

`view_file`은 이미지를 이미지 그대로 모델에 넘깁니다. agy 1.2.9에서 시각 비평가에게 테스트용 PNG를 보여 주었더니 내용을 정확히 묘사했고, 질문에서 물어본 도형이 실제로는 없다는 점까지 제대로 짚었습니다. 직접 눈으로 보는 비평가는 코드 리뷰로는 보이지 않는 종류의 결함을 잡아냅니다. 서로 겹친 요소, 컨테이너에 잘린 텍스트, 명도 대비 기준에 못 미치는 색, 화면 밖으로 밀려나 렌더링된 요소, 400 px에서 깨지는 레이아웃, 끝나지 않고 계속 도는 스피너, DOM에는 있지만 사람 눈에는 보이지 않는 컨트롤 같은 것들입니다.

콘솔은 매번 확인합니다. 스크린샷만 보는 검증이 가장 자주 놓치는 결함은, 화면은 멀쩡히 렌더링됐는데 그 컴포넌트 안에서 런타임 예외가 나는 경우입니다.

## API 계약 검증

API 호출, fetch, 폼 제출을 비롯해 요청이 오가는 곳이라면, 클라이언트 코드와 핸들러 코드를 읽고 둘이 맞물리는지 머리로 따지지 않습니다. 그 경로를 실제로 실행하고, 네트워크에 실제로 오간 내용을 확인합니다.

- `browser_list_network_requests`: 어떤 요청이, 어떤 순서로, 몇 번 나갔는지 보여 줍니다.
- `browser_get_network_request`: 메서드, 헤더, 페이로드, 상태 코드, 응답 본문을 보여 줍니다.
- 브라우저 도구가 없으면 하네스로 같은 트래픽을 기록하거나, `run_command`에서 `curl`로 엔드포인트를 직접 호출합니다.

이렇게 하면 텍스트 리뷰로는 짐작만 하던 문제가 확실히 드러납니다. 중복 제출, 아예 나가지 않는 요청, 클라이언트는 보내는데 서버는 무시하는 필드, 상태 코드는 200인데 본문에는 에러가 담긴 응답, 재시도 폭주 같은 것들입니다.

## 상태는 직접 만들어서 확인하기

빈 상태, 에러 상태, 로딩 상태는 정적 리뷰로 추론하면 틀리기 쉽습니다. 개발하면서 가장 드물게 실행해 보는 경로이기 때문입니다. 추론하지 말고 그 상태를 직접 만들어서 돌려 봅니다.

- `execute_browser_javascript`로 원하는 상태를 곧바로 강제합니다.
- `browser_input`, `browser_click_element`, `browser_select_option`으로 실제 사용 흐름을 그대로 따라갑니다.
- 미디어 쿼리를 읽고 판단하는 대신 `browser_resize_window`로 브레이크포인트를 직접 시험합니다.

상태마다 캡처해서 시각 비평가에게 보여 줍니다.

## 목표와 비교하기

목업, 디자인 파일, 참조 구현처럼 시각적인 목표가 있다면, 그 목표와 구현 결과 캡처를 함께 시각 비평가에게 주고 간격, 굵기, 정렬, 색, 비율에서 구체적으로 무엇이 다른지 목록으로 받습니다. 목표가 없을 때는 `generate_image`로 목표 이미지를 만들 수 있는데, 이때는 생성한 이미지라는 점을 표시해 둡니다. 이렇게 하면 텍스트만 다루는 에이전트로서는 답할 수 없는 "제대로 보이는가"라는 질문이, 결과가 목록으로 나오는 비교 작업으로 바뀝니다.

## 이미지·문서·오디오를 증거로 다루기

Gemini는 이미지, PDF, Office 파일, 오디오를 그대로 읽을 수 있습니다. 그러니 사용자가 건넨 자료는 받았다고 확인만 하고 넘어갈 참고 맥락이 아니라 증거로 다룹니다. 버그 스크린샷은 그 자체로 재현 자료입니다. 디자인 목업은 비교 기준이 되는 사양입니다. 화이트보드 사진은 아키텍처 문서이고, 차트는 데이터입니다. 사용자가 에러 스크린샷을 붙여 넣으면 이미지에서 에러 내용을 직접 읽어 내고 그에 맞게 조치합니다. 다시 타이핑해 달라고 하면 손에 쥔 근거를 스스로 버리는 셈입니다.

작업의 기준이 되는 이미지가 있으면 그 이미지 자체를 비평가에게 넘깁니다. 직접 볼 수 있는 모델에게 이미지를 말로 풀어 설명해 봐야 아무 이유 없이 정보만 잃습니다.

## 브라우저 관찰과 코드 작업 병행하기

구현과 동작 확인을 함께 해야 하는 작업이라면, 구현이 진행되는 동안 에이전트 하나가 실행 중인 애플리케이션을 지켜보게 하고, 라운드마다 두 에이전트가 `send_message`로 서로 내용을 맞춥니다. 관찰 담당은 애플리케이션이 실제로 무엇을 하는지에 대해 직접 확인한 사실을 쥐고 있고, 구현 담당은 애플리케이션이 무엇을 해야 하는지를 바꿉니다.

두 역할은 섞지 않습니다. 관찰 담당이 코드를 고치기 시작하거나 구현 담당이 렌더링 결과를 짐작하기 시작하면, 애초에 역할을 나눈 이유인 독립성을 잃게 됩니다.

## 관찰할 수 없을 때

아키텍처 판단, 안전하게 실행시켜 볼 수 없는 경로를 두고 하는 보안 추론, 아직 돌아가지 않는 코드처럼, 실행해서 확인할 대상 자체가 없는 주장도 있습니다. 이런 주장은 3등급과 4등급에 머무르며, 텍스트를 놓고 하는 적대적 검토가 알맞은 도구가 되는 경우는 여기뿐입니다.

1. 주장을 서로 독립된 반박자들에게 보냅니다. 각자에게 반박을 목표로 하되, 확신이 서지 않으면 기본적으로 '반박됨'으로 판정하라고 지시합니다.
2. 주장이 틀릴 수 있는 방향이 여럿이면, 검증자마다 정확성, 보안, 성능, 재현성 가운데 서로 다른 관점을 하나씩 맡깁니다.
3. 과반수가 통과로 판정해야 인정합니다.
4. 끝까지 살아남은 주장도 등급을 함께 적어 가설로 보고합니다.

관찰할 수 없다고 결론 내리기 전에, 품이 적게 드는 하네스로 관찰 가능하게 만들 수 있는지부터 확인합니다. 임시 스크립트 하나, 테스트 하나, 쿼리 한 번 같은 것입니다. 코드가 아마 이렇게 동작할 거라며 에이전트 다섯이 토론하는 것보다 하네스를 만드는 쪽이 거의 언제나 비용이 덜 들고, 투표가 아니라 결과를 내놓습니다.
