# 모듈 04 - 실행 중 검증

## 목적

이 모듈은 실행 중이거나 렌더링된 표면이 있는 모든 것의 검증을 다룹니다. 애플리케이션, 웹 페이지, 3D 장면, 차트, 생성된 이미지, 조판된 문서 등입니다. 이는 `03-domain-checks.md`의 일반 원칙, 즉 자신의 추론을 거치지 않는 검증을 찾으라는 원칙이 한 분야에서 구체화된 것입니다. 소프트웨어에서 그 검증은 실제로 실행해 보고 들여다보는 것입니다.

## 먼저 도구 세트를 확인하기

이번 세션에 실제로 있는 도구를 기준으로 검증을 계획하고, 계획을 쓰기 전에 그 도구들을 확인합니다.

| 환경 | 브라우저 및 런타임 도구 |
| :--- | :--- |
| agy CLI | 없음. 2026-09-24 agy 1.2.9에서 얻은 도구 목록에는 `run_command`, `view_file`, `read_url_content`, `search_web`, `generate_image`와 서브에이전트 도구가 있었고 브라우저 도구는 없었습니다 |
| Antigravity 데스크톱 앱 | 브라우저 연동이 켜져 있을 때 `open_browser_url`, `capture_browser_screenshot`, `capture_browser_console_logs`, `browser_list_network_requests`, `browser_get_network_request`, `execute_browser_javascript`, `browser_click_element`, `browser_input`, `browser_select_option`, `browser_resize_window`, `read_browser_page`, `browser_subagent` |
| 둘 다, 플러그인 사용 시 | Chrome DevTools 플러그인을 설치하고 켜면 브라우저 제어가 `mcp_` 도구로 제공됩니다 |
| 둘 다, 언제나 | 파일로 작성해 `run_command`로 실행하는 Playwright 또는 Puppeteer 검증 하네스 |

기록된 데스크톱 앱 실행 하나에는 브라우저 도구가 전혀 없었습니다. 도구 세트는 `view_file`, `grep_search`, `list_dir`, `find_by_name`, `run_command`, `replace_file_content`, `write_to_file`, `schedule`, `manage_task`가 전부였습니다. 에이전트는 그래도 `run_command`로 Playwright 하네스를 만들어 스크린샷을 찍었고, 이는 옳은 판단이었습니다. 문제는 하네스가 아니라 그것이 무엇을 확인했느냐였으며, 그 부분은 `06-perceptual-gates.md`에서 다룹니다.

## 먼저 관찰하기

렌더링되거나 실행 중인 표면이 있는 모든 것에 대한 기본 방식입니다. 텍스트 리뷰는 “코드가 맞아 보이는가”에 답합니다. 중요한 질문은 “그것이 올바른 일을 하는가”이며, 이는 직접 가서 볼 수 있습니다.

1. 실행시키기: `restart_dev_server` 후 `open_browser_url`, 또는 `run_command`로 서버를 띄우고 하네스에서 엽니다.
2. 변경 전 기준선 확보: 스크린샷과 콘솔 로그.
3. 변경하기.
4. 변경 후 같은 뷰포트에서 같은 표면을 다시 확보하기.
5. 두 결과를 `gravitas-visual-critic`에 넘겨 무엇이 다른지, 그 차이가 의도한 것인지 설명하게 합니다. 이 에이전트는 코드를 보지 않았고 아무것도 편집할 수 없습니다.

`view_file`은 이미지를 이미지로 모델에 넘깁니다. agy 1.2.9에서 비평가는 테스트 PNG를 정확히 묘사했고, 질문받았지만 존재하지 않는 도형도 없다고 답했습니다. 보는 비평가는 코드 리뷰가 볼 수 없는 종류의 결함을 잡아냅니다. 겹치는 요소, 컨테이너에 잘린 텍스트, 명암비 미달 색상, 화면 밖에 렌더링된 요소, 400 px에서 무너지는 레이아웃, 끝나지 않는 스피너, DOM에는 있지만 사람 눈에는 보이지 않는 컨트롤 등입니다.

매번 콘솔을 읽습니다. 정상적으로 렌더링된 컴포넌트 안에서 발생한 런타임 예외는 스크린샷만 보는 검증이 가장 자주 놓치는 결함입니다.

## 계약 검증

API 호출, fetch, 폼 제출, 요청에 대해서는 클라이언트와 핸들러를 읽고 둘이 맞는지 추론하는 대신, 그 경로를 실제로 실행하고 오가는 트래픽을 읽습니다.

- `browser_list_network_requests`는 무엇이, 어떤 순서로, 몇 번 발생했는지 보여 줍니다.
- `browser_get_network_request`는 메서드, 헤더, 페이로드, 상태 코드, 응답 본문을 보여 줍니다.
- 브라우저 도구가 없으면 하네스로 같은 트래픽을 기록하거나, `run_command`에서 `curl`로 엔드포인트를 직접 호출합니다.

이렇게 하면 텍스트 리뷰로는 추측만 할 수 있던 것이 결판납니다. 이중 제출, 발생하지 않는 요청, 클라이언트는 보내는데 서버는 무시하는 필드, 오류 본문을 담은 200 응답, 재시도 폭주 등입니다.

## 상태를 실제로 구동하기

정적 리뷰는 빈 상태, 오류 상태, 로딩 상태를 추론하지만 자주 틀립니다. 이런 경로는 개발 중에 가장 적게 실행되기 때문입니다. 대신 실제로 구동합니다.

- `execute_browser_javascript`로 상태를 직접 만듭니다.
- `browser_input`, `browser_click_element`, `browser_select_option`으로 실제 흐름을 따라갑니다.
- `browser_resize_window`로 미디어 쿼리를 읽는 대신 중단점을 시험합니다.

각 상태를 캡처해 시각 비평가에게 보여 줍니다.

## 목표와의 차이 비교

목업, 디자인 파일, 참조 구현처럼 시각적 사양이 있으면, 목표와 구현 캡처를 시각 비평가에게 함께 주고 간격, 굵기, 정렬, 색상, 비율의 구체적인 차이를 나열하게 합니다. 목표가 없으면 `generate_image`로 만들고 생성된 것임을 표시합니다. 이렇게 하면 텍스트 에이전트는 답할 수 없는 “제대로 보이는가”가 결과 목록이 있는 비교로 바뀝니다.

## 이미지, 문서, 오디오는 증거다

Gemini는 이미지, PDF, Office 파일, 오디오를 그대로 읽습니다. 따라서 사용자가 준 것은 받았다고 알리기만 할 맥락이 아니라 증거로 다룹니다. 버그 스크린샷은 재현 그 자체입니다. 디자인 목업은 비교할 사양입니다. 화이트보드 사진은 아키텍처 문서입니다. 차트는 데이터입니다. 사용자가 오류 스크린샷을 붙이면 이미지에서 오류를 읽어 내고 처리합니다. 다시 입력해 달라고 하면 그 단서를 버리는 셈입니다.

작업에 시각적 단서가 있으면 이미지 자체를 비평가에게 넘깁니다. 이미지를 볼 수 있는 모델에게 이미지를 말로 설명하는 것은 이유 없이 정보를 버리는 일입니다.

## 브라우저와 코드의 병행

작업이 구현과 동작 모두에 걸쳐 있을 때는, 한 에이전트가 실행 중인 애플리케이션을 관찰하는 동안 구현이 진행되고, 둘은 매 라운드 `send_message`로 맞춰 봅니다. 관찰자는 애플리케이션이 실제로 무엇을 하는지에 대한 사실을 쥐고, 구현자는 그것이 무엇을 해야 하는지를 바꿉니다.

역할은 분리해 둡니다. 코드를 편집하기 시작한 관찰자나 렌더링 결과를 추측하기 시작한 구현자는, 이 분업에 가치를 주던 독립성을 잃은 것입니다.

## 관찰이 불가능할 때

실행 표면이 없는 주장도 있습니다. 아키텍처 판단, 안전하게 촉발할 수 없는 경로에 대한 보안 추론, 아직 실행되지 않는 코드 등입니다. 이런 주장은 3등급과 4등급에 머물며, 오직 여기서만 텍스트에 대한 적대적 검토가 알맞은 도구입니다.

1. 주장을 독립적인 반박자들에게 보내고, 각자 반박을 시도하되 확신이 없으면 반박된 것으로 판정하게 합니다.
2. 주장이 여러 방식으로 틀릴 수 있으면 검증자마다 다른 관점을 줍니다. 정확성, 보안, 성능, 재현성입니다.
3. 과반이 통과시켜야 성립합니다.
4. 살아남은 주장은 그 등급과 함께 가설로 보고합니다.

주장을 관찰 불가능하다고 받아들이기 전에, 저렴한 하네스로 관찰 가능하게 만들 수 있는지 확인합니다. 임시 스크립트 하나, 테스트 하나, 쿼리 한 번입니다. 그것을 만드는 편이 코드가 아마 무엇을 할지에 대해 다섯 에이전트가 논쟁하는 것보다 거의 언제나 싸고, 표가 아니라 결과를 냅니다.
