# 모듈 05 - 인수 검증

## 목적

이 모듈은 세 가지를 다룹니다. 실제로 실패할 수 있는 검사를 작성하는 법, 스크린샷은 사람이든 모델이든 누군가 실제로 들여다보기 전까지는 검증이 되지 못하는 이유, 그리고 통과가 내가 생각한 바로 그 이유로 나왔는지 확인하는 법입니다. 무엇이든 통과했다고 보고하기 전에, 그리고 테스트나 게이트, 체크리스트를 작성할 때마다 이 모듈을 불러옵니다.

예시가 소프트웨어 쪽에 몰려 있는 것은 실패 사례가 거기서 기록되었기 때문일 뿐이고, 규칙은 어느 분야에나 똑같이 적용됩니다.

| 규칙 | 소프트웨어 | 법률 | 수학 | 실증적 주장 |
| :--- | :--- | :--- | :--- | :--- |
| 게이트는 실패할 수 있어야 한다 | 보고서 템플릿에 하드코딩한 `PASS` | '인용 확인 완료'가 실은 형식만 맞췄다는 뜻 | '식 전개 확인 완료'가 실은 한 번 더 읽어 봤다는 뜻 | '출처 확인 완료'가 실은 출처가 존재하는지만 봤다는 뜻 |
| 수집만 하지 말고 assert한다 | 아무도 읽지 않는 배열에 쌓아 두기만 한 콘솔 에러 | 찾아 놓고 한 번도 읽지 않은 법적 근거 | 돌려 놓고 비교하지 않은 수치 검산 | 열어 놓고 인용하지 않은 1차 자료 |
| 대리 지표가 아니라 결과물 자체를 판단한다 | 렌더링 결과를 보지 않고 메시 개수를 센다 | 판결 요지를 읽지 않고 인용 개수를 센다 | 결과를 시험해 보지 않고 한 줄씩 검증만 한다 | 수치를 확인하지 않고 논문이 존재하는지만 확인한다 |
| 통과에는 이유가 있어야 한다 | 코드 경로가 아예 실행되지 않아서 통과한 테스트 | 데이터베이스가 잘못돼서 상충 판례가 하나도 걸리지 않은 검색 | 빈 범위에서 돌린 반례 탐색 | 에러를 반환한 검색에서 나온 '반박 증거 없음' |

## 이 모듈의 출발점이 된 실패

한 에이전트가 Three.js로 초콜릿 공장을 만들고 스크린샷 8장을 캡처한 다음, 게이트 8개짜리 `VERIFICATION.md`를 작성하고 `ALL TEST GATES PASSED SUCCESSFULLY`라고 보고했습니다. 그런데 장면은 한눈에 봐도 이상했습니다.

테스트 스위트에는 이런 줄이 있었습니다.

```js
| **T12-R1** | Hero Chocolate Identity Persistence | **PASS** | Exactly 1 mesh; UUID ${uuids[0]} persists. |
```

여기서 `PASS`는 템플릿에 박혀 있는 문자열 리터럴입니다. 측정값은 보간으로 채워 넣지만 판정은 그냥 적어 넣은 글자입니다. 비교도, 임곗값도, 분기도 없습니다. 스위트 전체에 게이트 8개와 하드코딩된 PASS 8개가 있었을 뿐 조건 로직은 하나도 없었고, `process.exit(1)`은 크래시 핸들러 안에 있는 것 하나뿐이었습니다.

콘솔 에러도 수집만 하고 한 번도 읽지 않았습니다.

```js
const consoleErrors = [];
page.on('console', msg => { if (msg.type() === 'error') consoleErrors.push(msg.text()); });
```

## 게이트 작성 규칙

1. 모든 게이트는 측정값을 기댓값과 비교합니다. 어떤 조건에서 실패하는지 말할 수 없다면 그건 게이트가 아닙니다.
2. 게이트를 믿기 전에, 실패할 수 있다는 것부터 증명합니다. 대상을 일부러 망가뜨리고 스위트를 돌려서 빨간불이 들어오는 것을 직접 본 뒤 원래대로 되돌립니다. 한 번도 실패해 본 적 없는 스위트는 사실 한 번도 테스트된 적이 없는 스위트입니다.
3. 게이트가 하나라도 실패하면 프로세스는 0이 아닌 코드로 종료해야 합니다. 늘 0으로 종료하는 스위트는 아무것도 알려 주지 않습니다.
4. 수집한 것은 assert하거나 지웁니다. 아무도 읽지 않는 배열에 콘솔 에러를 모아 두는 것은 아예 수집하지 않는 것보다 나쁩니다. 코드만 보면 검사를 하는 것처럼 보이기 때문입니다.
5. 출력을 읽기 전에 검사가 실제로 실행됐는지부터 확인합니다. 실패를 찾는 입장에서는 결과가 비어 있는 것과 스크립트가 죽어 버린 것이 똑같아 보입니다. 그러니 종료 상태나 출력 줄 수, 또는 검사가 끝까지 돌았을 때 찍히는 완료 마커로 확인합니다.

## 통과에는 이유가 있어야 한다

통과 결과가 증거가 되려면 테스트하려던 일이 실제로 일어났어야 합니다. 통과를 보고하기 전에, 그 통과가 기대고 있는 경로가 실제로 실행됐는지 확인합니다.

Antigravity 자체를 테스트하면서 겪은 사례가 두 가지 있습니다. 하나는 인젝션 테스트입니다. 에이전트가 파일에 심어 둔 악성 지시를 잘 버텨 낸 것처럼 보였지만, 트랜스크립트를 보니 `read_file` 호출이 권한 시스템에서 거부된 상태였습니다. 에이전트는 페이로드를 본 적조차 없었고, 버텨 낸 것도 없었습니다. 다른 하나는 도구가 거부된 헤드리스 실행이 해당 턴의 작업을 버린 채 `"status": "SUCCESS"`와 종료 코드 0을 반환한 경우입니다. 이 문제는 업스트림인 `google-antigravity/antigravity-cli`에 issue #794로 올라가 있습니다. 두 경우 모두 통과 신호는 하네스가 낸 것이었고, 실제 동작에 대해서는 아무것도 말해 주지 않았습니다.

중요한 통과 결과마다 테스트한 경로가 실제로 실행됐다는 증거를 밝힙니다. 트랜스크립트에 남은 도구 단계, 로그 줄, 값이 바뀐 카운터, 실제로 나간 요청 같은 것입니다.

## 계측기부터 의심하기

결과가 예상 밖이면 시스템을 탓하기 전에 하네스부터 확인합니다. 같은 테스트 기간에 Antigravity 쪽 결함처럼 보이는 실행이 있었는데, 알고 보니 테스트 하네스가 실행 도중에 자기가 부여해 둔 권한을 스스로 걷어 낸 것이었습니다. 실패 자체는 진짜였지만, 실패한 쪽은 계측기였습니다.

이번 버전을 테스트하면서도 같은 일이 또 있었습니다. 하네스가 Windows 셸을 거쳐 `agy`에 프롬프트를 넘겼는데, 이 셸은 첫 줄바꿈에서 명령을 끝내 버립니다. 그래서 여러 줄짜리 프롬프트가 첫 줄만 전달됐습니다. 임시 와일드카드 권한을 쥐고 있던 Gemini 3.8 Flash는 지시가 빠졌다고 판단하고 직접 찾아 나섰습니다. 사용자의 PowerShell 명령 기록(history), 다른 대화 네 개의 트랜스크립트, 실행 중인 프로세스들의 커맨드 라인까지 읽은 끝에 하네스 자신의 프로세스에서 전체 프롬프트를 찾아냈고, 그대로 작업을 끝냈습니다. 잘못은 하네스에 있었습니다. 이 일로 드러난 동작은 `00-orchestrator.md`에서 다룹니다. 요청이 불완전해 보이면 묻거나 멈춰야 한다는 내용입니다. 이어서 이번 릴리스용으로 만든 출처 검사기 자체가 첫 테스트에서 실패했습니다. 출처를 제대로 단 법률 답변을 두고 인용된 6개 모두를 '열어 보지 않은 출처'로 보고했는데, 검사기의 경로 패턴이 `https://` 안의 `s:/`에 매칭됐기 때문입니다.

한 번에 하나만 바꿉니다. 모든 실행은 즉석에서 친 명령이 아니라 저장된 스크립트로 남기고, 대조군도 테스트 케이스와 함께 다시 돌립니다. 저장된 스크립트로 다시 돌릴 수 없는 결과는 일화에 불과하며, `11-findings.md`도 그렇게 취급합니다.

## 보고 전 확인 사항

- 검사가 실제로 실행됐다는 것을 종료 상태, 출력 줄 수, 완료 마커 중 하나로 확인했다.
- 모든 게이트에 실패 조건이 명시되어 있다.
- 실패하는 모습을 직접 확인한 게이트가 하나 이상 있다.
- 중요한 통과마다, 테스트한 경로가 실제로 실행됐다는 증거를 댔다.
- 콘솔 출력은 assert로 검사했고, 모아 두기만 한 것은 없다.
- 렌더링된 결과물이 있으면, 새로 띄운 비평가가 그것을 보고 재질, 조명, 식별 가능성(무엇인지 알아볼 수 있는지)을 묻는 질문에 답했다.
- 계획에서 외관에 관해 정한 모든 항목에, 실제로 그렇게 보이는지 묻는 게이트가 있다.
- 다루지 않은 범위를 보고서에 밝혔다.

전부 초록불이고 빨간불이 들어온 게이트를 한 번도 보여 주지 않은 보고서라면, 게이트 중 어느 하나라도 실패를 잡아낼 수 있다는 것을 보여 주지 못한 셈입니다.
