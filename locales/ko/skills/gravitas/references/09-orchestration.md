# 모듈 09 - 조율

## 목적

이 모듈은 팬아웃을 짜는 방법을 다룹니다. 결과를 기다릴 때와 기다리지 않을 때, 어떤 상황에 어떤 패턴이 맞는지, 그리고 원장으로 개수와 중복 제거를 정확히 유지하는 방법입니다. 표준 규모 이상에서 불러옵니다. 각 패턴은 해결하는 문제, 구조, 막는 실패를 밝히며, 패턴들은 자유롭게 조합할 수 있습니다.

패턴은 분야를 가리지 않습니다. 탐색자는 작업 목록에서 한 종류의 결함을 찾으며, 작업 목록은 파일일 수도, 조문일 수도, 논문일 수도, 장부의 줄일 수도 있습니다. 다중 방식 탐색은 여러 각도로 동시에 찾으며, 코드베이스에서는 디렉터리, 호출 그래프, 렌더링 결과를, 문헌 검토에서는 인용 관계, 키워드, 저자, 재현에 실패한 연구를 뜻합니다.

## 패턴 고르기

| 상황 | 패턴 |
| :--- | :--- |
| 독립적인 검증이 있다 | 관찰 우선 검증(`04-runtime-verification.md`) |
| 문제가 몇 개인지 모른다 | 마를 때까지 반복 |
| 한 각도로는 놓친다 | 다중 방식 탐색 |
| 해의 공간이 넓다 | 심사단 |
| 발견이 그럴듯하지만 틀렸을 수 있다 | 적대적 반박 |
| 발견이 여러 방식으로 틀릴 수 있다 | 관점을 달리한 검증 |
| 무언가 놓쳤을 수 있다 | 완결성 비평 |
| 항목마다 비용 차이가 크다 | 단계적 승격 |
| 수백 개 항목을 정확히 세야 한다 | 스크립트 조율(`13-platform.md`) |
| 수정을 초록불까지 몰고 가야 한다 | 수렴형 루프(`10-iteration.md`) |
| 출력에 필요한 것이 교정이 아니라 다듬기다 | 경사형 루프(`10-iteration.md`) |

## 먼저 정찰하고, 단계마다 팬아웃 하나

먼저 자신의 도구로 작업 목록을 찾습니다. 파일을 나열하고, 검색을 실행하고, 조문 색인을 가져오고, 목차를 읽습니다. 그런 다음 찾은 것에 대해 팬아웃합니다. 여러 단계의 작업은 단계마다 팬아웃 하나(이해, 설계, 구현, 검토)를 차례로 실행하고, 부모는 각 결과를 읽은 뒤 다음을 계획합니다. 처음에 계획한 거대한 팬아웃 하나는 아무것도 배우기 전에 쓴 작업 목록에 묶입니다.

## 기본은 파이프라인

발견은 생기는 즉시 검증합니다. 일찍 돌아온 탐색자의 발견은 느린 탐색자가 아직 일하는 동안 반박자 앞에 놓여야 합니다.

전체가 모이기를 기다리는 것은 다음 단계가 한꺼번에 모두를 필요로 할 때뿐입니다. 비싼 검증 전에 모든 탐색자의 결과에서 중복을 없앨 때, 합계가 0이어서 일찍 끝낼 때, 발견끼리 비교하는 단계일 때입니다. 펼치기, 거르기, 형식 바꾸기에는 기다림이 필요 없으니 항목마다 처리합니다. 탐색자 다섯이 돌고 가장 느린 것이 가장 빠른 것의 세 배가 걸린다면, 아무것도 필요로 하지 않는 기다림은 빠른 결과를 실행 시간의 3분의 2 동안 놀게 합니다.

## 원장

개수 세기, 중복 제거, 투표 집계는 장부 정리이며, 장부 정리는 코드의 몫입니다. 세 라운드에 걸친 발견 마흔 개를 머릿속으로 따라가는 모델은 수를 틀리고, 이미 기각한 발견을 다시 검증하고, 루프를 너무 이르거나 늦게 멈춥니다. `scripts/ledger.py`는 그 상태를 JSON 파일에 보관해 결정을 결정적으로 만듭니다. Python 3.8 이상만 있으면 됩니다.

설치된 플러그인 안의 전체 경로 `<home>/.gemini/config/plugins/gravitas/skills/gravitas/scripts/ledger.py`로 실행하고, 원장 파일은 실행이 끝나도 남도록 워크스페이스나 결과물 디렉터리에 둡니다. 아래 예에서는 경로를 줄였습니다.

```bash
python scripts/ledger.py init  run.ledger.json --scale full
python scripts/ledger.py add   run.ledger.json finder-security.json --round 1 --by gravitas-finder
python scripts/ledger.py verdict run.ledger.json <key> --by gravitas-refuter --refuted no \
    --tier executed --source "pytest tests/test_session.py::test_logout -> 1 failed"
python scripts/ledger.py verdicts run.ledger.json refuter-verdicts.json --by gravitas-refuter
python scripts/ledger.py child run.ledger.json --id <conversation-id> --agent gravitas-finder --status denied \
    --note "read_file denied on src/auth"
python scripts/ledger.py close-round run.ledger.json --round 1
python scripts/ledger.py report run.ledger.json
```

원장이 강제하는 것:

- 등급이 `observed`, `executed`, `read`인데 `source`가 비어 있는 기록은 `inferred`로 강등되고, 내용을 전혀 인용하지 않은 `source`를 가진 `read` 기록도 강등됩니다. 세 단어 이상이나 열두 글자 이상의 인용이 필요하며, 따옴표로 감싼 경로는 인용이 아닙니다. 기록은 발견과 판정 스키마로 검사되고, 형식이 잘못된 기록은 이유와 함께 거부됩니다. `01-evidence.md`의 출처 규칙이 원장이 모든 기록에 대해 실행하는 검사가 됩니다.
- 새 기록은 반박자가 기각한 것까지 포함해 지금까지 추가된 모든 기록과 중복을 대조합니다. 살아남은 것하고만 대조하면 기각된 발견이 매 라운드 돌아와 루프가 수렴하지 않습니다.
- 같은 위치의 두 기록은 주장의 단어가 0.25 이상 겹치면 자동으로 합쳐지고, 0.10부터는 중복 가능성으로 표시됩니다. 같은 파일에서 5줄 이내에 있는 기록은 표현이 거의 같을 때(0.8)만 자동으로 합쳐지고, 그렇지 않으면 표시만 됩니다. 몇 줄 떨어진 서로 다른 결함은 비슷한 말로 적히기 쉽기 때문입니다. 한 실제 감사에서 진짜 중복은 0.13~0.69, 같은 줄의 서로 다른 결함은 0.02~0.15였고, 자동 병합은 기록 22개를 15개로 줄이면서 잘못 합친 것이 없었습니다. 표시된 것은 `ledger.py merge KEEP DUP`로 정하며, 표도 함께 옮겨집니다.
- 발견은 집계된 표 가운데 반박하지 않은 표가 과반일 때만 살아남으며, 필요한 표 수는 규모를 따릅니다. 표준은 1표, 전체와 망라는 3표입니다. 표에도 발견과 같은 출처 규칙이 적용되어, 강등된 표나 상태가 `blocked`인 표는 기록되지만 집계되지 않습니다. 빠른 규모에서는 표를 받지 않으므로 보고서는 발견을 검증되지 않은 것으로 나열합니다.
- `close-round`는 새 발견을 세고, 마른 라운드 카운터를 올리고, `CONTINUE` 또는 `STOP`을 이유와 함께 출력합니다. 마른 라운드 수에 도달했는지, 라운드 상한에 도달했는지입니다.
- `report`는 살아남은 발견을 심각도순으로 등급과 출처와 함께 나열하고, 이어서 반박된 기록, 보류 기록, 강등된 기록, 상태가 `done`이 아닌 모든 하위 에이전트와 `blocked`를 반환한 모든 탐색자, 마지막으로 상한을 나열합니다.

원장 파일은 마지막 턴을 잃어도 남으므로 사용자가 찾을 수 있는 곳에 둡니다. Python이 없다면 같은 항목을 계획 결과물의 표로 관리하고, 같은 규칙을 손으로 적용하고, 보고서에 원장을 수작업으로 관리했다고 밝힙니다.

## 마를 때까지 반복

문제가 몇 개인지 모를 때 씁니다. 버그, 보안 발견, 죽은 코드, 경계 사례, 문서 묶음 속 모순입니다. 탐색자를 한 차례 보내고, 그 기록을 원장에 더하고, 새 기록을 검증하고, 라운드를 닫습니다. 규모가 정한 횟수만큼 마른 라운드가 이어지면 멈춥니다. 정해진 횟수로 끝나는 루프가 꼬리 중간에서 멈춰 쉬운 발견만 보고하고 나머지를 놓치는 것을 막습니다.

## 다중 방식 탐색

한 가지 탐색 각도로는 모든 것을 볼 수 없고, 무엇을 놓칠지는 각도에 달려 있으므로 여러 각도를 동시에 돌립니다. 탐색자는 디렉터리, 심볼, 호출 그래프, 최근 변경, 테스트 커버리지, 오류 문자열, 렌더링 결과로 찾습니다. 이 플랫폼에서 가장 중요한 것은 시각 각도입니다. 모든 경로를 캡처와 함께 훑으면 텍스트 검색으로는 질의할 수 없는 결함을 찾습니다. 그 결함은 문자열이 아니라 렌더링 결과이기 때문입니다. 함수 이름으로 검색해서는 그것을 호출하는 동적 디스패치를 결코 찾지 못하는 것 같은 단일 각도의 사각지대를 막습니다.

## 심사단

해의 공간이 넓을 때 처음 떠오른 그럴듯한 답이 최선인 경우는 드뭅니다. 서로 다른 출발점에서 독립적인 시도를 여러 개 만듭니다. 작동하는 가장 단순한 것, 위험 우선, 성능 우선, 사용자 우선입니다. 어느 것도 작성하지 않은 새 심사자가 점수를 매깁니다. 이긴 것을 바탕으로 삼고 나머지의 가장 강한 아이디어를 접목합니다. 한 번 시도한 뒤 다듬기, 즉 첫 틀에 갇혀 그 안에서만 반복하는 것을 막습니다.

## 적대적 반박

각 발견을 독립적인 반박자들에게 보내 반박을 시도하고 확신이 없으면 반박된 것으로 판정하게 합니다. 과반이 반박하면 버립니다. 전체 규모에서는 반박자 3명을 씁니다. “이것을 반박하라”는 검토를 부르고, “이것이 맞는가”는 동의를 부릅니다. 그럴듯하지만 틀린 발견이 글의 힘으로 살아남는 것을 막습니다.

## 관점을 달리한 검증

발견이 여러 방식으로 틀릴 수 있을 때는 똑같은 반박자를 보내는 대신 검증자마다 다른 관점을 줍니다. 정확성, 보안, 성능, 재현 여부입니다. 과반을 요구합니다. 같은 질문을 던지는 세 에이전트는 하나의 사각지대를 공유하고, 그것을 합의라고 부릅니다.

## 완결성 비평

보고하기 전마다 실행합니다. `gravitas-completeness-critic`은 원장과 작업 목록을 읽고 한 가지 질문, 무엇이 빠졌는지에 답합니다. 어떤 각도가 탐색되지 않았는지, 어떤 주장이 검증되지 않았는지, 어떤 파일이 열리지 않았는지, 어떤 상태가 실행되지 않았는지, 어떤 경로가 렌더링되지 않았는지, 어떤 하위 에이전트가 실패했는지. 지목된 것이 다음 라운드가 됩니다. 자신만만한 부분적 답, 즉 철저해 보이는 감사가 틀리는 가장 흔한 방식을 막습니다.

## 단계적 승격

대부분의 항목이 싸고 일부만 비쌀 때 모든 곳에 비싼 값을 치르면 예산 대부분이 낭비됩니다. 모든 항목에 `flash_lite`로 한 번 훑고, 신호가 걸린 것만 승격합니다. 양방향의 개수를 기록합니다. 승격률이 0이나 1에 가깝다면 작업이 균일해서가 아니라 신호의 보정이 어긋난 것입니다.

## 안티패턴

- 추측한 작업 목록에 대해 팬아웃하기.
- 하류에서 발견을 비교하는 단계가 없는데도 모든 탐색자를 기다린 뒤에야 검증을 시작하기.
- 무언가가 맞는지 묻는, 확인의 틀을 쓴 검증.
- 지금까지 본 모든 것이 아니라 살아남은 것하고만 중복을 대조하기.
- 조용한 상한: 보고서에 밝히지 않은 표본 추출, 상위 N개, 조기 중단.
- 실행 중인 시스템을 직접 볼 수 있는데도 소스로부터 추론하기.
