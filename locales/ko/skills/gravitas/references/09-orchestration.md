# 모듈 09 - 오케스트레이션

## 목적

팬아웃을 어떻게 짤지 다루는 모듈입니다. 결과를 기다려야 할 때와 기다리지 말아야 할 때, 상황별로 맞는 패턴, 그리고 원장(ledger)으로 개수와 중복 제거를 정확하게 관리하는 방법을 설명합니다. standard 규모 이상에서 불러옵니다. 패턴마다 어떤 문제를 풀고, 어떻게 구성되며, 어떤 실패를 막는지 적어 두었습니다. 패턴끼리는 자유롭게 조합해도 됩니다.

이 패턴들은 특정 분야에 매여 있지 않습니다. 탐색자(finder) 하나는 결함의 한 가지 차원만 맡아 작업 목록 전체를 훑는데, 작업 목록은 파일일 수도 있고 법 조문, 논문, 장부의 각 행일 수도 있습니다. 다각도 탐색은 여러 각도에서 동시에 찾는 방식입니다. 코드베이스라면 디렉터리, 호출 그래프, 렌더링 결과로 찾는다는 뜻이고, 문헌 리뷰라면 인용 그래프, 키워드, 저자, 재현에 실패한 연구로 찾는다는 뜻입니다.

## 패턴 고르기

| 상황 | 패턴 |
| :--- | :--- |
| 독립적으로 확인할 방법이 있다 | 관찰이 먼저(observe-first verification), `04-runtime-verification.md` 참고 |
| 문제가 몇 개나 있는지 모른다 | 더 나오지 않을 때까지 반복 |
| 한 각도로만 찾으면 놓치는 것이 생긴다 | 다각도 탐색 |
| 가능한 해법의 폭이 넓다 | 심사단 |
| 그럴듯하지만 틀린 발견일 수 있다 | 적대적 반박 |
| 발견이 틀릴 수 있는 경우가 여러 가지다 | 다관점 검증 |
| 빠뜨린 것이 있을 수 있다 | 완결성 비평가 |
| 항목마다 드는 비용 차이가 크다 | 단계적 에스컬레이션 |
| 항목이 수백 개이고 개수를 정확히 맞춰야 한다 | 스크립트로 오케스트레이션하기(scripted orchestration), `13-platform.md` 참고 |
| 수정을 green이 될 때까지 밀고 가야 한다 | 수렴형 루프(convergent loop), `10-iteration.md` 참고 |
| 결과물을 고칠 게 아니라 다듬어야 한다 | 점진 개선형 루프(gradient loop), `10-iteration.md` 참고 |

## 먼저 정찰하고, 팬아웃은 단계마다 한 번씩

작업 목록은 먼저 요청이 지정한 범위 안에서 찾아냅니다. 파일 목록을 뽑고, 검색을 돌리고, 법령의 색인을 가져오고, 목차를 읽습니다. 파일은 `list_dir`, `find_by_name`, `grep_search`가 있으면 그것으로 찾습니다. agy CLI의 메인 에이전트에는 1.2.7부터 이 도구들이 없으므로(`13-platform.md`), 폴더의 절대 경로를 주고 `gravitas-scout`에게 맡깁니다. 셸 명령으로 목록을 보는 것은 대안이 되지 못합니다. 상시 규칙은 맥락을 찾으려는 목록 보기를 금지하고, 기본 설정의 헤드리스 실행에서는 명령이 거부되어 그 턴의 작업이 모두 사라집니다. 팬아웃은 그렇게 찾아낸 것을 대상으로 합니다. 단계가 여러 개인 작업은 이해, 설계, 구현, 리뷰 단계마다 팬아웃을 한 번씩 차례로 실행하고, 부모 에이전트는 각 단계의 결과를 읽고 나서 다음 단계를 계획합니다. 처음부터 거대한 팬아웃 하나를 계획해 버리면, 아직 아무것도 알아내지 못한 상태에서 쓴 작업 목록에 발이 묶입니다.

## 기본은 파이프라인

발견은 나오는 즉시 검증합니다. 먼저 끝난 탐색자의 발견은 느린 탐색자들이 아직 작업하는 동안 이미 반박자(refuter)에게 넘어가 있어야 합니다.

결과 전체를 기다리는 것은 다음 단계가 전부를 한꺼번에 필요로 할 때뿐입니다. 비용이 큰 검증에 앞서 모든 탐색자의 결과를 모아 중복을 제거할 때, 합계가 0이면 바로 끝낼 때, 발견끼리 서로 비교하는 프롬프트를 쓰는 단계일 때가 그렇습니다. 평탄화, 필터링, 형식 변환은 기다릴 필요가 없으니 항목 단위로 처리합니다. 탐색자 다섯을 돌리는데 가장 느린 것이 가장 빠른 것보다 세 배 오래 걸린다면, 어느 단계도 필요로 하지 않는 대기 때문에 빠른 결과가 전체 실행 시간의 3분의 2 동안 그냥 놀게 됩니다.

## 원장

개수 세기, 중복 제거, 투표 집계는 모두 장부 정리이고, 장부 정리는 코드가 맡아야 합니다. 세 라운드에 걸쳐 나온 발견 40개를 머릿속으로만 추적하는 모델은 개수를 놓치고, 이미 기각한 발견을 다시 검증하며, 루프를 너무 일찍 혹은 너무 늦게 멈춥니다. `scripts/ledger.py`는 이 상태를 JSON 파일에 저장해 두고 판단을 결정론적으로 처리합니다. Python 3.8 이상만 있으면 되고, 그 밖에 필요한 것은 없습니다.

실행할 때는 설치된 플러그인 안의 전체 경로 `<home>/.gemini/config/plugins/gravitas/skills/gravitas/scripts/ledger.py`를 씁니다. 원장 파일은 실행이 끝난 뒤에도 남도록 워크스페이스나 아티팩트 디렉터리에 둡니다. 아래 예시는 경로를 줄여 적었습니다.

```bash
python scripts/ledger.py init  run.ledger.json --scale full
python scripts/ledger.py add   run.ledger.json finder-security.json --round 1 --by gravitas-finder
python scripts/ledger.py verdict run.ledger.json <key> --by gravitas-refuter --refuted no \
    --tier executed --source "pytest tests/test_session.py::test_logout -> 1 failed"
python scripts/ledger.py verdicts run.ledger.json refuter-verdicts.json --by gravitas-refuter
python scripts/ledger.py child run.ledger.json --id <conversation-id> --agent gravitas-finder --status denied \
    --note "read_file denied on src/auth"
python scripts/ledger.py close-round run.ledger.json --round 1
python scripts/ledger.py report run.ledger.json
```

원장이 강제하는 규칙은 다음과 같습니다.

- 등급이 `observed`, `executed`, `read`인데 `source`가 비어 있는 기록은 `inferred`로 강등됩니다. 출처에 내용을 하나도 인용하지 않은 `read` 기록도 마찬가지입니다. 인용은 세 단어 이상이거나 12자 이상이어야 하고, 경로를 따옴표로 감싼 것은 인용으로 치지 않습니다. 기록은 발견(finding) 스키마와 판정(verdict) 스키마로 검사하며, 형식이 맞지 않는 기록은 이유와 함께 거부합니다. `01-evidence.md`의 출처 규칙은 원장이 모든 기록마다 실행하는 검사가 됩니다.
- 새 기록은 지금까지 추가된 모든 기록과 대조해 중복을 걸러 냅니다. 반박자가 기각한 기록도 대조 대상에 들어갑니다. 살아남은 기록하고만 대조하면 기각된 발견이 라운드마다 다시 올라오고, 루프는 끝내 수렴하지 않습니다.
- 위치가 같은 두 기록은 주장에 쓰인 단어 중 0.25 이상이 겹치면 자동으로 병합되고, 0.10부터는 중복 후보로 표시됩니다. 같은 파일 안에서 5줄 이내로 떨어진 기록은 표현이 거의 똑같을 때(0.8)만 병합되고, 그렇지 않으면 표시만 됩니다. 몇 줄 떨어진 서로 다른 결함이 비슷한 말로 기술되는 일이 잦기 때문입니다. 실제 감사 한 건에서 진짜 중복은 0.13~0.69, 같은 줄에 있는 서로 다른 결함은 0.02~0.15가 나왔고, 자동 병합으로 기록 22개가 15개로 줄었는데 잘못 병합된 것은 하나도 없었습니다. 중복 후보로 표시된 기록은 병합 여부를 판단해 `ledger.py merge KEEP DUP`로 처리합니다. 이 명령은 투표도 함께 옮깁니다.
- 발견이 살아남으려면 집계 대상 투표 가운데 반박하지 않은 투표가 과반이어야 합니다. 필요한 투표 수는 규모에 따라 정해지며, standard에서는 1표, full과 exhaustive에서는 3표입니다. 투표에도 발견과 똑같은 출처 규칙이 적용되므로, 강등된 투표나 상태가 `blocked`인 투표는 기록은 되지만 집계에서는 빠집니다. quick 규모에서는 투표를 하지 않으므로, 보고서에는 발견이 미검증 상태로 나열됩니다.
- `close-round`는 새 발견 수를 세고, 새 발견 없는 라운드(dry round) 카운터를 올린 뒤 `CONTINUE`나 `STOP`을 이유와 함께 출력합니다. 이유는 새 발견 없는 라운드가 정해진 횟수에 도달했거나 라운드 상한에 도달했다는 것입니다.
- `report`는 살아남은 발견을 심각도순으로 등급, 출처와 함께 나열하고, 이어서 반박된 기록, 판정 대기 중인 기록, 강등된 기록을 보여 줍니다. 그다음 상태가 `done`이 아닌 모든 서브에이전트와 `blocked`를 반환한 모든 탐색자를, 마지막으로 상한(cap)을 나열합니다.

원장 파일은 마지막 턴이 유실되어도 남기 때문에, 사용자가 찾을 수 있는 곳에 둡니다. Python을 쓸 수 없다면 계획 아티팩트 안에 표를 만들어 같은 필드를 기록하고, 같은 규칙을 직접 적용한 뒤, 원장을 수동으로 관리했다고 보고서에 밝힙니다.

## 더 나오지 않을 때까지 반복

버그, 보안 관련 발견, 죽은 코드, 에지 케이스, 문서 묶음 안의 모순처럼 문제가 몇 개나 있는지 알 수 없을 때 씁니다. 탐색자를 한 라운드 보내고, 돌아온 기록을 원장에 추가하고, 새로 나온 것을 검증한 뒤 라운드를 닫습니다. 규모가 정한 횟수만큼 새 발견 없는 라운드가 연달아 나오면 멈춥니다. 정해진 횟수만 도는 루프는 롱테일을 다 훑기도 전에 중간에서 끝나 버려서, 찾기 쉬운 발견만 보고하고 나머지는 놓칩니다. 이 패턴은 그런 루프를 막아 줍니다.

## 다각도 탐색

탐색 각도 하나로는 모든 것을 볼 수 없고, 무엇을 놓치는지는 각도마다 다릅니다. 그러니 여러 각도를 동시에 돌립니다. 탐색자는 디렉터리, 심볼, 호출 그래프, 최근 변경 빈도(churn), 테스트 커버리지, 에러 문자열, 렌더링 결과를 기준으로 찾습니다. 이 플랫폼에서 가장 중요한 것은 시각적 각도입니다. 모든 라우트를 돌며 화면을 캡처하면 텍스트 검색으로는 쿼리조차 만들 수 없는 결함이 드러납니다. 그런 결함은 문자열이 아니라 렌더링 결과로 나타나기 때문입니다. 이 패턴은 한 각도만 볼 때 생기는 사각지대를 막습니다. 예를 들어 함수 이름으로 검색해서는 그 함수를 호출하는 동적 디스패치를 끝내 찾지 못합니다.

## 심사단

가능한 해법의 폭이 넓을 때, 처음 떠오른 그럴듯한 답이 최선인 경우는 드뭅니다. 출발점을 달리해 서로 독립적인 시도를 여러 개 만듭니다. 동작하는 가장 단순한 방법, 리스크 우선, 성능 우선, 사용자 우선 같은 식입니다. 점수는 어느 시도도 직접 만들지 않은 새 심사자가 매깁니다. 1위로 뽑힌 안을 바탕으로 삼고, 나머지 안에서 가장 좋은 아이디어를 가져와 붙입니다. 한 번 시도해 놓고 다듬기만 하면 처음 잡은 틀에 갇혀 그 안에서만 맴돌게 되는데, 이 패턴은 그것을 막습니다.

## 적대적 반박

발견을 하나씩 독립된 반박자들에게 보내면서, 반박을 시도하되 확신이 없으면 반박된 것으로 판정하라고 지시합니다. 과반이 반박하면 그 발견은 버립니다. full 규모에서는 반박자를 3명 씁니다. "이걸 반박해 봐"라고 하면 꼼꼼히 따져 보게 되지만, "이게 맞아?"라고 물으면 동의하는 쪽으로 기웁니다. 이 패턴은 그럴듯하지만 틀린 발견이 글솜씨만으로 살아남는 일을 막습니다.

## 다관점 검증

발견이 틀릴 수 있는 방식이 하나가 아니라면, 똑같은 반박자를 여러 명 보내지 말고 검증자마다 다른 관점을 맡깁니다. 정확성, 보안, 성능, 재현 여부 같은 관점입니다. 통과 기준은 과반입니다. 같은 질문을 던지는 에이전트 셋은 같은 사각지대를 공유하면서 그걸 합의라고 부를 뿐입니다.

## 완결성 비평가

보고하기 전에는 매번 실행합니다. `gravitas-completeness-critic`은 원장과 작업 목록을 읽고 '무엇이 빠졌는가'라는 질문 하나에 답합니다. 한 번도 탐색하지 않은 각도, 검증하지 않은 주장, 열어 보지 않은 파일, 실제로 구동해 보지 않은 상태, 렌더링해 보지 않은 라우트, 실패한 서브에이전트를 짚어 냅니다. 여기서 지목된 것이 다음 라운드의 작업이 됩니다. 이 패턴은 자신만만하지만 반쪽짜리인 답을 막습니다. 철저해 보이는 감사가 결국 틀리는 가장 흔한 이유가 바로 이것입니다.

## 단계적 에스컬레이션

대부분의 항목은 싸게 처리되고 몇 개만 비쌀 때, 모든 항목에 비싼 비용을 치르면 예산 대부분을 낭비하게 됩니다. 먼저 `flash_lite`로 전체를 한 번 훑고, 신호에 걸린 것만 상위 단계로 승격합니다. 훑은 개수와 승격한 개수를 모두 기록합니다. 승격 비율이 0이나 1에 가깝다면 작업이 균일해서가 아니라 신호 기준이 잘못 보정되었다는 뜻이기 때문입니다.

## 안티패턴

- 짐작으로 만든 작업 목록을 대상으로 팬아웃하기.
- 뒤 단계에서 발견끼리 비교하는 일이 없는데도, 모든 탐색자가 끝날 때까지 기다렸다가 검증을 시작하기.
- "이게 맞아?"처럼 맞다는 답을 구하는 식으로 묻는 검증.
