# DSH A/B 第三轮：用插件里的核对机制代替一句规则

**简体中文** · [English](./README.md)

第二轮（PR #2）说明，写一句“核实或删掉补充的数字、日期和步骤”并不会改变 deepseek-flash 的做法。所以第三轮我不再加句子，而是在插件里加了一个机制：声明核对（`dsh/lib/claims.js`，在 `dsh/index.js` 里接入，设置项 `claimCheck`）。每轮回答快结束时，插件找出草稿里既没有用户原话支持、也没有本轮任何工具结果支持的具体信息（带单位的数字、金额、日期、条款号和文号、电话、链接、引用原文、App 菜单路径，以及算不对的书面计算），提醒模型一次：逐条用工具核实、写出算式，或者删掉、说得宽一些，然后重新给出完整回答。

简短结论：Gravitas 在投票、得分和错误补充声明上都胜过原版 DSH，但没过我事先冻结的两条限制（含糊要点数和篇幅），所以不算赢。而且起作用的不是声明核对：关掉核对的 Gravitas 以 26 比 13（1 平）胜过开着核对的 Gravitas，核对删掉正确细节的比例还高于删掉错误细节的比例。我已把它改为默认关闭。

## 怎么测的

- 跑之前新写了一组留出题：7 条中文、3 条英文日常请求，每条都带一个诱导性的错误前提（[prompts](prompts)）。答案要点由四个核查者对照官方来源核实（[sources](sources)），再由一个从没看过任何回答的代理拆成编号的必答要点（[keypoints](keypoints)）。
- 三组都用 deepseek-flash，每组每题跑两次：原版 DSH（gv-plain）、带核对的 Gravitas（gv-grav，本分支）、同一个 Gravitas 但关掉核对（gv-grav-nocheck）。共 60 次运行，按带种子的三元组排程，三组同时跑。所有运行都有效；从第一次到最后一次代码完全相同（[freeze-start.txt](freeze-start.txt)、[freeze-end.txt](freeze-end.txt)，提交 a261ba5）。之前先在开发题上做了两次冒烟运行（[smoke](smoke)）。
- 判定标准在运行前冻结（[criteria.md](criteria.md)）。随后三个独立评审专门找“不真正变好也能过关”的最省事办法；他们的发现在任何留出题运行之前就收紧了核对和标准（见 criteria.md 的修订部分）。
- 盲评：两位评审（Claude Opus 5.5、Claude Sonnet 5.5），每个会话只评一对，A/B 顺序按设计平衡，打五项分、标要点、列出补充声明。除了 Gravitas 对原版，还评了 A/A 对（测噪声底线）、带核对对不带核对、每份被提醒的草稿对它的修改稿。所有补充声明备注（1,569 条）都由两位重标者盲标；只有两人都判错且给出依据时才算错。判定代码由另一个代理只根据标准写成并冻结（[verdict.py](verdict.py)，自测 167 条断言）。
- 相比第二轮修了一处运行环境：DSH 的 Windows 沙箱需要工作文件夹的“完全控制”权限，而我的 W: 盘只给“修改”权限，所以第二轮两组的所有 shell 调用都失败了（35 次全失败）。第三轮我给自己的账户开了运行文件夹的完全控制权限，各组 shell 都正常。

## 结果

主比较：带核对的 Gravitas 对原版，20 对、40 票（[verdict.txt](verdict.txt)）：

| 关卡 | Gravitas | 原版 | 限制 | 结果 |
|---|---|---|---|---|
| 投票（净胜超过 A/A 噪声底线 8） | 26 | 13（1 平） | 净胜 > 8 | 通过（净胜 13） |
| 每位评审 | Opus 13–7，Sonnet 13–6 | | 胜多于负 | 通过 |
| 按请求胜 / 负 | 5 | 2（3 持平） | 胜更多 | 通过 |
| 平均分（满分 50） | 37.43 | 35.35 | 不低于原版 | 通过 |
| 要点正确 / 错误 | 187 / 2 | 183 / 6 | 不少于 / 不多于原版 | 通过 |
| 要点含糊 | 62 | 55 | 不多于原版 | **未通过** |
| 错误补充声明（两位重标者都判错） | 26 | 35 | 少于原版 | 通过 |
| 陷阱分低于 8 | 40 中 5 | 40 中 11 | 不多于原版 | 通过 |
| 篇幅中位数 | 2448.5 字符 | 2282 字符 | 比值 0.70–1.00 | **未通过**（1.07） |
| 含糊措辞（第一轮表和扩展表） | 更少 | | 不多于原版 | 通过 |
| 没打开网页却声称查过来源 | 0（20 次中 0 次符合条件） | 0（20 次中 5 次符合条件） | 不多于原版 | 通过，但 Gravitas 一侧没测到 |

来源关卡只统计没打开任何网页的运行。Gravitas 的每次运行都打开了网页，所以这一关在 Gravitas 一侧没有可测的对象，等于没测；它不能说明 Gravitas 会不会编造来源。

判定：未证明（含糊要点和篇幅）。39 张非平票的符号检验：p = 0.053。分语言：中文 16–11（1 平），英文 10–2。评审没有偏向更长的回答（20 票给更长的，19 票给更短的）。

各组各语言的篇幅（字符中位数）：原版 2282（中文 2282，英文 2290）；带核对的 Gravitas 2448.5（2303.5，3187.5）；不带核对的 Gravitas 2297.5（2063.5，3158.5）。英文里两个 Gravitas 组都是原版的约 1.38 倍，所以让英文回答变长的是规则而不是核对；读下来，多出来的是一段解释回答纠正了请求里哪些说法，以及背后的法律依据。

### 声明核对做了什么

| | |
|---|---|
| 触发 | 20 次 Gravitas 运行中 18 次 |
| 每份草稿列出的条目 | 平均 6.95 条 |
| 修改稿怎么处理这些条目 | 删掉 60，找到来源 25，推导出 3，保留未支持的 51 |
| 草稿对它自己的修改稿 | 修改稿 25，草稿 1，平 10 |
| 带核对对不带核对 | 带核对 13，不带核对 26，平 1 |
| 被列出的条目中修改稿删掉的比例（按对照答案的盲标） | 标为正确的 38%，标为错误的 24%，无法核实的 80% |

修改稿胜过自己的草稿，说明多改一遍对单个回答略有帮助。但核对删掉正确细节的比例高于错误细节，所以它只是一次泛泛的修改，不是在识别错误；带核对的运行输给了不带核对的运行。每次运行耗时（中位数）：原版 129 秒，不带核对的 Gravitas 142 秒，带核对 217.5 秒。

### 不带核对的 Gravitas 对原版（事后加评，未预先登记）

判定之后，我用同样方法、同一批运行，把关掉核对的那一组和原版做了比较，因为归因结果说明它显然是下一轮的基线。这不在冻结的计划里，所以它是下一轮设计的依据，不是本轮的结果（[blind-map-posthoc.json](blind-map-posthoc.json)、[blind/posthoc-grades](blind/posthoc-grades)）。下面所有数字，以及上面“带核对对不带核对”和“草稿对修改稿”的数字，都来自 [tally_posthoc.py](tally_posthoc.py)（`python tally_posthoc.py --events <存放运行 NDJSON 的文件夹>`；事件流没放进仓库，因为里面有抓取的网页内容）。

|---|---|---|
| 投票（40） | 33 | 7 |
| Opus / Sonnet | 17–3 / 16–4 | |
| 中文 / 英文 | 23–5 / 10–2 | |

按冻结的限制，这一组通过了投票、每位评审、要点、陷阱和含糊措辞。篇幅没通过：中位数比值整体 1.007，超过 1.00 的上限，英文 1.38。错误补充声明这一关没测，因为它的备注从没重标过；来源关卡也测不了（这一组没有一次运行是不开网页的）。

## 前后对比

- 第二轮（规则句子）：Gravitas 19，原版 16，平 5；错误补充声明 30 对 23；篇幅比值 0.95。
- 第三轮（声明核对）：Gravitas 26，原版 13，平 1，超过实测噪声底线；错误补充声明 26 对 35；但篇幅比值 1.07，含糊要点比原版多。两轮的题目和评审不同，不是同条件比较。
- 第三轮最有力的发现是事后加评：不带核对的常驻规则在这里以 33 比 7 胜过原版。但它仍然没过篇幅限制（整体 1.007，英文 1.38），补充声明也没有重标，所以它是第四轮的线索，不是一次胜利。

## 分支上改了什么

- `dsh/lib/claims.js` 和 `dsh/index.js` 里的钩子保留，测试也在，但 `claimCheck` 现在默认关闭。`GRAVITAS_CLAIM_LOG` 记录核对列出了什么、修改稿怎么处理，用于测量。
- `docs/dsh-ab/WIN_CRITERIA.md` 冻结了之后每一轮“胜过原版”的标准，包括全部四种语言。

## 核对的已知弱点

- 它把“decide 1”读成了日期，还把一个数字读成了 22026 年。用汉字写的日期（下个月二十一号）读不出来。
- 多步算出、但没写出算式的数字（比如月度预算）会被列为未支持；模型大多保留了它们。
- 基于 NDJSON 日志的离线重放会多算，因为日志把每个工具结果截断在 8 KiB；以运行时日志为准。
